# 用实测参考时钟重做时序签核

## 适用场景

PL 时钟由 PS 的 PLL（Zynq 的 `pl_clk0` 等）提供，或在 PL 内用 MMCM 从它倍频得到；
Block Design 里填的是标称频率（例如 100 MHz），但板上 FSBL 实际配置的分数分频可能使真实频率略有不同。
提频、报告吞吐 / GOPS、或计算理论峰值时都会用到真实频率。

## 使用方法

1. **在板上读出真实频率**：通过 `/dev/mem`（Python `mmap`）读 PS 的 PLL / 分频寄存器（本板为 RPLL 分数分频），
   按 TRM 公式算出 `pl_clk0` 的实际频率；也可以用一个 PL 计数器对已知时钟计数交叉验证。
2. **按真实频率重新约束**：在实现后的设计检查点（DCP）上，把输入时钟周期改成实测值，
   重新跑 `report_timing_summary`，记录 WNS / WHS。
3. **报告里统一使用真实频率**：吞吐率、GOPS、峰值利用率都按真实频率计算，并注明"标称 / 实测"两个数。
4. **一次只跑一个完整的 Vivado 构建**（多个实例同时初始化 tclapp 会互相冲突）。

```
vivado -mode batch -source retime_f_real.tcl -tclargs f150 f150nv   # 对已实现的设计按实测参考时钟重做时序
```

## 失效条件

- PL 时钟来自板上独立晶振（不经过 PS PLL）：直接用晶振标称值即可，无需此流程；
- 更换 boot.bin / FSBL 后 PLL 配置可能改变，需要重新读寄存器；
- 只适用于"同一份实现结果换约束重新分析"，不能代替按新频率重新布局布线。

## 已验证效果

- 本板 `pl_clk0` 标称 100 MHz，实测 101.376 MHz；MMCM 标称 150 MHz 的固件 f150 实际运行在 152.15 MHz；
- 按实测频率重新签核：f150 WNS +0.470 ns，f150nv WNS +0.486 ns / WHS +0.015 ns，均收敛；
- CPU 写 PL BRAM 实测 1616 MB/s = 16 B × 101.376 MHz 的 99.6 %，与实测频率吻合，反过来也证明了读数正确。

## 来源

提频固件 f150 上板后，并行的性能测量对话在写结果前做了一致性检查：整网加速比 ×0.6677 与"100 → 150 MHz"吻合，
却与交接文档中记录的 101.376 MHz 参考时钟对不上。只读方式读出 PLL 寄存器后确认：设计按 99.999 MHz 输入做，
实际输入是 101.376 MHz，固件真实运行在 152.15 MHz。交接文档里早有这个数，做提频时被漏看了。
随即按真实频率对 f150（及后来的 f150nv）重做了时序检查，并把"每版新固件按实测时钟复核"写成规则。
完整经过见 `report/llm_collaboration/case_01_real_clock.md`。

实例：`tcp_image/tcp_image_rx/vivado/f_clock/`（retime 脚本与报告），`perf_j/`（带宽与峰值测量）。
