# 板上部署与回滚流程（PS 服务 + 比特流）

## 适用场景

Zynq / Zynq UltraScale+ 板上跑着一个长期服务（PS 端 Linux 程序，通过 systemd 启动）和一个 PL 比特流，需要反复升级其中之一，
而板子同时还在被演示、测试使用，任何一次升级失败都不能让板子"砖掉"或停在半新半旧的状态。

## 使用方法

把部署拆成互不重叠的四步，每一步只做一件事：

1. **prepare**：把新源码上传到板上一个带时间戳的新目录（`releases/v5_<utc>/`），在板上原生编译，跑单元测试；
   同时备份**当前正在运行的**可执行文件和 systemd unit。此时还没有切换任何东西。
2. **activate**：停服务 → 安装新可执行文件 → 启动 → 校验运行文件的 sha256 与编译产物一致。
3. **验收**：自动跑回归（逐位比对 + 稳定性），任一项失败就执行第 4 步。
4. **rollback**：恢复 prepare 时备份的可执行文件和 unit，重启服务。

比特流单独走一条链：新比特流装到 `/lib/firmware/ai_sys.bin`，旧的改名为 `ai_sys.bin.before_<tag>`，重启生效；
驱动只在比特流的 sha256 出现在"指纹清单"里时才去访问对应的 PL 外设（防止旧驱动访问新比特流里不存在的地址导致 PS 挂死）。

验收脚本分两个阶段运行，便于对比：

```
python acceptance.py baseline       # 旧版本上：备份、编译测试工具、跑一遍全部检查，记录基线
python acceptance.py deploy_tests   # 安装新版本、重启、再跑同一套检查；任何一项不过就自动回滚
```

规则：

- 一次只改一样东西：换比特流时 PS 服务不变，换服务时比特流不变；
- 每个版本都有明确的上一版（回滚链），不允许跨版本回滚到"不兼容的旧服务"；
- 工作区里还没准备部署的源文件用 `prepare --exclude=src/x.c` 排除，或用 `--pin=src/x.c=路径` 固定为指定版本，
  避免把别的分支的半成品一起编进去。

## 失效条件

- 板上没有足够空间保存一个完整的 release 目录和备份（本板根分区只有约 7 GB，曾经剩 481 MB）；
- 改动涉及 boot.bin / FSBL / 设备树：这些不在本流程覆盖范围内，回滚需要换 SD 卡上的文件；
- 新比特流让 PS 在启动阶段就挂死（例如 AXI 地址冲突）：此时服务层回滚无效，需要在 SD 卡上换回 `.before_<tag>`。

## 已验证效果

- 本作品 PS 服务从 v5.1 升到 v5.26、比特流从 V9b 升到 f150nv，共二十余次部署全部走这套流程；
- 其中 v5.16 第一次部署时 `ct_seg + render3d` 段错误，被验收脚本发现后自动回滚，修复后重新部署，回滚链保持干净；
- 每次比特流升级都有 BoardCheck 全项 + 5000 帧稳定性 + 回归组逐位一致的记录，见 `acceptance/`。

## 来源

- 早期手动 `scp` + `systemctl restart` 升级时，曾出现新旧可执行文件和 unit 不一致、回不去上一版的情况；
- 回归脚本中途被打断时会跳过 `finally`，导致仓库里的证据文件被覆盖——因此改为"先备份证据、再运行"；
- 新旧服务对比特流的假设不同（v5.14 遇到 r1 固件会直接退出），因此引入了指纹清单和"不得退回到不兼容版本"的规则。

实例：`tcp_image/tcp_image_rx/boot/deploy_board_v5.py`（prepare / activate / rollback / status），
`acceptance/board_acceptance_nv/acceptance.py`（比特流 f150 → f150nv 的验收与自动回滚）。
