# 板端上位机：占用实测 + 「开始采集 / 曲线拖动」卡顿修复（2026-11-19）

**一句话**：卡顿不是一个原因。**开始采集时那一下卡死**是消息循环一趟把队列掏空（实测一次 **7.4 s**），
改成每趟最多 25 ms 后降到 **0.7 s 量级**；**拖动曲线**的 Python 部分本来就只占两三成，
剩下的是 GTK 兼容层每帧重绘（cProfile：`pump_events` 占 70%），这轮把合成、缓存、后台预取都收了收
（3 条掩膜的合成 **28.6 → 19.4 ms**），但 **P90 仍是 ~90 ms** —— 再往下要动兼容层的画布实现。

- 合成加速的逐字节对拍：`04_verify/verify_compose_fast.py`（324 个随机用例 + 两条旧路径，**0 差异**）
- 卡顿探针：`/tmp/probe_stutter2.py`（心跳法：每 10 ms 排一次 `after`，量最大间隔）、`probe_gtk_iter.py`（GTK 单轮耗时）

## 二、「点开始采集」为什么卡

引擎会把整段帧（1200 帧）一口气推过来，推进 `queue`；界面在 `_poll` 里 `while True: get_nowait()` **一次掏空**。
每帧要解掩膜、存原生帧、必要时渲染，实测 **单次 `_poll` 卡 7.38 s** —— 期间画面、按钮、「停止」全无响应。

改法：`_poll` 每趟最多占主循环 `POLL_BUDGET = 25 ms`，剩下的 4 ms 后下一趟接着取（事件一个不丢）。

| 指标（采集 12 s） | 改前 | 改后 |
| --- | --- | --- |
| 主循环最长一次阻塞 | **7384 ms** | **725 ms** |
| 心跳 P90 / P99 | 337 / 493 ms | 102 / 507 ms |
| 归因到各回调的总工作量 | 14.4 s | **6.9 s** |

另外把现场模式那三样「一次共约 70 ms」的重绘（容积曲线 / 逐帧延迟图 / 预算文字）从 0.25 s 改成 0.40 s
一刷；预览间隔 0.12 → 0.08 s（约 8 → 12 帧/秒，`max(RENDER_GAP, 1.4×上一帧耗时)` 的自适应保护不变）。

## 三、「容积曲线上拖动」为什么卡

拆成三层（198 次 60 Hz 扫全片，心跳法）：

| | 改前 | 改后 |
| --- | --- | --- |
| 合成调用 `_vprep_build` | 99 次 / 2086 ms | **60 次 / 996 ms** |
| `_frame_photo` | 1608 ms | 740–1176 ms |
| `compose_preview`（3 条掩膜） | 28.6 ms | **19.4 ms**（1 条掩膜 12.8 → 12.8） |
| 心跳 P90 / 最大 | 90.7 / 1266 ms | 90.5 / 1080 ms |

第一层（我们自己的代码）这轮做了三件事：

1. **合成不再用 PIL 的 `paste(颜色, 掩膜)`**（675×448 上一条 5.5 ms）：改成 numpy 布尔上色，
   最近邻放大索引**让 PIL 自己算一次**并存下来（放大/缩小两条分支取整规则不同，自己推公式会对不上，
   实测差几十个像素）。三条掩膜 28.6 → 19.4 ms，一条持平，输出**逐字节相同**。
2. **缓存放得下整段片子**：底图 64 → 128 帧、整帧照片 32 → 40 帧（99 帧的片子原来扫一遍有一半是冷的）。
3. **后台预取让路**：预取线程合成一帧要十几毫秒，用户一拖它就停手（`_render_pending` / 最近 200 ms 内渲染过就 sleep 50 ms）。

第二层（GTK 兼容层）没有动：cProfile 显示拖动时 **`pump_events` 占 70%**（单次 `update()` 平均 **22 ms**，
全部是我们的 Python 调进去的 GTK 布局 + 重绘），我们自己的 `compose/_render/_to_pixbuf` 加起来不到 20%。
心跳 P90 90 ms 基本就是它。要再快只能改兼容层的画布实现（例如把曲线光标做成独立图层，
不再整张 560×200 重新合成 + 上传），收益大但风险也大，这轮没做。

> 试过但**没上板**：给 `pump_events` 加 12 ms 时间预算 —— 实测没变化（慢的不是轮数多，是单轮重），
> 所以没有部署，避免白白增加变量。
