# 版本演进说明（PL 主线）

这份文件按**里程碑版本**顺序，逐个说明每个版本的定位、特性、实现方式、关键文件、实测数字，以及与前一版的差异和最终结论。

> **怎么读**：只想快速定位"哪一版在跑"，看 [`README.md`](README.md)；想看某个专题（上位机、板端、纠错、清理），看 [`专题工作说明.md`](专题工作说明.md)；想看 `2026pld` 里那 11 笔零碎改动，看 [`2026pld_变更记录说明.md`](2026pld_变更记录说明.md)。

**三条贯穿全线的约束**，读每一章时都成立：

1. **结果必须逐位不变**。整数通路，任何一刀的成败都要同时看「逐位一致性 + 实钟 WNS + 资源账」三张表，只报面积或只报毫秒都不算数。
2. **先量后改**。每一刀之前都先把耗时/资源拆开量一遍，量完经常发现想改的那一项根本不是瓶颈（P1、P3、P9 都是这么被否掉的）。
3. **板上的实钟不是标称**。`pl0_ref` 由 BOOT.BIN/FSBL 定死，加载比特流改不了；本板实测 `pl0_ref = 101.376 MHz`，对应 152.15 MHz。所以「标称 150 MHz 过约束」不等于「板上能跑」。

## V00 分享包底版（2026-11-13）

**一句话定位**：`PLD_share_lite_20261113` 里的主工程 `fpga-echo-workstation`，是「一块 FZ3B 上跑固定结构 U-Net 张量引擎 + 心脏主线整病例工作流」的完整可交付底版，后续 P6/P7/P8/P10/P13/扇形全部以它为基线。

**硬件与平台**

| 项 | 事实 |
| --- | --- |
| 板卡 | FZ3B，Zynq UltraScale+ MPSoC，器件 **XAZU3EG-1SFVC784I**，4 GB DDR4（4×MT40A512M16LY，64 bit） |
| PS | 4×Cortex-A53 + 2×Cortex-R5 |
| 系统 | 厂商 Ubuntu 18.04，内核 **4.14.0-xilinx-v2018.3** |
| 工具 | Vivado / Vitis HLS **2025.2** |
| PL 时钟 | 固件 `ai_sys_f150nv` 标称 150 MHz；板上 `pl0_ref = 101.376 MHz` → 实钟 **152.15 MHz**，由 BOOT.BIN/FSBL 决定，加载 `.bit` 改不了 |
| 网口 | PHY = KSZ9031RNX，接 **PS BANK502 MIO64..77（RGMII）**；PL 拿不到 RGMII，所以 TCP 协议栈必须在 PS Linux 里跑，板端只是用户态 socket 服务端 |
| 板上 IOB | Bonded IOB = **0** —— 一个 PL 引脚都没用，计算与存储都在 PL、通信全走 PS 内部 AXI |

**核心特性**

- **一个比特流、多种任务**：30 节点固定结构引擎 + 换权重即换程序。内置程序 0–22（fundus / skin / echo_lv / echo_inter / echo_seq / reg_absdiff / op_* / ct_spleen / echonet_lv / 左房 / 心外膜 / 视盘 / 视杯 / cardiac_rv / cardiac_ra），运行时还可用 `.upk` 程序包安装 17–254 号程序，服务端和比特流都不用改。
- **心脏主线**：A4C 单切面；`echo_ef` 四种模式（0/1 整段与实时档、2 关键帧+质量灯+保形区间、3 现场模式）；mode 2/3 可叠 "HC01" 全心扩展（6 节段室壁运动 + 右室/右房程序 21/22 + RV/LV、RA/LV 面积比）。
- **PL 三块能力**：U-Net 张量引擎、行缓冲图像预处理（`img_proc_axil`）、像素级后处理（`pp_layer`）。
- **PS 负责通信、调度、整病例任务**（CT 整卷、整段心超、Simpson、配准搜索）与临床测量；PC 上位机只选文件与显示。
- **逐位验证体系**：板上输出 = HLS 位级参考 = 离线评测；每次换固件/服务端都跑 BoardCheck 31 项、严格逐位比对、PL 后处理向量、程序回归、稳定性帧。

**实现方式（机制层）**

*PL 引擎结构*

- `30 节点 = 1 输入 + 20 CONV（12×3×3 + 6×1×1 + 2×2 转置）+ 9 ELT（5 Add + 2 Concat + 2 MaxPool）`，共 **34 201 参数**。
- 两个 HLS 核 `conv_layer` / `eltwise_layer` 串联；激活为 **NHWC**、每值 **int16 容器**、通道补齐到 **8** —— **一个 128 bit 字 = 一个像素的 8 个通道**；权重 64 bit 字。

*条带 + halo 调度*

- 整网张量常驻 PS 内存（30 节点约 85 MB）；PL 里只有 **256 KB 张量 BRAM**（128bit × 16384，@`0xB0000000`）当"一层条带的暂存"。
- 每个节点按**输出行**切条带：3×3 要 `y±1`（喂 S+2 行、丢首尾各 1 行），1×1 与转置无 halo，Add/Concat 逐像素，MaxPool 要 `2y, 2y+1`；图像边界由 PS 自己补零行。
- 128×128 一次推理 **66 个条带**、搬 **12.4 MB**（put 7.03 MB / get 5.34 MB）。

*地址与搬运*

- `M_AXI_HPM0_FPD`（32 位）挂 `img_proc_axil` `0xA0000000`、conv 控制 `0xA0010000`、eltwise 控制 `0xA0020000`、`pp_layer` `0xA0030000`；`M_AXI_HPM1_FPD`（128 位）挂张量 BRAM `0xB0000000`，IP 主口也指同一块存储 —— 两条路同宽，**全程没有位宽转换器**（32↔128 转换器在本板会丢非 16 字节对齐的写数据）。
- 搬运走 `plbram` / `plbdma` 两个内核模块；读回走 GDMA，**逐行必须合并成整条带**、写侧不用 DMA；J1 让"读回"与"下一次写入"重叠（`pl_split.overlap = true`）。

*PL 前后处理*

- `pp_layer`：阈值、×2/×4 双线性放大、连通块（含 8 连通）、最大块 + 填洞、4×4 分块和。
- `img_proc_axil`：归一化 / 阈值（只看 G）/ 边缘（Sobel）/ 伪彩（jet）/ 组合 / 直通；另有"边缘叠加"在 PS 侧做（PL 无此模式）；帧缓冲为全帧 2 Mb。

*PS 服务端*

- C 写的用户态 socket 服务（`src/` 整目录上传到板上编译），行包协议 = `row(u16)+length(u16)=1536+crc16(u16)` 共 1542 B/行、512 行。
- DDR 保留区 `0x40000000` 4 MiB、设备树 `no-map`。
- 任务层：`caps / ct_seg / reg_search / echo_ef / simpson_ef / render3d / overlay / strain / tile`。
- 关键帧调度让 **PL 只算约 18 % 的帧**，其余帧由板上块匹配跟踪补。

*部署*

- 比特流放 `/lib/firmware/ai_sys.bin`，由 `ai-sys-bitstream.service` 开机加载；其 sha256 要追加进 `/lib/firmware/ai_sys_pp.sha256`（**漏了会静默关掉 pp**）。

## V01 P6 ADD 融合交付（2026-11-14）

**一句话定位**：把 5 个 Add 节点并进卷积的**写出级（MERGE）**、删掉 eltwise 里闲置的 Add 硬件、时钟退到 146 MHz 标称的交付版 —— 单次推理快约 **5.5%**，**结果逐位不变**。

**核心特性**

- 一个 Add 节点原来要"卷积写 BRAM → eltwise 读两路、加、写回"，一趟 **5 次 BRAM 访问**；融合后卷积在**回写那一趟**直接算 `round(m0*a + m1*skip)`，只要 **3 次**。
- 9 个 ELT 节点占全部张量流量 **30 %**（3.77 MB / 12.48 MB），融合砍在它身上。
- `use_skip = 0` 时与原版逐位一致，老测试向量仍能跑。
- 代价是 conv 多 32 个乘法器（DSP），同时删掉 eltwise 的 `MODE_ADD` 把 32 个 DSP 还回来 —— 整板 DSP 326 回到 **291**。

**实现方式（机制层）**

*HLS（conv）*

- `conv_layer_p6.cpp`（V12 副本）新增一路 `m_axi` 输入口 `skip`（独立 bundle `gmem_skip`）+ 6 个 AXI-Lite 参数 `use_skip / sk_m0 / sk_m1 / sk_shift / sk_qmin / sk_qmax`。
- 在 **MERGE 循环**"把 orow 回写进 BRAM"那一支里先读 `skip[n]`，逐 lane 算 `round_clamp(m0*a + m1*skip)`（与 eltwise 逐字相同：对绝对值四舍五入、半值取偶）。
- **为什么放在 MERGE 而不是计算流水线**：V10/V11 把 m_axi 折进 `STEP_ALL` 后慢 1.5–1.6 倍；MERGE 本来就是"回写本行 + 预取下一行"的独立一趟。

*HLS（eltwise）*

- `MODE_ADD` 分支直接 `return ELT_BAD_CONFIG`（不留循环），只留 Concat / MaxPool；综合 DSP 76 → 44、LUT 24 909 → 17 064。

*BD / PS*

- 数据互联从 9 个从口加到 **10 个**（S09 = conv 的 skip），构建脚本 `build_ai_sys_p6a.tcl`。
- `unet_ai.c` 新增 `build_fuse_table()`，融合发生在 Add 的 **in1 生产者**上（节点 3/8/13/20/27 吸收 4/9/14/21/28，因为 `in0 < in1` 恒成立、in1 的生产者后跑）；跑该 conv 时带 skip 地址与参数，然后**跳过 ELT 调用**。
- 覆盖检查不通过就打印 `[ai] FATAL: … not fused` 并拒跑（`return -5`）—— **宁可报错也不静默算错**。
- **寄存器表变了**：PARAMS 后面插了一个 skip 指针，后面的寄存器整体后移 **0x0C** —— 服务端与比特流必须一起换，一新一旧必写错寄存器。这条后来在 P7 上真的引发了事故（见 V02）。

*两个上板才暴露的坑*

1. skip 必须带行偏移（`srow = skip + y*out_w*cog`），否则每行都读第 0 行。
2. 两路系数要对调（`C_SK_M0 = e->m1`、`C_SK_M1 = e->m0`）。

**与前一版的差异**

- **PL**：conv 多一路 `skip` 主口与 6 个 AXI-Lite 参数、MERGE 内做融合；eltwise 删 `MODE_ADD`；BD 数据互联 9→10 从口。
- **PS**：`unet_ai.c` 增加融合表、skip 缓冲与寄存器写入，跳过被吸收的 ELT 调用；conv 寄存器偏移整体后移 0x0C。
- **固件**：LUT +2 049、DSP +1、BRAM +4；时钟 150→146 标称。
- **行为**：数值逐位不变（EF 不变），单次推理 −5.5%；但"没有 Add 硬件的退路"。

**为什么这么做**

- 先量后改：11-13 加 12 个阶段计时点，测出一次推理 22.5 ms 里 `ap` 14.08 ms（62%）、`put` 4.10（18%）、`get` 4.69（21%），整段时长先动 PS、降延迟只能动 PL。
- **P1（张量 BRAM 256→448 KB）实测净亏**：条带 66→42，`ap` 只降 0.27 ms（每条带约 11 µs，不是外推的 75 µs），但重叠变差 `unet_run` 反升 2.9%。由此"少条带 / 减 halo / 第 4 行槽预取"整族作废。
- **P3（1×1 走窄通路）动手前被证伪**：`conv_layer.cpp` 第 91 行 `taps = mode==MODE_CONV3 ? 9 : (MODE_CONV1 ? 1 : 4)`，1×1 早已是 1 抽头。
- **P9（去 bounce memcpy）上限只有 0.63 ms**（2.56 ms 里 1.93 ms 已被 J1 藏掉），不值得动内核。
- **"先把 ELT 搬到 PS"的方案失败**：逐位成功但 `unet_run` 22.42 → 46.62 ms，根因是 **A53 没有 32×32→64 的 SIMD**，`a*m0+b*m1` 的 47 位乘积只能标量跑长依赖链（约 25 ns/lane）。结论：这类定点乘加必须留在硬件。
- **DSP 账**：ELT 的 9 个节点占 30% 流量但两路输入全是单消费者；逐位融合"乘法器从 ELT 搬到 conv、不消失"，省的是传输不是 DSP。XU=3 需要约 240 DSP（整板约 370/360 = 103%，装不下），所以 P6 是"收益大、不欠新债"的那一档。

**结论与遗留**

- **eltwise 不再支持 Add**：服务端启动时检查"每个 Add 是否都被融合"，有一个没覆盖就拒跑；`UNET_NOP6A` 的 A/B 退路因此失效。
- 融合只处理**两路输入都是单消费者、形状一致**的 Add；网络结构变了要重新核对 `build_fuse_table()` 的条件。
- **实钟下 WNS −0.033 ns 没过签核**（只有标称 146 过），功能与逐位都通过但签核不干净。
- 时钟比 f150nv 低 0.6 %（152.15 → 约 151/148），这部分抵消了一点 ap 收益，已算进上面数字。
- 时序教训：同结构换约束，布局布线能摆出 **±0.35 ns** 差距，比降 0.6 % 时钟（+0.048 ns）大一个量级，"调频率追时序"上限很低。

## V03 P8 conv 两级 requantize（2026-11-14 夜 ~ 11-15）

**一句话定位**：想解决 P7d 上"全片最差路径"（conv 的 requantize，6.309 ns / 实钟 slack −0.073），结果证明**拆 requantize 三次全错、HLS 本来就自己切好了三段**，真正管用的是**把热循环里的 `%3` 换掉** —— p8c 实钟 WNS −0.050 → **+0.005**、0 个违例端点、LUT 再降 8.4 %，并且**在板上跑通整网（0/262144）**。

- p8c 只改一处：把内层热循环里的 `(iy + 6) % 3` 换成递增计数器；**requantize 一字未动**、接口/寄存器映射/内存布局一字未动。

**为什么这么做 / 为什么拆拍必败**

- 动机来自 P7d 的验收：全片最差路径是 conv 内部 requantize 链，**63.8 % 的时间在 DSP 内部**（16 级里 6 个 CARRY8 + 8 个 DSP48E2 内部 + 2 个 LUT3/LUT4），"激进的布局布线能动的部分不到 40 %"。
- **为什么拆拍必败**：HLS 本来就已经把这条链切成三段 —— `acc →(relu)→ a` 一拍、`a → 乘+加 → v` 一拍、`v → 收尾 → resA` 一拍，那个"乘+加"段就是 p7d 的 6.309 ns。每显式声明一次新边界，HLS 就重新调度一次：切在 v 时它把原本插在 `a*mult` 后的内部寄存器**并掉**（relu+乘+加全挤进一拍 → 7.081）；切在 product 时又把已寄存好的 `mult_buf[sg][o]` 选择**拉回组合路径**（→ 6.790）。
- **为什么去 `%3` 才是那一刀**：`ir` / `fr` 每行只 +1，槽位就是 0→1→2→0，递增计数器与 `%` 逐位等价；但 HLS 为等那个 36 拍流水除法器的商，把热循环沿途信号寄存了 35 拍 —— FF 掉 13 018 的主要来源在这里，不是"省了一个除法器"。
- 另一条被作废的假设：P8a 阶段报告先猜那条 6.55 ns 的行级控制路径也像 `%3` 造成的，**查证后收回** —— `empty_reg` 出现在顶层 `conv_layer.v` 的"每输出行一次"的行级控制逻辑里，两刀都在内层循环，碰不到它。
- **方法论教训**：csynth 的"估计时钟"不能当证据（基线整核 7.300 ns 被 MERGE 钉住完全没动、STEP_ALL 只降 78 ps），只有整片 impl 的 `report_timing` 能回答"拆拍到底赚了多少"。

**结论与遗留**

- **`+0.005 ns` 属于"纸面收敛"**：动态时序检查器没开，也没做温度/电压角。
- 剩下的最差路径（6.259 ns）已经不是 requantize，而是 **compute 段每拍 8 次 MAC 点积 + 累加**（18 级 = 8 DSP + 5 CARRY8 + 5 LUT），是 **II=1 的循环携带依赖** —— 这就是这套结构在 152.15 MHz 的天花板。
- 冷路径还有两个 `%3`（`ry % 3`、`pslot = (prow+6)%3`）没换，消掉最后一个除法器实例约 394 FF / 238 LUT，但收益很小。
- 上板自检是 512×512 眼底整网，不是心脏 112 档；耗时 300 ms 量级与 128 档的 21 ms 不是一个口径，不能混比。

## V04 P10（S1a + S2）（2026-11-15）

**一句话定位**：在 P8c 之上只做两件**逐位不变**的表达式改写（移位量常量化 + 计数器窄化），纯为降 CLB，不改调度、不改数值；已出比特流并上板，整网 `mismatch 0 / 262144`。

**核心特性**

- **S1a**：`requantize()`（conv，8 lane）、`sk_round_clamp()`（conv skip 融合，8 lane）、`round_clamp()`（eltwise，8 lane）三个函数里的 `magnitude >> shift` 从 **65 位变量桶形移位器**改成静态移位分支 + 窄 mux；mask/half 写成常量；余数与半值比较降到 32 位；**先判饱和**再在 17 位上做加/取负/夹紧。
- **S2**：15 个循环计数器 `int` → `ap_uint<8>/<4>/<2>`、`ap_int<16>`（都 ≤144）。
- 运行期零代价、逐位不变，因此**不需要重跑 VAL**。

**实现方式（机制层）**

- `shift` 只有 6 个取值 `{0,23,27,28,29,30}`（扫遍 `unet_models.c` 4×30、`unet_net_data.c` 30、`skin/board/gen/unet_net_data.c` 30 的并集，27 出现在 `unet_net_data.c` 的 L1）。每条 `case` 里 `quotient = magnitude >> N` 变成一根线抽头，外面套一个 5 选 1 的 65 位 mux；`mask` / `half` 直接写常量，余数只取低 32 位。
- **等价性依据**：输出必然被夹到 int16，所以 `quotient ≥ 32768` 时一定饱和到 `qmax`（负则 `qmin`），不必真做 65/67 位加法与比较；舍入规则一字未改（仍 round-half-to-even，tie 看 `quotient[0]`）。
- 实际 diff 里落地的是 `ap_int<17> r`（报告正文伪代码写作 `ap_int<18>`，以 diff 为准）；eltwise 的 diff 则是把基线里那份**手工位切片**的 6 case 版本（含 shift=10）换成同一套，同时把入口校验里的 `shift != 10` 去掉。
- **S2 机制**：每个 32 位 `++` 要 4 个 CARRY8、每个比较要 4~5 个 LUT，窄化后进位链与比较器一起缩。

## V06 P11（S6 指针累加实验）（2026-11-15，被否决）

> **这一版没有上板。** 留在归档里是因为它留下的"发现"比它自己值钱，而且后来的人很容易再想到同一个主意。

**一句话定位**：S6「把 conv 每行的地址乘法换成指针累加」的验证件 —— **按设计做到了承诺的事，但整体 WNS 反而退步，结论是不采用、不要上板**，只留档。

**核心特性**

- `dst / srow / psrc` 三个「每行算一次」的 `y*out_w*cog`、`y*(out_w*cog)`、`psafe*in_w*cig` 改成指针累加 `dst_p += ostep` / `srow_p += ostep` / `ld_p += wstep`，只动 conv，不动 eltwise。

**实现方式**

- 在 `ROWS` 循环外先算一次 `wstep = in_w*cig`、`ostep = out_w*cog`，并置 `dst_p = out`、`srow_p = skip`、`ld_p = in + (pf_row+1)*wstep`。
- 循环里 `dst = dst_p`、`srow = srow_p`、`psrc = ld_p`（`ld_en=0` 时不解引用），行末 `dst_p += ostep; srow_p += ostep;`，仅当 `ld_en` 时 `ld_p += wstep`。
- 被去掉的这三个 32×30 乘法各要 3 个 DSP，其中一条正是 P10 的 WNS 关键路径（`mul_32ns_30s_60_1_1_U912` → `add_ln287_1_reg[62]`）。

**实测数字**

- HLS csynth：LUT 46 571→46 709（+138）、FF 30 048→30 300（+252）、**DSP 221→211（−10）**
- post-route：LUT 42 705→42 580（−125）；**CLB 8 054→8 010（91.32%→90.82%，−44）**；FF 40 029→40 187（+158）；**DSP 268→258（−10）**；CARRY8 2 243 不变
- **WNS @150.08 MHz +0.177 → +0.011（−166 ps）**；折算到板上 152.15 MHz：+0.087 → **−0.079（违例）**；WHS +0.005
- 关键路径：P10 是 `conv_layer_0/inst/mul_32ns_30s_60_1_1_U912 → add_ln287_1_reg[62]`；P11 变成 `eltwise_layer_0/inst/icmp_ln188_reg → trunc_ln197_1_reg[59]`（Concat 的 round_clamp）
- 帧耗时：**文档未给出**（P11 未烧板，无板上测量）

**为什么被否决**

- 全片最差的两条路径本来就几乎一样长（数据延迟 6.486 vs 6.474 ns），P10 里 conv 那条排第一只是恰好多占 0.17 ns 布线；把 conv 那条摘掉后 eltwise 的 Concat 立刻顶上，而它在 P11 里被摆得更差，于是整体退步。
- 账不划算：S6 单独做只有 **−44 CLB / −10 DSP**，代价是 WNS 退 166 ps（板上折算直接违例）。
- **这条发现比 S6 本身值钱**：S3（把 Concat 搬下 PS）不只是省面积，它同时把这条"接班"的瓶颈整块拿掉；等 S3 做完、eltwise 路径没了，conv 地址乘法会重新成为关键路径，**那时再上 S6 才是对的顺序**，所以 P11 源码留档不删。

**结论与遗留**

- **P11 不烧板，板子保持 P10**（已验 0/262144）。
- 附带查清：板上跑着两套驱动、走不同 Add 通路 —— `tcp-image-server`（生产，融合版驱动）走 conv 的 skip 融合 `sk_round_clamp`；`unet_selftest_p6` 走 eltwise 的 ADD 分支。推论：**两条舍入通路都不能单独删**，想省这块必须先统一驱动。（这一条后来在"统一驱动"那一轮被修正了，见 [`专题工作说明.md`](专题工作说明.md) 的「统一驱动与单文件上位机」。）
- 后续隐患：源码树里的 `conv_layer.cpp` 一度是 P11 版而出货比特流是 P10，谁不看文档重编一次就会拿到违例版。

|---|---|---|---|
| **T1** | `offset_buf` 64 → **48 位**（含 `requantize()` 形参） | 32 个 64 位寄存器 + 每 lane 一个 4:1×64 位 mux → 窄 1/4 | `\|offset\| < 2^47`（qmin ≤ 2^15、shift ≤ 31）；装载时越界直接 `CONV_BAD_CONFIG` |
| **T2** | **三处 `% 3` → 递增计数器**（首次装载行槽位 `ry%3`、`(base_row+6)%3`、`(prow+6)%3`） | `%3` 被综合成流水除法器（两个 `srem_32ns_3ns` 实例 350 LUT / 331 FF），删掉后 −701 FF | 槽位就是 `base_row mod 3`，起点只有 2（MODE_CONV3）/0，之后每行 +1、转置每两行 +1 |
| **T3** | `product`/`v` 64/65 → **63 位** | 65 位取绝对值 + 6 路 65 位 mux → 各窄 2 位 | `\|a\| ≤ 2^31`、`\|mult\| < 2^30`(Q30) ⇒ `\|product\| < 2^61`；`\|v\| < 2^62` |
| **T4** | `qmin/qmax` 内部 → **`ap_int<17>`** | 夹紧比较从 32 位降到 17 位（8 lane × 2 处） | 结果本来就只在 int16 范围内比较 |

**实现方式（机制层）**

- **T1** 只是把 `offset_buf[MAX_G][LANES]` 的存储元素与 `requantize()` 形参一起改窄、并在装载循环里加一条越界检查 —— 省的是每 lane 一个 4:1 的 64 位 mux 宽度与 `product + offset` 的加法宽度。
- **T2** 把三处「每行一次」的冷路径取模换成计数器：`slot` 在首次装载循环里 0→1→2 回绕；`sl0c` 起点 `(mode==MODE_CONV3)?2:0`，行末 `if (!transposed || (y&1)) sl0c = (sl0c==2)?0:sl0c+1;`；`pslot = (sl0+kk>=3)?(sl0+kk-3):(sl0+kk)`（`kk` 只有 1 和 3）。
- **T3** 把 `ap_int<64> product` / `ap_int<65> v` / `ap_uint<65> magnitude` / `ap_uint<65> quotient` 全部降到 63 位，省掉那条 65 位取绝对值与多路选择。
- **T4** 在函数开头把 `int qmin/qmax` 转成 `ap_int<17>` 再比较。

**实测数字**

- post-route（P10 → P13）：LUT 42 705（59.75%）→ **42 162**，−543；**CLB 8 054（91.32%）→ 7 971（90.37%）**，−83；FF 40 029→**39 149**（−880）；CARRY8 2 243→**2 173**（−70）；F7 Muxes 1 327→1 416；**DSP 268 / BRAM 138 不变**
- **WNS +0.177 → +0.177（0 变化，0 违例）**；**WHS +0.011**
- HLS csynth：46 571 → **45 327** LUT（−1 244）、30 048 → 28 572 FF
- csim 25 组 / 737 695 字 **failures = 0**
- 上板：编程前后 conv/elt 都 `ctrl=0x4` → ALL_IDLE、`state=operating`、SSH 未断
- **logit 逐字节**：112（12 544 B）/ 128（16 384 B）与 P10 完全相同（同 seed 的 sha 逐一相同）
- 帧耗时（板测中位，model 16）：**112 16.56 → 16.44 ms**、**128 20.76 → 20.58 ms**（噪声内；同日志里 model 3 的 112 档是 16.58 → 16.25）

**为什么「先判饱和再窄算」两轮都更差**

- 这里指的不是 P10 里那条「先判饱和再在 17 位上算」（那条是采纳的），而是**把 65 位的 `magnitude` 本身先判饱和再窄化到 47 位**这条路线。
- 实测两轮都输：**11-15 的 v3 = +391 LUT**、**11-16 的 v21 = +1 307 LUT**。
- 原因：**省下的窄位移器不够补两个 65 位比较器**；位数审计里的账更细 —— 收益只是 `−150 LUT / −64 CARRY8`，代价是新增高 19 位的饱和判断。
- 已在 P13 README 与「三项大改的账」里明确「**实测更差，封掉，别再试**」。

**结论与遗留**

- 耗时不变是**应该的** —— 四项只动位宽和取模，一个时钟拍都没改；资源省下来是给第 4 行槽 / 更大并行度 / 时序余量腾地方。

- 遗留：eltwise 的同一套窄化未做；`magnitude` 先判饱和路线封掉；requantize 的 32 DSP 换 CSD 移位加（LUT↑换 DSP↓）不划算；AXI 水管 12.3 k 要动接口；Concat 3.7 k 要搬 PS。

## V08 扇形外跳过（2026-11-16，量化研究）

> **这一版没有改任何代码。** 它的价值在于把"扇形外是黑的"这件事算成一笔账，从而决定了后面只砍解码器。

**一句话定位**：先不动手，把「扇形外是黑的」算清楚 —— 扇形到底占多少、每层"必须算"多少、能省几个百分点、要付什么代价。

**核心特性**

- 纯量化研究，**没有改任何代码**（`02_数据/实测4CH帧.png` + 6 个 numpy 脚本）。
- 核心方法不是阈值分割，而是**从输出端按感受野反推**每层「必须算」的像素集合：3×3 conv → 膨胀 1；2×2 pool / 2×2 转置卷积 → 2×2 块合并 / 复制。
- 结论事先钉死上限：**ap −30.4%、整帧 −26%**，且**省的钱几乎全在解码器**。

**实现方式**

- **扇形怎么判定**：不能用简单阈值（心室腔内也是黑的），改用**从画面四边连通的近黑区**（flood fill）才算「扇形外」。9 张真实 4CH 帧（worst/median/best 三档、不同病人）。
- **外侧像素怎么跳过**：不是矩形裁剪，而是**逐行区间** —— 先证明矩形没用（扇形在 y≈0.8H 处撑满整个宽度，外接矩形 = 整幅图），再把每层掩码化成「从第 a 个像素到第 b 个像素」。脚本对 30 个节点逐行检查，**每行都是单段连续区间，0 例外** —— 这是能落到硬件的前提（行循环边界只要两个数）。
- **硬件友好性论证**：`unet_ai.c` 里 `LANES=8`、`rin = w * ceil(c/8)`，一个 128 bit 字装同一个像素的 8 个通道，**列粒度是 1 像素不是 8 像素**；行槽位 `rows[3][MAX_W][MAX_G][LANES]` 本来就整行存，列号只是 RAM 地址，三行窗口不会因各行区间不同而错位。

**实测数字**

| 几何量 | 实测 |
|---|---|
| 扇形占画面 | **0.533**（外侧 0.467） |
| 顶点位置 | 画面**上方**（y ≈ −0.33H，尖角被裁掉） |
| 全张角 | 37.0°（8 张）/ 43.0°（1 张） |
| 外弧半径 | ≈1.33H（所以底角被外弧切掉） |
| 逐行有效宽度 | y=0.1H 只有 0.12W；0.5H 0.63W；0.8H 0.99W；0.98H 又收回 0.35W |

- 每层「必须算」比例（输出层 → 输入层）：node 29/26/27 = **0.533**、25 = 0.560、23 = 0.587、18 = 0.651、16 = 0.699、12 = 0.724、11 = 0.804、7 = 0.870、6 = 0.897、2 = 0.923、**1 = 0.934**。
- **ap 省多少**：理想逐行精确区间 14.940 → **10.405 ms（−30.4%）**；4 像素粒度 −26.8%；只去掉外弧 −29.8%；**只做解码器 12.451 ms（−16.7%）**。
- **整帧省多少**：21.00 → **15.59 ms（−26%，put/get 不变）** / 14.63 ms（put/get 同缩）；只做解码器 → 18.03 ms（−14.1%）。
- 按分辨率：112 占 ap 54.5% / 可省 32.8%；56 占 37.1% / 省 28.0%；28 占 8.4% / 省 24.5%。
- **编码器 vs 解码器**（关键一刀）：解码器 112 层（22,23,24,25,26,27,29）占 ap **37.6%**、可省 **44.3%**；56 层占 37.1% / 省 28.1%；28 层占 8.4% / 省 24.5%；**编码器 112 层（1,2,3）占 16.8%、只省 7.3%**。
- **端到端验掩码**：numpy 跑 30 节点图两遍（随机权重、float），A 全算、B 按掩码每层置 0，3 个 seed 扇形内 `max |diff| = 0.000e+00 PASS`（扇形外分别 2.32 / 0.98 / 0.76）；112×112 与 56×56 两种尺寸都过；另逐节点验「消费者要读的输入 ⊆ 生产者算过的输出」，无违反。
- 代价侧：CLB **7 971 / 8 820 = 90.37%**（余 849）、WNS **+0.177** / WHS +0.011、DSP 268/360；每行固定开销 `init 48` / 每行 3 476 拍（512 宽）= 1.4%，112 宽升到 ≈6%，再裁短行会到 ≈10%。

**反直觉发现**

- **为什么扇形只占 53 % 但 ap 只省 30 %**：U-Net 有 pooling 和 3×3 卷积，扇形内要算对，扇形外的像素也得算 —— 它们通过池化窗口和卷积邻域渗进来。输出层只需要 53 %，但 28×28 瓶颈层已经需要 80 %，池化和膨胀把它一路放大回输入端，**第一层还是要算 93 %**。所谓「黑区很大」在浅层根本不是黑区，网络早就把那里当成有用的上下文了。
- **为什么编码器几乎不省**：编码器 112 层占 16.8% ap，可省比例只有 **7.3%**（必须算 87~93%）。省的全在解码器（44.3%）—— 这就是「只做解码器」这一刀性价比最高的原因。
- 另外两条结构性事实：矩形裁剪零收益；张角会随机器/探头变（37° vs 43° 已出现），几何**不能写死**，得每会话测一次（但两种几何填充率都落在 0.53 附近，收益对角度不敏感）。

**结论与遗留**

- 结论：能省，但**省不到「黑区 46 %」那么多**；理论天花板 ap −30.4%，落到硬件约 −25%。
- 遗留/风险四条：① 几何不能写死；② 扇形外 logit 会变成上一帧残留的脏值，必须在收尾强制写 qmin，否则「logit ≥ thr」在扇形外出假阳性、动到掩膜面积进而动到 EF（容忍线 1 个百分点）；③ HLS 行流水线是最贵的资产（V10/V11 把 m_axi 折进流水线慢 1.5~1.6× 的教训在隔壁），建议先在 csim 量迭代延迟、别直接上板；④ 一份 HLS 服务 17 个模型 / 3 种尺寸，区间取「全宽」时必须逐位退化成今天的行为，否则 512 整网 `0/262144`、128 档逐字节不变这两条回归会一起崩。

## V09 扇形裁剪 P14 / P15（2026-11-16）

**核心特性**

*P14（解码器扇形裁剪，出货版）*

- 只做解码器 5 个 conv 节点（23 / 25 / 26 / 27 / 29），把每行的连续列区间下发给 kernel。
- 板上 112 直跑 **16.24 → 15.27 ms（−6.0%）**、ap **10 798 → 9 341 µs（−13.5%）**、扇形内 logit 与 P13 **逐字节相同（0/6681 差异）**、掩膜一位不变、128 档逐位不变。
- 整片 CLB 90.37% → **92.85%**、WNS +0.177 → **+0.036**（仍 0 违例）。
- 22（转置上采样）与 24（eltwise Concat）**不裁** —— 前者要满足「x0 为偶」、后者这一版没动 eltwise。

*P15（全流程裁剪 + 几何逐帧自标定）*

- 裁剪扩到**三层分辨率的全部 conv 节点**，几何从写死改成每帧自己标定。
- 已上板、**掩膜一位不变、两种张角都能用**，但 **15.5 ms 比 P14 的 15.3 ms 慢 1.5 %** → 这条线到此为止。

**实现方式（机制层）**

*kernel 改动*

- `conv_layer` 末尾追加 6 个 AXI-Lite 寄存器，**老偏移一个没动**（已核 `conv_layer_control_s_axi.v`：`in=0x18 out=0x24 params=0x30 skip=0x3C mode=0x48 … sk_qmax=0xB8`）：

```
ADDR_FAN_ON  0xC0   ADDR_FAN_XA0 0xC8   ADDR_FAN_XAG 0xD0
ADDR_FAN_XB0 0xD8   ADDR_FAN_XBG 0xE0   ADDR_FAN_Y0  0xE8
```

- kernel 按**绝对输出行号**求本行列区间，**Q8 斜率 + 累加器推进**（行内只有加法/移位）：`x0(ay) = fan_xa0 - (q0>>8)`、`x1(ay) = fan_xb0 + (q1>>8)`，其中 `q0 = fan_xag*ay`、`q1 = fan_xbg*ay`、`ay = fan_y0 + y - (CONV3 ? 1 : 0)`。
- 改动只有五处，全是「把常量换成区间」：滑窗初始化读列、`nsteps/total`、`wcol0/st_x0` 起点、requantize 存回 orow 的闸、MERGE 回写与预取。
- `fan_on == 0` 时 `wx0=0, wx1=out_w, lx0=0, lx1=in_w`，**逐位退化回 P13**。

*扇形寄存器怎么下发*

- 驱动 `unet_ai.c` 新增 `unet_set_fan(int)`（**默认关闭**）+ `unet_model_is_sector(idx)`（2=echo_lv / 3=echo_inter / 4=echo_seq / 16=echonet_lv）；每个被裁节点**每条带下发 6 个寄存器**，`fan_y0` = 该条带首个输出行。
- 几何用实测 4CH 的 Q10 比例（中心 0.498W、顶点上方 0.328H、半张角 tan 0.333），可用 `UNET_FAN_CX/AY/TAN` 环境变量覆盖（bring-up 不重编）。
- **末节点扇形外填 −128**，保证 `logit ≥ thr` 恒假。
- 打开点：`handle_v6c`（任意边长档）+ `job_unet_hw()`，两个入口都按 `by_size && sector_model` 判；走档位的 `job_unet(shift)`（CAMUS/F1/应变/眼底）显式关闭。

*几何余量 `FAN_PAD = 2` 是量出来的*

- 把扇形逐行真实最左/最右列与整数式（cx/base 取整 + Q8 斜率 + 每行 `>>8` 向下取整）逐行比，余量 1 时有 **9 行（112 档）/ 119 行（128 档）**包不住，2 才全部包住（右边还要 +1 是开区间）。
- 余量 1 的后果不是算错，而是末节点把扇形最右一列当区间外填了 −128 —— 上板实测 76 个像素、掩膜不变但 logit 变。

*P15 几何逐帧自标定*

1. 逐行取非零像素的最左/最右列 → `hw(y)`；
2. 只用「外弧还没切进来」的那段（`y ≤ argmax hw`）做最小二乘 → 斜率 b；
3. 再整体上移，使其**支配**所有行（含被外弧切掉的那段）→ 截距 a；
4. 每层按自己的分辨率再加 `FAN_GMARGIN` 像素。

- 标定失败（内容不足半幅 / 斜率不在 (0.03, 1] px/行）→ **整帧不裁**（合成负载就是这样自动退回全算）。实测标定：37° 帧 tan=0.469、43° 帧 tan=0.414，逐行检查 0 违例。
- P15 另留两个护栏：`<8` 像素的窄区间一律退回整行（conv 侧与哨兵侧用**同一个**判定式）；`UNET_FAN_OFF=1` 一刀关掉、`UNET_FAN_TAN` 走固定几何。

**三个坑（只有上板才暴露）**

1. **每行一个 `(xag*ay)>>8` 的 32×30 乘法把 WNS 从 +0.177 打到 −0.180**。综合成 `mul_32s_30s_32_1_1_U927`（两级级联 DSP48E2 + 一串 CARRY8）→ `empty_1185_reg`，Data Path **6.563 / 6.663 ns（18 级逻辑）**，单这条路就 4.08 ns。改成 **Q8 累加器**后这条路径消失，WNS 回到 **+0.036**。
2. **累加器必须在第一条带的头两行停两拍**。`ay = max(0, y0+y-off)` 在 `y0=0、CONV3` 时头两行的 `ay` 都是 0；无条件 `+= xag` 会让整条带**系统性偏 1 行**。csim 抓到：区间内差异仍是 0，但**区间外被写脏 72 字**。判据是「未夹紧的下一行行号 > 0」。
3. **`unet_set_fan()` 只加在 `job_unet_hw()` 里 → 板上完全不生效**。上位机实时帧走的是 `handle_v6c` 直调 `unet_run`，根本不经过 job 层。「改了但没接线」这类只有上板才暴露。

> 另记两条同类陷阱：④ 几何余量**不能随分辨率缩水**（112 的 2 px 到 56 只剩 1、28 只剩半 → 扇形边 109 个像素变；P15 第一版 109/20/5，改成每层按自己分辨率给固定余量才干净）；⑤ 板上 `make` **不能并发**（两个 `-j4` 同目录 → 整板挂死到 ARP 都不回）。

- P15 的内容内差异（更严的「输入非零区域 +1 px 逐字节相同」判据）：37° 帧 **21/6640**（±1~4，全在扇形左右边界 3 px 内）、m3 **4/6640**、m4 **0**、43° **0**、合成 0、128 档 0；**掩膜全部 0 差异**。
- GMARGIN 扫描（上板量的）：固定窄锥 + 全流程 **14.92 ms / 153 差异（欠覆盖）**；GMARGIN=2 15.28 / 109；=3 15.28 / 34；=5 **15.45 / 21**；GMARGIN=5 且 d 全 +1 15.52 / 25（无改善）—— 一条此消彼长的曲线。
- 全流程收益预测 1903 µs ap（≈16%），**实测只多拿到 ~250 µs**；三条原因：窄分辨率整数余量（56 档 `floor(5.94)=5`、28 档 `floor(2.97)=2`，余量必须 3 而不是 2）、几何余量不能随分辨率缩水、内容包络比几何扇形宽（37° 那帧 flank 拟合 tan=0.334，按内容包络最小二乘 tan=0.47）。

**上板状态**

- **P14 报告当时**：PL = `ai_sys_p14.bin`，服务端 md5 `861d93d7…`；**开机固化仍是老路径**（`/usr/local/sbin/load_ai_sys.sh` 写死 `BIN=/lib/firmware/ai_sys.bin` = P10），**重启会回到 P10** —— 这条后来被确认为地雷：P14 服务端会写 `0xC0~0xE8`，而 P10 的 conv IP 没有这些寄存器，重启后一发 112 请求就可能整板 AXI 挂死。
- **P15 收尾（2026-11-16）**：`/data/b112/new/tcp_image_server` = P15（md5 `fffeb4ccbdd720e2e73911a15f03f0ff`），`src/` 也是 P15；`/lib/firmware/ai_sys.bin` = **P14 比特流**（md5 `edcf887f…`）—— P15 是纯服务端改动，扇形寄存器 P14 的 conv IP 就有，不需要新比特流。P10 备份成 `ai_sys_p10_boot_backup.bin`。**已 `systemctl reboot` 验收**：uptime 0 min、跑的是 fffeb4cc、`fpga_manager=operating`、6 个用例 logit SHA 与重启前**逐字节一致**。
- **掩膜是否一位不变**：P14 **扇形内一位不变**；P15 **全部用例掩膜 0 差异**、两种张角都成立。

**结论**

1. 扇形裁剪**成立且可证明等价**（不是近似）：解码器 5 个节点 ap 掉 37~51%，合计 ap −13.5%，扇形内逐字节不变。
2. 但**墙钟只拿到 −6.0%**：put/get 一共 5.7 ms（占 112 帧的 37%）这一版没动，ap 省的 1.46 ms 有一半被「能重叠的窗口变小」吃掉。**下一刀必须动搬运**。
3. **方向性上限就是 −5~7%**，不是「黑区 46%」；P15 证明全流程 + 逐帧自标定**不比 P14 快**，三条原因是结构性的。
4. P15 的真正价值是**顺带修掉两个真隐患**：固定锥对 43° 帧会少算（P14 几何跑 43° 帧，扇形内容内 219 个像素 logit 变了）；开机镜像指 P10 而服务端是 P14 的 AXI 挂死地雷。
5. 代价要记住：CLB 90.37% → 92.85%（只余 631 slice），WNS 只剩 +0.036 —— 还能塞东西，但余地不大了。

## 当前版本：2026pld 集成版（2026-11-18）

> **这一版不在归档里 —— 它就在 `E:\fpga\my_project\2026pld\`，是一切归档的对照物。**

**一句话定位**：以 11-13 分享包的 `f150nv` PL 为底，只在 conv kernel 上做了**去 `%3`**和**追加 6 个扇形列区间寄存器**两件事，重综合出一块新比特流；PS 侧把 112 直跑与 P15 扇形逻辑并进 v5.27 服务端；上位机跟上 112 口径。

**为什么要以 f150nv 为底重做，而不是直接拿 P14**

- 11-13 这版服务端启动时要读 `img_proc` 的 VERSION（`0xA0000010`），而 **P7 起的比特流（含 P10/P13/P14）已经把 `img_proc` 整块删掉了** —— 读那个地址是 Synchronous External Abort。

## 一页纸：这条线到底改变了什么

**PL 侧只做了三件事**（其余全在 PS 与上位机）：

1. **把乘加之外的"表达式"压下去** —— P10 的移位常量化/窄化、P13 的位数收窄。这两刀合计 LUT 47 085 → 42 162、CLB 95.77% → 90.37%，**一毫秒都没换**，换的是余量。
2. **把 `%3` 换掉** —— P8c 在 P6pf2 血统上拿到 −8.4% LUT / 实钟 WNS 转正；在 f150nv 血统上只拿到 −2 849 LUT、零速度。**同一个改动在两个血统上收益不同，因为关键路径不同。**
3. **少算像素** —— 112 直跑（−20%，砍补边）+ 扇形裁剪（−6%，砍解码器黑区）。这一条才是真正换到墙钟的。

**被反复验证的四条"不能做"**（完整清单见 [`专题工作说明.md`](专题工作说明.md)）：

- 加并行（XU=3 / 双 IP / XU=4）：DSP 与 CLB 都到顶，实测 90.6% DSP 就破时序。
- 拆 HLS 已自动流水的段：requantize 拆三次、m_axi 折进流水线两版，全部更差。
- int8 打包／减字节：本板 BRAM 访问是**纯延迟主导**（每次约 198 ns，与位宽无关），减字节零收益。
- 把重定标搬 PS：A53 没有 32×32→64 SIMD，`a*m0+b*m1` 只能标量跑长依赖链，比 PL 慢一倍以上。
