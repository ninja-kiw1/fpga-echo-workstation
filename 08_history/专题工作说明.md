## 01 CLB 占用分解与优化方案（2026-11-15）

**要回答的问题**：P8c 的 **CLB 已经 95.77%（8 447 / 8 820）但 LUT 只有 66.7%（47 085 / 70 560）**，到底被什么计算/表达式吃掉了、怎么省。基线 P8c，心超 128² 通路。

**结论：CLB 到底被什么吃掉**

- **模块级**：`conv 62.3%`、`eltwise 20.1%`、`pp 10.4%`、`总线/互联 7.2%`（post-route 实测）。
- **表达式级**（HLS csynth 口径）：`requantize()` **11.1 k** + `sk_round_clamp()` **9.0 k** + eltwise `round_clamp()` **6.2 k** = **26.3 k**；换算 post-route **≈14.8 k = 全片 47.1 k 的 31 %**。其中**变量移位一项就占 conv 的 6.9 k**。
- **按功能重新归类**（占全片 LUT）：
  - 定点舍入/饱和通路（MERGE 4 946 + CONCAT_MERGE 3 807）**8 753 = 18.6%**
  - **AXI 适配 + 互联 + 3 个控制寄存器组 12 303 = 26.1%**（FF 12 427）—— 实打实、动不了，**比乘加点积还多**
  - 卷积乘加点积主体（STEP_ALL 去掉 requantize）≈8 150 = 17.3%（DSP 128）
  - STEP_ALL 里的 requantize ≈6 300 = 13.4%（DSP 32）
  - pp 后处理 2 160 = 4.6%；地址/下标乘法 2 405 = 5.1%；参数装载+初始化+srem 1 699 = 3.6%；纯寄存器块 1 171 = 2.5%；其它 4 157 = 8.8%
- 口诀：**吃掉 LUT 的头号来源不是乘加点积（只占 17%），是定点舍入/饱和这一类表达式（31%）**。

**关键洞察**

- **1 CLB ≈ 5.7 LUT，但边际只有 ≈11 LUT/CLB**：5.6~6.0 LUT/CLB 是该网表稳定的结构事实（p7b 6.02、p8c 5.57、p9 5.71），所以「省 1 个 CLB ≈ 省 5.7 个 LUT」；但**真要估一次改动的收益，边际换算率只有 ≈11 LUT/CLB** —— P10 实测 LUT −9.3% 只换 CLB −4.7%，因为减掉的恰是装得满的宽位算术，剩下的装箱密度反降到 5.30。
- **CLB 是布局结果，不是 LUT 的确定函数**：p9 的 LUT/FF/CARRY8 全都比 p8c 多，CLB 反而**少 134 个**；同规模重跑之间有 **±1.5% 噪声**，别拿「95.8%」当精确预算，要留 ~150 CLB 余量。
- 为什么 LUT 66.7% 却 CLB 95.8%，四条结构性原因：① **47% 的 LUT 只用了 ≤3 个输入**（LUT1 3 988 + LUT2 7 537 + LUT3 10 454 = 21 979 = 46.7%），两个独立 LUT3 不能并进一个 LUT6，只有 9 008 个 LUT（19%）用上 O5+O6 双输出；② **2 691 个 CARRY8**（conv 1 840 / elt 585 / pp 263）；③ **8 143 个 FF 前面没有 LUT**，约等于 **500 个 CLB 被半个占住**（来源是 conv 的 `raw` 4 096 + `resA` 1 024 + `acc` 512 + bias/mult/offset 3 072）；④ **998 个唯一控制集**。
- 所以：**这里没有「某个巨大浪费」可以一刀切掉**，优化必须同时降 LUT 数量和位宽，只降一个会被装箱吃掉。
- 「改写舍入公式」的三次尝试**全部更差**（+872 / +391 / +392），别再走那条路。
- **别为 XU=3 腾面积**：DSP 会到 348/360 = 96.7%，这片子实测 **90.6% 就破时序（WNS −0.090）**。

**可交付补丁**

- `R1_requantize_v12.diff`（conv，基线 `v0_base.cpp` → `v12_narrow17.cpp`）：同时改 `requantize()` 与 `sk_round_clamp()`，三件事 —— ① `magnitude >> shift` → `switch(shift)` 的常量分支；② `mask` / `half` 直接写常量，余数与半值比较从 65 位降到 **32 位**；③ `sat = (quotient >> 15) != 0` 取代 65/67 位加法、取负、两次夹紧，之后只在 **`ap_int<17>`** 上算。舍入规则一字未改。
- `R1_eltwise_round_v15.diff`（eltwise）：逻辑完全相同，只改 `round_clamp()`。
- 两份补丁都**要求入口补一条校验**：`shift` 限定 {0,23,28,29,30}，否则算错。补丁 README 明确写「本次**未跑** csim」。

**实测数字（A/B，单次 csynth ≈60 s；HLS→post-route 系数 conv 0.565、eltwise 0.554）**

- conv 基线 51 939 LUT / 32 280 FF / 221 DSP：v12（5 选 1 + 17 位窄算）**47 519 / 30 691**，ΔLUT **−4 420**；v11 单独 −2 676；v8 全常量天花板 −8 005；v10 只 shift 常量 −6 872；v9 只 qmin/qmax 常量 −1 037；v2 计数器窄化 −516。
- eltwise 基线 17 060 / 7 995 / 44 DSP：e5 **15 386 / 7 601**，ΔLUT **−1 674**；e4 −1 090；e3 天花板 −3 536。
- 合计 **−6.1 k HLS ≈ −3.4 k post-route ≈ −600 CLB / −1.1 k FF**。
- 反面：v1 舍入公式改写 **+872**、v3 先饱和再窄算 **+391**、e1 **+392**、v5 循环界外提 **+71**、v4 指针累加 **+1 010**。
- 消融上限（会改数值，只能量面积）：v6 删 requantize **−11 126**、v7 删 skip 融合 **−9 011**、e2 删 round_clamp **−6 240**、e6 删整个 `MODE_CONCAT` 分支 **−8 966**。
- 方案汇总（post-route）：S1a −3 400 LUT / −600 CLB / −1 100 FF；S2 −780 / −140 / −500；S6 **+80 LUT / +15 CLB / −44 DSP**；S1a+S2 合计 −4 180 / −740；做完 S1a+S2 CLB 预计 8 447 → ≈7 710（87%）。

## 02 算法段 ↔ 资源（2026-11-15）

**要回答的问题**：基线 P10，两件事 —— ① 每一段算法各自吃多少资源；② 只改**写法**（不改算法、不改数值）还能省多少。口径：心超全推理单帧耗时（板端 112 直跑，16.57 ms）；资源全部 post-route（`ai_sys_p10` routed DCP，`-hierarchical -depth 4`）。全片 **LUT 42 705 / CLB 8 054（91.3%）/ FF 40 029 / DSP 268 / BRAM 138**。

**结论**

- 三段 IP + 互联：`conv_layer_0` **25 138（59%）**/ 23 324 FF / 221 DSP；`eltwise_layer_0` **9 268（22%）**/ 7 390 / 41；`pp_layer_0` 4 884（11%）/ 6 273 / 6；互联 3 402（8%）。
- **`Pipeline_STEP_ALL` 的 11 834 LUT 里，只有 128 个 DSP 是乘加**，其余全是定点重定标 + 控选 + 计数器：MAC 阵列 128 DSP、`requantize()` ≈4 200 LUT / 32 DSP、其余（滑窗读口、15 个计数器、控选 mux）≈7 600。原文一句：**「算法段里最贵的不是卷积，是 requantize 那条表达式」**。
- `Pipeline_MERGE` 3 393 / 1 433 / 32，其中 skip 融合 ≈2 900；4×m_axi 2 651 / 4 006；`control_s_axi` 957 / 792；10 个 `mul_*` + 2 个 `srem` 1 247 / 400 / 23；函数级 `(inst)` 641 LUT / **6 470 FF**。
- eltwise：`Pipeline_CONCAT_MERGE` **3 723 / 791 / 16**；POOL 590；3×m_axi 2 044 / 3 072；7 个 `mul_*` **1 249 LUT / 20 DSP**。**ADD 分支在 P6-A（11-14）就删掉了**，现在只有 Concat / MaxPool。

**表述级优化：只有 T1 有效，T2/T3 是空操作**

| # | 改法 | 结果 | 判定 |
|---|---|---|---|
| **T1** | `offset_buf` 64 → **48 位**（`\|offset\| < 2^47`，装载时校验越界拒跑） | **46 571 → 45 917（−654 LUT）/ 30 048 → 29 247（−801 FF）** | ✅ **采纳**，csim 25 组 / 737 695 字 **0 差异** |
| T2 | 去掉 `pixel[XU][LANES]` 中间数组，MAC 里直接读 `wstA/wstB` | 46 709 → 46 709（**0 / 0**） | ❌ HLS 本来就把它优化掉了 |
| T3 | `(first ? bias : acc) + dot` 的 2:1 mux 改成 `if(first) acc=bias; acc+=dot;` | 46 709 → 46 709（**0 / 0**） | ❌ HLS 已经用写使能实现了 |

- T1 为什么能省（机制）：`offset_buf[MAX_G][LANES]` 是 32 个 64 位寄存器、被运行时 `sg` 索引 → 每个 lane 一个 **4:1 × 64 位 mux**（8 lane 合计约 1.5 k LUT），外加 `product + offset` 的 65 位加法；砍到 48 位后 mux 窄 1/4、加法窄 17 位、寄存器少 512 个。换算 post-route ≈ **−370 LUT / −453 FF ≈ −65 CLB**。
- 同一天还试过 4 种「看起来更省」的写法，**全部更差或更慢**：舍入公式等价替换（conv +872 / elt +392）、先饱和再窄算（+391）、循环界外提（+71）、行指针累加 S6（LUT +138 / DSP −10，**WNS +0.177 → +0.011，板上折算违例**）。
- 结论：**表述层面还剩的便宜就 T1 这一处**；真正的大块不是「表述」问题 —— requantize 4.2 k、**AXI 水管 12.3 k**（要省只能动接口/pragma）、`CONCAT_MERGE` 3.7 k（只能搬 PS）。以后做任何资源改动都要同时报对单帧耗时的影响，**只报面积不算数**。

## 03 心超提速方案（2026-11-15）

**要回答的问题**：P8c 之后还剩什么可做？「用空闲资源换并行度」这条路还能不能走？

**结论**

- **CLB 只剩 373 个 slice（4.23%，8 447 / 8 820）**。名义 LUT 还有 33.3%（23 475）没用，但 47 085 个 LUT 只装进 8 447 个 CLB（装箱密度 5.57/8），按现密度**最多再塞约 2.0~3.0 k 个 LUT**（373 × 5.57 ≈ 2 078 是「真预算」）。
- **DSP 268/360 看着剩 92 个，但这片子到 90% 以上就摆不下**：P6-A 那版 DSP 326/360（90.6%）+ LUT 84.9% → WNS **−0.090 ns、16 个违例端点**。XU=3 要 +80 DSP 到 **348/360 = 96.7%**，还没算它 +9 k LUT ⇒ **XU=3 / 双卷积 IP / XU=4 三条「加并行」的路全部关闭**。XU=4 更直接：DSP 428/360，超片。
- 时序余量 **+0.005 ns（板上实钟）**，等于 0；任何加深逻辑的改动都要先付时序代价。
- 可用面积预算 = **约 2.0~2.5 k LUT + 56 个 DSP（安全线内）+ 0 时序余量**。

**ap 13.2 ms 的构成**

| 项 | ms | 占 ap |
|---|---:|---:|
| **有用 MAC**（真实通道，128 MAC/拍） | **8.66** | **65%** |
| **MERGE**（读下一行 + 写本行，真双口 1 字/拍） | **3.42** | **26%** |

## 04 心超单帧耗时（长期口径）（2026-11-15）

**为什么需要这个专题**：心超这条通路同时存在好几个都能叫「耗时」的数 —— 服务端 `[prof] total`、`ai_us` 整网驱动、`ap`（只算 PL 计算）、`selftest` 的 512 整网、以及四段相加。历史上多次出现「拿四段相加当成绩」「拿 LUT 或单节点 µs 当成绩」的误读，所以专门定一个口径，**以后所有性能改动都报这个数**。

**最终口径**

- 一律报 **「心超功能全推理单帧耗时」**：一帧超声图像走完整网 30 个节点（含 5 个已融合的 Add）的**墙钟时间**。
- **基线 = 21.00 ms**（P10，融合通路，174 帧片段 / 31 帧被推断）。
- **不能把四段相加**：`ap 17.82 + put 4.48 + get 5.02 + zero 0.04 = 27.36 ms`，但墙钟只有 21.00 ms —— 因为 **J1 让 `get` 与 `put`/`ap` 重叠**，重叠掉约 **6.4 ms/帧**。四段相加是「总线占用时间」，不是用户等待时间。
- 不看 LUT、不看 CLB、不看「单节点 µs」，除非它是为了解释这个数。
- 稳定性：`ai` 与 `ap` 每帧稳定到 **±0.06 ms（±0.3%）**，可以当硬指标；`put`/`get` 抖动 ±20%，**别拿它们比版本**。

**各口径的数字**

| 口径 | 数值 | 说明 |
|---|---|---|
| **全推理单帧墙钟（基线）** | **21.00 ms** | 651.09 ms / 31 帧 |
| ├ `ap`（PL 计算） | **17.82 ms/帧** | |
| ├ `put`（PS→BRAM） | **4.48 ms/帧** | |
| ├ `get`（BRAM→PS） | **5.02 ms/帧** | |
| └ `zero` | 0.04 ms/帧 | |
| 四段相加 | 27.36 ms | **不要用**（J1 重叠约 6.4 ms/帧） |
| **纯净 128² 单帧（selftest）** | **23.32 ms** | ap 14.94 / put 2.77 / get 5.23 / zero 0.03，strips=57 |
| 逐节点 ap 合计 | ≈14.78 ms ≈ ap 14.94 ✓ | 最贵三个：**25（1.41 ms）、18（1.29 ms）、27（1.00 ms）** |
| 整段墙钟（174 帧） | 3915.9 ms | 其中 `track` 109.95 ms/143 帧、`quality` 132.28、`ext` 193.54 |

- **两个数为什么不一样（21.0 vs 23.3）**：服务端跑的是 112² 裁剪 + 关键帧调度，条带切法与 selftest 的 128² 整图不同，所以 `ap` 反而更高（17.82 vs 14.94），但 put/get 被 J1 藏掉一部分。**要单看 PL 计算效率用 selftest 的 23.32；要报「用户感知的单帧耗时」用 21.00。**
- **别拿什么当成绩**：别拿四段相加（27.36）；别拿 LUT / CLB / 单节点 µs；别拿旧文档的「条带 66」当现在的心超基线（那是上一代参数 67 840 B / 818 KB 的网络，本代 echonet_lv 只有 41 024 B、条带 57→43）；也别把「Σ 阶段下降」当成「用户延迟下降」—— 现场模式墙钟由信号源按 50 fps 回放决定（4.26 s），Σ 只有 1.28 s。

- **P10 上板 ap 与整帧**：ap 稳定在 **207.7 / 208.2 ms**，整帧 **293.29 / 303.56 ms**；`put` 字数从 7 364 400 降到 6 512 432（Add 不再单独跑一趟），**ap 一模一样（207 691 → 207 692）**。
- 上位机验证：`py_compile` OK；`symtable` 静态检查**未定义 0 个**；冒烟测试（真跑，宿主 Python 3.14）`tk.Tk()` → `HeartApp(...)` → `PlatformWindow(...)` → destroy，**SMOKE_OK**。

**澄清的事实：eltwise 的 ADD 分支「再省 5k」为什么不存在**

- 三条证据链：① 源码 `eltwise_layer.cpp:134` 里 `if (mode == MODE_ADD)` 直接 `return ELT_BAD_CONFIG`，注释写明「P6-A：Add 已经并进 conv 的写出级，这里不再实现 —— 省掉这条流水线的 32 个 DSP；万一还有没被吸收的 Add 走到这里，宁可报错也不要静默算错」；② 综合报告：P10 的 eltwise 只有 4 条流水线（`CONCAT_MERGE` / `POOL` / `TOP_MERGE` / `STORE_LAST`），**没有 ADD 流水线**；③ 板上实测：`UNET_NOP6A=1` 直接 `FATAL: 5 Add node(s) not fused, but this firmware has no ELT Add hardware`。

## 07 上位机 PC 侧提速（2026-11-16）

**问题**：PC 侧每帧都在白白消耗 30~40 ms（AI 模式 GUI 线程占用 35.5 ms），冷启动到出首图 811.7 ms；而网络层（板端 + 链路）一毫秒没动（AI 模式 356.97 → 355.78 ms，属于噪声）。瓶颈不在收包，而在「PC 把已经拿到的数据画到屏幕上」这一段。

**实现方式：6 类改动、14 处定点替换**，全部在 `workstation.py` 里，代码里搜 `WS_OPT_V1` 可定位每一处。

- **`imageio.make_photo`（最大的一刀）**：原路径是把裸 RGB 拼成 PPM → base64 编码 → `tk.PhotoImage(data=...)`，Tk 收到 base64 后要自己解码、再逐像素建图，512×512 一张 21.8~23.9 ms。改成 Pillow 直接建图：`ImageTk.PhotoImage(Image.frombytes("RGB", (512,512), image))`，**1.16~1.37 ms**；Pillow 不可用时自动退回原路径。一次发送要画两幅图，等于每帧省下约 45 ms 的 GUI 线程时间。
- **`App._rebuild_views`**：原来每帧无条件算 4 幅图（掩膜 / 叠加 / 热力图 / 不确定带），而界面一次只显示一幅；热力图 0.66 ms、不确定带 5.4 ms 纯属白算。新增 `_LazyViews`（dict 子类），用 `later(key, fn)` 登记造价高的视图，重写 `__missing__` / `__contains__` / `get` / `items` / `values`，只有真正被取用时才生成。
- **`App._load_logits` 的逐字节自检**：原来每帧把掩膜和叠加图本地重算一遍再和板端回传比对（3.8 ms）。结论只跟 (门限, 模型, 分辨率) 有关，改成计时、**1 秒最多复算一次**。
- **轮询自适应**：结果队列原来固定 50 ms 轮一次，有任务在途时这 50 ms 就是白等（平均多等 25 ms）。改成 `busy` 时 5 ms、空闲仍 50 ms；心超现场窗口与序列窗口同样处理（30 → 4 ms）。
- **惰性 import**：`-X importtime` 实测 `scipy.ndimage` 一个包导入 330 ms（其中 `_support_alternative_backends` 202 ms、`_array_api` 203 ms），占整个 561 ms 导入的一半以上，而它只在算 EF 几何时才用。改成 `_LazyModule` 惰性代理 + `find_contours` 惰性包装，启动路径完全不碰 scipy/skimage；`check.py` 仍显式 `import scipy`，依赖自检没被绕过。
- **三张内置图样**：`make_gradient` / `make_colorbars` / `make_checker` 原来是 512×512 逐像素 Python 循环（每张 24~34 ms）。改成 numpy 广播后 **0.2~2.6 ms**，输出逐字节相同。

**实测数字**（Windows 11 / Python 3.14.7 / Tk 9.0.4，服务端 v5.27，每档 7~8 帧取中位数、丢第 1 帧）

| 场景 | 改前 | 改后 |
| --- | ---: | ---: |
| 冷启动到出首图 | 811.7 ms | **287.5 ms**（2.82×） |
| `make_photo` 单图 | 21.8~23.9 ms | **1.16~1.37 ms** |
| `_rebuild_views` | 8.0 ms/帧 | **1.5 ms/帧** |
| 逐字节自检 | 3.5 ms/帧 | **0.1 ms/帧** |
| AI 模式整帧墙钟 | 437.4 ms | **365.9 ms**（−16.4%） |
| AI 模式 GUI 线程 | 35.5 ms | **5.8 ms**（−83.7%） |
| 基础模式整帧墙钟 | 79.5 ms | **61.9 ms**（−22.2%） |
| 基础模式 GUI 线程 | 25.7 ms | **4.2 ms**（−83.8%） |
| 基础模式帧率 | 12.6 fps | **16.2 fps**（+28.6%） |

**结果逐字节不变**，做了三次独立比对：① 同一张图同一组 flags（0x2F）分别跑两版导 md5，只有两个**耗时字符串**不同，其余全同；② 「显示」下拉 6 种图逐个比实际画出的字节，**6/6 完全一致**；③ 惰性 import 后的 `clean()` / `diameters()` / `find_contours()` 与改前逐值一致；外加 `check.py` 17/17。

**`apply_opt.py` 的作用**：`workstation.py` 是 18 个模块机械合并出来的，下次重新合并会把改动冲掉。所以优化做成**补丁脚本**：每处替换先确认锚点**唯一命中**（`count != 1` 直接 `SystemExit`），打完在文件里留 `WS_OPT_V1` 标记，**幂等** —— 重复执行会打印 `[skip] 已打过`。重新合并后跑一遍 `python apply_opt.py <新的 workstation.py>` 即可恢复。

**试过没用的（负结果）**：socket 收发缓冲 `SO_RCVBUF` 试 1 MB / 4 MB / 16 MB / 交给系统，reply 中位数 338.7 / 338.8 / 339.4 / 339.7 ms，完全没差别；`_recv_exact` 的两次拷贝 < 0.2 ms。**瓶颈在板端，别再动这里。**

## 09 板端独占引擎（2026-11-18）

> **⚠ 这一笔后来被整体撤销。** 归档记录的是"当时做了什么、为什么"，最终状态以 [`2026pld_变更记录说明.md`](2026pld_变更记录说明.md) 的 12_ 那笔为准（独占引擎已整段删除）。

**做了什么**：两件事，都在 FZ3B 实机上改好并验过。

1. **取消板端程序的开机自启**。`/etc/xdg/lxsession/LXDE/autostart` 里那行 `@/data/ws2026/board/launch.sh` 要去掉，但**这个路径被工具策略挡住**。
2. **界面在跑的时候自动屏蔽上位机指令**。板端 `tcp_image_server` 一次只服务一个客户端，PC 上位机连进来会和本机界面抢同一个引擎。

**实现方式**

- **取消自启用 LXDE 自己的规矩**：用户级 `~/.config/lxsession/LXDE/autostart` 会**整体覆盖**全局那份。新建 `/root/.config/lxsession/LXDE/autostart`，只抄进要保留的三行（`@lxpanel`、`@pcmanfm`、`@xscreensaver`），等于「全局那份里少一条我们的自启项」。恢复自启：`rm /root/.config/lxsession/LXDE/autostart`。
- **独占引擎用 iptables 一条规则**，在 `launch.sh` 起界面前插入：

```
iptables -I INPUT 1 -p tcp --dport 5060 ! -i lo \
         -m comment --comment ws2026-standalone -j REJECT --reject-with tcp-reset
```

- `REJECT` 带 `tcp-reset`，对面的上位机会**立刻**报「连接被拒绝」，而不是干等到超时。本机界面走 `127.0.0.1`，不受影响。`launch.sh` 里加 `shield_on()` / `shield_off()` + `trap 'shield_off' EXIT INT TERM`，界面退出时自动撤掉。`WS_NO_SHIELD=1` 可关掉。
- 实测：界面在跑时 PC 连 5060 → `Connection refused`；本机 `127.0.0.1:5060` 正常；SSH 22 / SMB 不受影响；关界面 / Ctrl-C 规则自动撤。**直接把 launcher 进程 kill 掉**时规则可能残留。

## 10 点击纠错 findpeaks 修复（2026-11-18）

**现象**：板端关键帧模式里，**每次分析结束**和**每次点击纠错之后**，`ws.log` 里都会出现 `TKEXC in after:`，栈是 `_poll → _on_fixed → _reanalyze → echo_ws.analyze`，最后 `ImportError: cannot import name 'find_peaks'`。用户看到的是：

- 分析结束：`_on_job` 在 `_win_len_changed → _apply_win → _reanalyze` 炸掉，后面的 `_goto / _redraw / 报告按钮使能 / 「左键补漏」提示` 全部跳过，**画面要等用户拖一下进度条才出来**。
- 点击纠错：`_on_fixed` 在 `_reanalyze()` 处炸掉，**`_goto(t)` / `_redraw()` 根本没执行**，即「纠错算完了但画面不刷新」—— 看起来就是「点完轮廓对不上」。

**根因**：板上 scipy 是 **0.19.1**：`medfilt` 有、`find_peaks` **没有**（scipy 1.1 才加）。异常被 Tk 回调吞掉（只写日志、不弹框）。PC 上没有这个问题（PC 的 scipy 是 1.x）。同批还有 `np.unpackbits(bitorder=)` 与 `np.pad` 缺 `mode` 默认值。

**实现方式**

- 按工程既有惯例（`np_compat` / `pil_compat` 那样**补在 shim、不改被测代码**），新增 `shim/scipy_compat.py`，在 `bootstrap.install()` 里注入到**真** `scipy.signal` 上（不是替换整个模块）。
- 只补缺的那个：`scipy.signal.find_peaks`；`medfilt` 有就不动。
- 语义按 scipy 实现：局部极大（平台取中点，贴数组端点的整段平台不算峰）→ `distance`（按高度降序贪心）→ `prominence`（峰两侧各走到第一个比自己高的点，取两侧较低者）。
- 本工程只用到 `find_peaks(-v, distance=…, prominence=…)` 一种调用；其余参数**收下但不参与筛选**，真用到时要补。
- `workstation.py` / `echo_ws.py` **一个字没动**。

**同批还修了连接侧的两个真故障**

- `peer closed after 0/64 bytes` 的机理是服务端 `SO_RCVTIMEO` 10 s、客户端静默超时被断；「抢不到引擎」是原来借 `app.link` 与主窗口共用同一个 socket。
- 修法是 `_fix_worker` **独占一条 `ImageLink(timeout=25)`** + `_fix_round_trip()` 断线重连并把**同一帧**重发（每帧输入自带先验，重发安全），并加 `[FIX]` 埋点与失败堆栈落日志。
- 人为在第 20 / 41 次调用注入 `peer closed`，两次都打印「重连重发」，82 帧照常跑完（2.9 s vs 干净 2.5 s）；随后 `xdotool` 真点 8 次纠错（含连点 5 次），**一次失败也没复现**。

**验证方式**

- **模块自检**：`scipy_compat._self_check()` 随 import 执行，9 条用例全过。
- **端到端对照**：同一段 142 帧录屏，板上 C 服务端自己算的逐拍结果 vs 用 shim 跑 `echo_ws.analyze(...)` —— 逐拍 (ED, ES) 都是 `(0,16) (36,51) (70,88) (106,123)`，HR 都是 **85.71**，校准后 EF 都是 **71.60**，完全一致。
- 重启后日志出现 `INFO: 已给 scipy.signal 补上 find_peaks（板上 scipy 0.19.1 没有）`，不再有 `TKEXC` / `find_peaks` 的 ImportError。
- **「纯 Python 对拍」是什么意思**：另写一份只用标准库 / 纯 Python 位运算的参考实现，拿它和 shim 的输出逐项比对，用参考实现证明 shim 语义正确。本包里的典型例子是 `np_compat` 的 `board/nptest.py`：用纯 Python 位运算实现「低位在前」的打包/解包，对 8 项全部对拍通过 → `NPTEST_OK`。

## 11 点击纠错梯度恢复（2026-11-18）

**现象**：`echo_inter` 是**整幅重画**：点一下（尤其右键「去多」）会把离点击几十像素的地方整片切掉；切出来的是**开口的凹口**（背景能从图像边界走到，`binary_fill_holes` 按定义不管），于是同一次纠错把面积拉低一截。`ws.clean()` 只负责「最大连通块 + 填洞」，补不了这种凹陷。

**根因**：不是「错位」，而是纠错模型整幅重画后留下的**开口凹陷** —— 模型删掉的区域与外界连通，填洞算法按定义不会填。所以需要一层「按图像证据判断这片到底是背景还是误删」的后处理。

**实现方式：三条判据同时满足才恢复**

1. **先验里有、模型删了** —— 只动这次改动的部分；
2. **在点击锥之外**（锥半径 **10 格 × k**，默认 k = 2.0）—— 点击附近听用户的；
3. **走过去的「过边代价」≤ 预算** —— 从保留下来的腔体做测地线，代价 `max(0, 梯度/噪声底 − 1)`，散斑级梯度免费、真边界才收费。

- 为什么不用硬阈值：先做过一版「梯度高于某分位算边界、不许穿越」，离线合成里弱带/强带一律恢复 88~98% —— 硬阈值只要漏一个像素，整片就灌进去；改成代价累计才有区分度。
- 四档锥形（界面「纠错保护」下拉，11-18 加）：

| 档 | 保护半径 | 上机实测补回被删比例 |
| --- | --- | ---: |
| 关（不恢复） | — | 0% |
| 保守（3.0 锥） | 30 格 | 28% |
| **标准（2.0 锥，默认）** | 20 格 | **44%** |
| 激进（1.5 锥） | 15 格 | 51% |

- 换档只影响**下一次**点击；状态栏写 `梯度恢复 N 像素（标准（2.0 锥））`。
- 环境变量 `WS_GRAD_RECOVER`（默认 1）、`WS_GRAD_CLICK_K`（默认 2.0）、`WS_GRAD_BUDGET`（默认 1.0）、`WS_GRAD_MAX_FRAC`（默认 0.6，左键补漏自动放宽到 0.9）。
- 「纠错影响」三档：**小（只本帧）/ 中（后续 5 帧，默认）/ 大（后续 10 帧）**，做法是把同一次点击**重放**给 3 号 `echo_inter` 几帧。

**实测数字**（2026-11-18，FZ3B + 真 `echo_inter` + `demo_a4c.y8`，现场模式 99 帧取 5 帧 × 左/右键）

- 一次点击模型**删掉**先验 **135~523 像素 = 10~37%**，同时**新增** **70~323 像素 = 5~25%**。
- 默认 k=2.0 补回 **44%**（逐用例 5~67%）。
- 保护半径 k=1.5 / 2.0 / 2.5 / 3.0 / 3.5 → 补回 **51% / 44% / 39% / 28% / 11%**。
- 预算 0.5 / 1.0 / 2.0（k=1.5 时）→ 恢复 **1115 / 1206 / 1312 像素**，**只差 18%**。
- k=4.0 时只剩 **2%** 可补 —— 说明模型的改动基本都落在**点击周围 30~35 像素内**，「远处被咬掉」的「远处」其实是 20~35 像素。
- 纠错影响（20 帧重放）：只改本帧 平均 |Δ面积| **9.6**、新增区存活 82%、与原曲线相关 0.956；逐帧梯度恢复整段 169.6、末帧 **+301**、相关 0.815；逐帧薄层回补整段 231.6、**+449**、相关掉到 **0.453**；重放点击 5 帧 35.9、末帧 −7、存活 89%、相关 0.847。

**重要结论**

- **梯度判据在真机上几乎不参与筛选，真正起作用的是「离点击多远」**：预算从 0.5 放到 2.0 只多恢复 18%，而保护半径从 3.0 收到 1.5 就把补回比例从 28% 拉到 51%。所以界面把三档做成**保护半径**，预算固定在 1.0 不动。
- 只改本帧的话，影响平均不到 10 个像素、几帧内就归零；而「逐帧把模型删的补回来」是**单向棘轮**（只加不减），整段跑会把面积永久抬高 300 像素（+25%），薄层版更把运动曲线打死（相关 0.45）。最自然的是把同一次点击重放给 3 号 `echo_inter` 几帧。
- **已知局限**：它本质上是「并集」—— 恢复后的面积可能比先验和模型都大（t=30 那帧：先验 1302、模型 1214、恢复 1426）；如果模型这次改对了（先验本身畸形），恢复会把先验的畸形带一部分回来。判据分不出「用户真想删」和「模型误删」，只能靠点击锥 + 面积比例兜，所以是一层**保险**，不是「智能纠错」。

## 12 现场模式采集卡调试（2026-11-15）

**四个独立故障**（互不相干，全部定位并修好）

1. **采集卡彻底打不开（`cannot open /dev/video0`）**
   - 定位：`ls /dev/media* | wc -l` → **256**（0..255 全在，major 252）；`dmesg | grep -c "could not get a free minor"` → 16；`rmmod uvcvideo` → `ERROR: Module uvcvideo is builtin.`；`/dev/media0` 创建于 21:57、`/dev/media255` 创建于 23:11 —— **74 分钟正好 256 次枚举，一次枚举漏一个 minor**。
   - 修法：uvcvideo 是编进内核的、卸不掉，只能**重启恢复**。
2. **每 ~17 s 掉线一次**
   - 定位：`/root/radar_usb_watch.sh`（雷达项目 2026-11-11 加的）每 `INTERVAL=12` 秒找一次雷达网卡 `0cf3:1022`，找不到就 unbind/bind 板载 `05e3:0610` HUB。HUB 一 rebind，下游采集卡就被连根拔一次；12 s 周期 + ~5 s 重扫 = **17 s**。雷达网卡没插，所以它永远找不到、永远重扫。
   - 修法：`touch /root/radar_usb_watch.skip` 暂停（脚本自己认这个文件）。代价：暂停期间雷达网卡掉线不会自动重连。
3. **1 秒左右报 `RV program not available`**
   - 定位：v5.27 的 `UNET_MODELS_COUNT 17u`（模型 0..16），而 `echo_heart_config.json` 是 `rv_model: 21, ra_model: 22`。P7 精简把「运行时 .upk 程序台」删掉后，17 以上的程序号**没有任何加载途径**。关键帧模式（mode 2）里右心失败是优雅降级；现场模式（mode 3）的「切面判断」让 `rq_rv_area()` 返回 -1 → `job_fail("RV program not available")` → **整个任务死掉**。
   - 修法：板上跑 `02_源码/gen_rv_models.py` 重编服务端 —— 索引 17..20 留空槽，**21 = cardiac_rv、22 = cardiac_ra**，`UNET_MODELS_COUNT 17 → 23`；**只增不改**（0..16 的数组一个字节没动）。板上原生 `gcc 7.5` 编。
4. **`nothing moves in the first frames`**
   - 定位：`v4l2-ctl` 抓 862 帧逐帧统计 —— **前 85 帧整帧 Y 恒等于 16**（纯黑），第 85 帧才出现画面；服务端自动裁切拿头 50 帧判「有没有在动」，自然找不到。
   - 修法：`patch_live_skipflat.py` 改 `job_echo.c` —— 还没找到画面方块时先算稀疏采样（每 8 行 / 8 列）的动态范围，整帧一个电平（max−min ≤ 8）就丢掉、不占检测名额；最多跳 600 帧（60 fps 下 10 s）。

**采集卡的真实带宽限制**

- 蓝色 USB3 口**实际跑的是 USB 2.0 480M**（挂在板载 HUB 后面，`bcdUSB 2.00`）—— 不是本次故障主因，但带宽余量只有 640×480 这一档。
- **640×480 YUYV @60 fps = 36.9 MB/s**，已贴住 USB2 的实际上限（~35 MB/s）。2026-11-17 同一张卡实测：请求 60 fps 读到 40 帧、相邻帧逐像素差 **0.000%**（冻结/重复帧）；请求 30 fps 读 40 帧、逐像素差 **99.910%**（正常活帧）。这就是「有时候识别不到 / 只进来二十来帧」的真因。
- 这张卡「刚开流」的**头两秒给的是冻结帧**：立刻读 0.000%、等 2 s 再读 34.743%、等 4 s 再读 33.627%。
- 最终参数：11-15 这轮是 `source v4l2 / 640×480 / src_fps 60 / 1200 帧`，靠服务端「跳整帧黑帧」跑通；11-17 改成**默认按 30 fps 请求**、`frames = 20 s×30 = 600`、开流后**先热身 2.2 s** 再判，服务端 `live_src.c` 在 `STREAMON` 后**丢掉 2200 ms 的帧**（实测丢 59 帧）。后来采集卡换到 USB3 直连（`speed=5000`），60 fps 才真正可用，`ws_main.py` 改成**先试 60、喂不动自动退 30**。

## A3 应用价值与 FPGA 不可替代性论证（2026-11-16）

**要回答什么**：给设计报告补强"1.1 应用场景"与"1.3 为什么用 FPGA"，并同时产出答辩口头版。核心问题不是"FPGA 好不好"，而是：**在"床旁心超 EF 测量"这个具体场景里，为什么最终落在 FPGA 而不是 GPU / CPU / NPU / 云端 / ASIC。**

**六条约束**（全文骨架）

| # | 约束 | 含义 |
| --- | --- | --- |
| ① | **外挂不改在用设备** | 医院不会为一个科研盒子改超声机固件；旁路挂视频口是唯一能进科室的形态 |
| ② | **图像不出设备** | 超声视频含患者信息，一旦上网/进云/进厂商后台，合规路径立刻变长 |
| ③ | **低功耗 6～7 W** | 整板实测 6～7 W，才可能做成被动散热外挂盒 |
| ④ | **最坏情况延迟可控** | 不是"平均快"，是能给 P99 上界：4 线程 CPU 满载下 512 档 PL 的 ap 仍是 203.3 ms 与空载相同 |
| ⑤ | **结果逐位可复现** | 全整数通路；换编译器版本、换机器最后一位不变 |
| ⑥ | **设备寿命十年而算法仍在迭代** | 引擎结构固定、权重与量化移位作数据下发（每套约 34 KB），换程序不改比特流 |

- 关键论证手法是**逐条拿掉**：拿掉①→直接做进整机；拿掉②→云端；拿掉③→GPU 模组；拿掉④→4×A77 或 NPU；拿掉⑤→浮点+厂商推理栈；拿掉⑥→ASIC；**六条全要→只有可重构硬件**。
- 自评："不争'唯一能做'，只争'在这组约束的交集里，没有第二个'。"
- 另单列**第七条、性质不同**：研发阶段资料与工具的可获得性。它不改变"哪个技术最好"的排序，但决定"你现在能不能走到那一步"，只算研发论据、不算产品论据。

**四场景 / 七种解法**

四个真实科室场景（每个都按"谁在什么房间 / 看到什么 / 没有它会怎样 / 凭什么 / **哪些还没验证**"五段写，"未验证"不许省）：**急诊分诊**（EF 41%、80% 区间 32–50%，跨过 40% 界值 → 系统不给分型结论、标"建议复核"）、**ICU / 麻醉**（每 0.25 s 刷滚动 EF，只占 PL）、**基层筛查与医联体**（质量灯 AUC 0.911；全整数确定性使上下级看到的数逐位相同）、**随访与用药监测**（5 段 × 2 种运行方式 × 20 次重复哈希唯一）。

七种解法（同板 4×A53 NEON / QCS8250 4×A77 / QCS8250 NPU / GPU 模组 / 云端 / ASIC / 本作品 FPGA）各有取舍表，**每个的优点都写足、代价也写足**。

**关键结论：为什么「FPGA 不是最快」反而是立论的前提**

1. **把不利事实放在最前面讲**。第 0 节第二段就写"按峰值算力，它不是最快的"，并给出同套 int8、输出逐字节一致的 4×A77 数据（4.61 / 101.9 ms vs 15.4 / 285.4 ms，快 2.8～3.3 倍）。答辩要点里第一条"不能说的话"就是"我们的 FPGA 算得最快"。
2. **拆开"快"的来源**：单核 A77 与 PL 是同一量级（15.5 vs 15.4 ms；325.4 vs 285.4 ms），两个负载差 21 倍而单核比值几乎不变 —— **差距来自核数，不是每核算得更快**。这一步把"输"从"架构不行"改写成"并行度不同"，而并行度这条路在本板上已被 CLB 92.9%、DSP 280/360、主频被 FSBL 钉在 152 MHz 关掉。
3. **把比较维度从"峰值"换成"约束交集"**。可说的替代句：**"我们不是最快的，但在这组约束下是唯一同时满足的 —— 而且我们主动测了更快的实现，知道差距有多大。"**

**答辩要点**

- **四条"不能说的话"**：① "我们的 FPGA 算得最快"（假）；② "可以替代医生 / 辅助诊断"（越界）；③ "用了它患者预后更好"（没测）；④ "高通的资料买不到"（太绝对）。 
- **三十秒开场**（要求背下来）：24.7 个百分点 → 2.5 倍分型带宽 → 6 瓦外挂盒子 → 15.4 ms → 18% 关键帧 → P50 29 ms（带 f150nv 口径说明）→ 掩膜/曲线/80% 区间 → 建议复核 → 点一下改并向后传播 → 逐位可复现 → 同一比特流跑 9 个心脏程序加眼底、皮肤镜。
- **高危问题与应答**（14 题）：Q1 与超声机自带 Auto EF 的区别（可核对/可修改/可外挂）；Q2 为什么不用 Jetson / GPU（没在 GPU 上实测，所以不比速度，只讲功耗散热形态与延迟确定性）；Q3 NPU 不是又快又省电吗（真买了真试了，五条通路全堵，**落点是"买得到板子，不等于拿得到把模型编译进去的那一段"**）；Q5 为什么不直接做 ASIC（算法仍在迭代，流片 18～24 个月等不起）；Q7 倍数有意义吗（128 档 1.70×、512 档 1.98×，那 34.8 ms 是占满 4 个核换来的）；Q8 精度 5.39 够临床用吗（作为"分型参考 + 建议复核"够，作为"替代医生下诊断"不够）；Q10 单帧 15.4 ms 为什么端到端还是 29 ms（**延迟 89% 是排队不是算力**）；Q13 再加并行能不能更快（到顶了，上限钉在 −5～7%，"这是这颗芯片的上限，不是这个架构的上限"）；Q14 是不是因为熟悉 FPGA 才用 FPGA（"部分是"，但论证不靠熟悉）。
- **三条退路**：① "这一条我们没有实测，只有文献数字，我把出处给您。" ② "这个方向我们试过，实测更差，报告里写了为什么。" ③ "这是这颗芯片的上限，不是架构的上限。"
- **一条总结性提醒**："答辩时最容易犯的错：把'我们做了 X'讲成'X 更好'。每讲一个技术选择，都补一句它放弃了什么 —— 评委会因此相信你其余的判断。"

**数字溯源**：给每个数字标口径，分五类 —— 实测 P15/P14、实测 f150nv、对照实测 QCS8250、文献、推算（标了算式）。三条理由写死：

1. **混口径会当场翻车**（报告正文是 f150nv 的 22.0/22.9 ms，本包性能类是 P15 的 15.4 ms，并列会出现"同一份文件两个数"），并给了 12 行同步清单 + 两条路线。
2. **中间指标会自相矛盾**（MAC 吞吐 7.5 vs 6.2 GMAC/s 与时间比 15.5 vs 15.4 ms 对不上，所以只比时间）。
3. **对照实验有前提，去掉前提整张表作废**（QCS8250 那条必须保留"同 int8、输出逐字节一致"）。
