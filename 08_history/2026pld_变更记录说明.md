## 08 右心程序修复（2026-11-18）

**现象**：关键帧模式跑完，「全心」卡片里节段室壁运动正常出结果，但右心一栏是：

```
右心：program 21 not available
右室：0 拍都没通过位置合理性检查（面积、在左室左侧、不与左室重叠），不给数值
右房：没有通过位置合理性检查的拍，不给数值
```

第二、三行是误导：`pairs` 其实是空的（一个右心对都没跑成），上位机只要 `rv_lv` 为 null 就打印「没通过位置合理性检查」。

**根因**：右心不是编进二进制的模型，而是外部程序包 `cardiac_rv.upk`（id 21）/ `cardiac_ra.upk`（id 22），靠服务端 `--programs` 加载。**这些包在这块板上一直是加载成功的**（启动日志 6 个 `OK (self-test 0/16384)`、`LOADED.txt` 齐全，gdb 读运行进程的 `g_prog[]`，21 / 22 两个指针都在）。

调不到的原因是 2026pld 为做「112 直跑」新加的入口 `job_unet_hw()`（`01_src/board/src/job.c`）选模型时用的是：

```c
unet_select_model((int)model)      /* 只认 0..16 内置；17+ 直接 return -1，且不打印任何日志 */
```

而不是老 `job_unet()` 用的 `prog_select()`（0..16 走内置、17+ 走程序包）。`job_echo.c` 里右心那一对恰好走的就是 `job_unet_hw`，所以 21 / 22 永远不可达。

**证据链（现场取证）**

| 项 | 结果 |
| --- | --- |
| 反汇编 `job_unet_hw`（板端二进制 0x20bf0） | `bl unet_select_model` —— 不是 `prog_select` |
| 反汇编 `heart_json`（0x22450） | 右心循环里 `bl job_unet_hw` |
| gdb 读运行进程 `g_prog[21]` / `[22]` | 指针非空 |
| gdb 直接调用 `prog_select(21)` | 返回 0（包本身没问题） |
| 把 HC01 任务的 rv/ra 换成同样已加载的 17/18 | 同样报 `program 17 not available` —— 整条外部程序通路断，不是某个包的问题 |
| 重启服务端后复测 | 依旧 —— 不是运行期状态漂移 |

顺带：CAMUS 那条链用的 17 / 18 号（`camus_la` / `camus_epi`）走同一入口，此前同样不可达。

**改动**：`job.c` 的 `job_unet_hw()`，**一行**：

```diff
-    if (unet_ready() == 0 || unet_select_model((int)model) != 0 || unet_set_size(h, w) != 0) {
+    if (unet_ready() == 0 || prog_select(model) != 0 || unet_set_size(h, w) != 0) {
```

- `prog_select(id)` 对 `id < 17` 内部就是 `unet_select_model(id)`，所以 **0..16 号模型逐位不变**；17+ 才走程序包。
- `unet_model_is_sector((int)model)` 是纯下标判断（只对 2/3/4/16 返回 1），21 / 22 不开扇形裁剪，符合预期。

**验证（同板、同服务端、同一关键帧任务，仅换二进制）**

| 项 | 原二进制 `6c2718c6…` | 补丁版 `83e42a30…` |
| --- | --- | --- |

| beats / ef_raw | 3 / 100 | 3 / 100 **（相同）** |
| `rh_masks` 块 | 不回 | 回了（131 B） |
| `right_heart.error` | `program 21 not available` | 无 |

**部署状态**：`/data/pld2026/tcp_image_server` = `83e42a30…`（在跑），`tcp_image_server.orig_20261118` = `6c2718c6…`（回滚用）。

## 09 右心触边判定（2026-11-18）

**需求（原话）**：

> 全心功能加入判定，如果右心室到达图像边界就不要显示，因为右心室可能显示不完全，注意图像边界以扇形边界判定

**判据怎么定的**

- **边界 = 扇形边界，不是 112 方框的边。** 板上本来就有现成的扇区位图：质量灯那条路用的 `eq_sector()`（`echo_quality.c`）把整段帧取最大值、阈值 >4、`clean_wh` 清一遍，得到「扇形内 = 1」的 112×112 位图。右心判定直接复用这张图，所以「扇形边界」和板上其他扇形逻辑是同一个定义。
- **「到达」= 右室掩膜里有像素离扇形外 ≤ border_px 像素。** 实现上对每个掩膜像素看 (2m+1)² 的邻域（m = round(border_px)，至少 1），邻域里只要有一个点落在扇形外 —— 或者落在图像外 —— 就算触边。**图像边缘一律算边界**。
- **触边 → 这一拍不给数、也不画轮廓。** 走已有的 `rh_part_t.ok`：`ok = present && side && overlap<max && !on_border`。上位机本来就是「`rv_ok_ed` 为假就不画紫线」，所以不用改绘制逻辑。
- **`border_px` 放在 HC01 的最后 8 字节**（原来固定发 0.0 的那一格）。旧客户端发 0 → 不查（与原来完全一致）；新客户端发 1。**改这个值就能调松紧，不用重编。**

**改了哪些文件**

| 侧 | 文件 | 改了什么 |
| --- | --- | --- |
| 板端 | `cardiac_ext.h` | `hc_par_t` 加 `border_px`；`rh_part_t` 加 `on_border`；`rh_check()` 多一个 `sector` 参数（NULL = 不查） |
| 板端 | `cardiac_ext.c` | `hc_parse` 读 offset 168；`rh_check` 加触边扫描，并入 `ok` |
| 板端 | `job_echo.c` | `heart_json()` 收扇区位图并传给 `rh_check`；JSON 每拍多 `rv_border_ed` / `rv_border_es`，汇总多 `n_border`；`kfe_finish` 在质量灯没算扇区时补算一次 |
| 上位机 | `jobs.py` | `heart_block()` 末 8 字节发 `border_px`（默认 1.0） |
| 上位机 | `echo_heart_config.json` | `right_heart` 里加 `"border_px": 1` |
| 上位机 | `echo_ws.py` | `heart_text()` 右室那两行改成分因说明；证据报告补一句 |

**验证**

- **主机侧单测**（不连板，直接调 `rh_check`）5 个用例：右室完全在内 `border=0 ok=1` ✅、压过左边界 `border=1 ok=0` ✅、停在 3 px `border=0 ok=1` ✅、`border_px=0` 不查 ✅、`sector=NULL` 不查 ✅。
- **板上三档联调**（同一任务只改 border_px）：

```
[1] 正常档（1.0）   pairs=2 n_border=1  rv_lv=None
[2] 必触边档（200） pairs=2 n_border=2  ← 每一拍都被标出来
[3] 关掉检查（0）   pairs=2 n_border=0  ← 一拍都不标
PASS：触边判定接上了
```

- **主通路回归**：`masks` 925 B / sha16 `61a32f79bf81f254`、`rh_masks` 131 B / sha16 `656a608b2d0265ce`，改前改后**逐位相同**；beats / ef_raw 3 / 100 不变。

**部署状态**：`/data/pld2026/tcp_image_server` = `eee046d8…`（在跑，含 08+09 两笔）。

**保留意见**

1. **只判右室，没判右房。** 要一起管的话把 `rp[2].on_border` 也并进 `ra_ok` 即可（一行）。
2. **`border_px = 1` 是拍的，不是量出来的。** 112 网格上 1 px ≈ 1% 视野宽度。
3. 验证用的是合成图，**不是**真四腔上的 RV/LV 数值。
4. **`eq_sector` 的扇区是数据驱动的**：它把整段帧的亮区都算进来。如果录屏里扇形外有亮的东西（机器 UI、标注、彩标尺），扇区会被判大，触边判定就会偏松。

**当前代码在哪**：`2026pld\01_src\board\src\` 与 `2026pld\07_ui\`（两份 `01_src/ui` / `07_ui` 内容一致）

## 10 预览按输入分辨率（2026-11-18）

> ⚠ 这一笔做的是**多文件血统**（`heartview.py`）。同一天晚些时候上位机整体换成**单文件版**，这一笔的成果被 12_（预览原分辨率与像素标尺）在单文件版上重做了一遍。所以本目录的价值是"当时的做法与踩到的坑"，不是现役代码。

**需求（原话）**：「上位机视频预览分辨率改成输入分辨率」。定的是：**按原始视频帧尺寸 1:1**，装不下屏幕时**保底 448、超高自动缩**。

**行为**

| 输入 | 屏幕 | 预览 |
| --- | --- | --- |
| 112×112（EchoNet 序列） | 任意 | 448×448（和以前完全一样） |
| 640×480（采集卡/录屏） | 2560×1440 | 640×480（1:1） |
| 800×600 | 1920×1080 | 800×600（1:1） |
| 800×600 | 1366×768 | 584×438（等比缩到装得下） |
| 1920×1080 | 2560×1440 | 1920×1080（1:1） |
| 3840×2160 | 2560×1440 | 1973×1110（等比缩） |

规则一句话：`k = max(1, 448/短边)`（不缩水），再跟 `屏幕可用高/宽` 取小。

**关键做法**

- `read_video()` 额外带回**原生分辨率的整段灰度帧**（抽稀因子 `dec`）。
- 新增 `compose_preview()` + `_inner()`：**有原生帧就按原始分辨率画整幅**，把 112 掩膜放大到扇区方块再贴回 `(x0, y0)`；**轮廓在缩放之后才画**，所以预览被缩小时线也不会糊。
- **点击坐标仍然按 448 视图坐标存**，只有画和取的时候乘除 `self.s = 预览宽/448` —— 这样纠错链路零改动。

**验证**：合成单测 5 组、尺寸策略单测 6 档全过。**没验到的**：这个环境里没有 tkinter 也没有显示，**界面本身没跑起来过**。

**注意**：原生帧要留在内存里，上限 `NATIVE_MAX_BYTES = 384 MB`，超了按整数步长抽稀。

**目录**：`05_2026pld变更记录\10_预览按输入分辨率_20261118\`（只有 `说明.md` 一个文件）

## 12 板端主页提速与文字偏移（2026-11-18 报告 / 2026-11-19 追加）

> **这是这批改动里体量最大的一笔**：92 个文件（含 `01_板端运行时\` 完整可部署副本 + 27 张验证截图）。它同时修了三件事，第三件（删独占引擎）是 11-19 追加的。

**一句话结论**

| 现象 | 根因 | 结果 |
| --- | --- | --- |
| 拖动时间轴延迟大 | 每挪一格都把整帧从头算一遍，且拖动事件一个个排队渲染 | **单个事件 64 ms → 0.18 ms**；60 个连续事件 **3.8 s → 0.16 s** |
| 改分辨率 / 拖边框时文字显示区域偏移、被截断、被挤成窄列 | 兼容层给 GtkBox 的**每个**子控件都传了 `expand=True`，多余空间被平均分给所有控件 | 三个左排标签的 x 从 **101 / 329 / 548 → 0 / 27 / 45**，且窗口拉宽 400 px 后**纹丝不动** |
| 界面跑起来就封 5060，上位机连不进来 | `launch.sh` 里的「独占引擎」用 iptables REJECT 非 lo 的 5060 | 整段删除；宿主机连 **False → True**，按协议真握手 **PC_CAPS_OK** |

**一、文字偏移：根因与证据**

- 根因：`shim/tkinter/_gtkbase.py` 的 `_place_pack()` 里写死了 `self._host.pack_start(g, True, True, 0)` —— **expand=True, fill=True，每个子控件都是**。tk 的 `pack()` 里 `expand` 默认是 **False**。GTK 的 GtkBox 会把多余空间**平均分给所有 expand 的子控件**，于是 `pack(side="left")` 的标签不再贴边，而是各自居中在自己那一份空间里 —— 空间份额随容器宽度变化，所以一改分辨率 / 一拖窗口边框，文字就整体漂走。
- 板上实测（900 px 宽横条，三个 `pack(side="left")` 标签 + 一个 `pack(side="right")`）：

| 控件 | tk 期望 | 改前 | 改后 |
| --- | --- | --- | --- |
| 左 1（"AAA"） | x=0 | **x=101** | x=0 |
| 左 2（"BB"） | x=27 | **x=329** | x=27 |
| 左 3（"C"） | x=45 | **x=548** | x=45 |
| 右（"RIGHT"） | x=859 | x=758 | x=859 |

- 窗口拉宽 400 px 后：改前 151 / 479 / 798（**继续漂**），改后 0 / 27 / 45（不动）。主窗口顶栏 logo 的 x 从 69 → **16**，标题从 213 → **54**。
- 改法：

```python
# 只有 pack(expand=True) 的控件才吃多余空间；fill 沿排布轴传给 GtkBox，
# 跨轴那一维仍由 halign / valign 负责（_apply_pack 里原本就有）。
along = (fill in ("x", "both")) if axis == "h" else (fill in ("y", "both"))
self._host.pack_start(g, bool(item["expand"]), along, 0)
```

- **这一改影响所有窗口**。已逐一看过截图：主界面（1920×1054 与 1400×860 两档）、平台扩展页、大图精查、序列跟踪，都比改前更贴近 tk 的排法。
- 顺带修了一处**真的被裁**的文字：事件时间线那句「分析时分开标出：蓝 = 分割的关键帧（约 18%），灰 = 块匹配跟踪帧」在 392 px 宽的画布上要占 366 px、起点 x=56，右端溢出 30 px。改成「蓝 = 关键帧（约 18%）　灰 = 跟踪帧」。

**二、拖动时间轴：耗时分解与改法**

改前（板上实测，每挪一格）：

| 段 | 耗时 |
| --- | --- |
| `contour_rgb`（底图放大 + 画轮廓） | **44.1 ms** |
| ↳ 其中 `np.repeat` 复制成 3 通道 | 21.9 ms |
| ↳ 其中 `_edge` 求轮廓边界 | 9.6 ms |
| ↳ 其中 PIL 双线性放大 112→448 | 9.6 ms |
| 视频画布整张重合成 | 15.0 ms |
| 曲线画布 / 时间线画布重画（光标） | 7.0 + 14.2 ms |
| GTK 贴图 | 5.3 ms |
| **合计** | **≈ 90 ms/格（11 帧/秒）** |

而且拖动事件是**同步**处理的：手指划过 60 格要 3.8 s 才能追上。

四处改动：

1. **`echo_ws.contour_rgb`：去掉 `np.repeat`**（21.9 → ~1 ms）。`np.repeat(big[..., None], 3, -1)` 在 numpy 1.13 / A53 上要 21.9 ms；换成 `np.empty` + 三次整块赋值。
2. **`echo_ws._edge`：在 112 网格上判边界，再按 4×4 填回 448**（9.6 → 2.9 ms）。放大倍数正好是 4，一个格子的 4×4 块内部邻居必然同值、四条外沿各自只取决于对应方向邻居格的值 —— 结果**逐像素相同**。`scale == 1` 时走原式。
3. **`_canvas._render`：单图快路 + 底图缓存**（15.0 → 0.14 ms；光标 32.1 → 4.5 ms）。画布上只有"一张铺满的图"时直接把图自己的 pixbuf 交给 `Gtk.Image`；时间线画布按「不含 `tags="cursor"` 的图元指纹」缓存底图。（第一版漏了一种情形：`delete("cursor")` 那一瞬间画布里**没有**光标图元，指纹没算 → 每次删光标都把底图缓存清掉，白干两遍。）
4. **`EchoView._goto`：逐帧缓存 + 拖动合并事件**。一帧画好的 `PhotoImage` 按帧号缓存（LRU 32 帧 ≈ 38 MB），掩膜/点击/全心结果一变就整批作废；拖动时 `defer=True`，空闲时**只画最后那一帧**；ED/ES 角标从 canvas 文字图元改成直接画进图里（原本会让画布凑不成"单图"、快路失效）。

改后：

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 单个拖动事件（事件本身） | 64 ms | **0.18 ms** |
| 60 个连续事件总墙钟 | 3.8 s | **0.16 s**（真正只画 1 帧） |
| 一帧从没看过的画面 | 90.5 ms | **34.6 ms** |
| 已经看过的画面 | 90.5 ms | **10–15 ms** |
| `contour_rgb` | 44.1 ms | **17.9 ms** |
| `_edge` | 9.6 ms | **2.9 ms** |
| 视频画布重合成 | 15.0 ms | **0.14 ms** |
| 曲线 / 时间线重画 | 7.0 / 14.2 ms | **2.2 / 2.3 ms** |
| 光标重画 | 32.1 ms | **4.5 ms** |

改后一帧的完整账：画帧 21.4 + 交给画布 0.2 + 光标/曲线 0.5 + 布局刷新 12.3 ≈ **34.6 ms**。

**二·五、取消「独占引擎」（2026-11-19 追加）**

## 14 自动定标尺（2026-11-19）

**需求**：「上位机加入自动定标尺功能，删除标尺定标入口」。定下两点：**载入时自动完成、在上位机做**；**自动读不到深度刻度就只报像素**（不弹框、不猜默认深度）。

**关键发现：原来的自动读刻度，在真机上根本读不出来**

- `depth_ticks()` 早就有（原来只当手动弹框的预填），但它只认**黄色**刻度像素（`r-b>25 & g-b>25 & r>90`）。拿本机 `ES000108_4CH_1.avi` 实测：这段录屏的深度刻度是**灰白色**的（扇区左边缘一排小斜杠，旁边写 5 / 10 / 15）—— 黄色判据一个都不命中；返回 `None`，而且**耗时 13.5 秒**（穷举所有候选两两连线，候选最多 400 个）。
- 也就是说：如果只是"把入口删了、改成自动调 `depth_ticks`"，用户这段视频会永远显示"只报像素"。所以这次把识别本身重做了。

**识别改造（`depth_ticks`）**

| 项 | 改前 | 改后 |
|---|---|---|
| 颜色模型 | 只认黄色刻度 | 黄色 **或** 「黑底上的灰/白细线」（`55<亮度<215`、低饱和、11×11 邻域够黑） |
| 候选筛选 | 面积 ≤ 25 | 面积 3~45、长边 4~16、短边 ≤ 5（细长条），再均匀抽稀到 ≤ 200 个 |
| 找线 | 穷举两两连线，取共线最多 | 同左（抽稀后快 100 倍） |
| 单位核对 | 必须有"每 5 cm 长刻度" | **只有"少数长刻度"的机型才核对** |
| 返回值 | 两枚长刻度 + 固定 5 cm | 首尾两枚刻度 + 它们之间的实际厘米数（基线更长、更准） |
| 耗时 | 13.5 s | **0.05~0.13 s** |

**实测（本机 8 段录屏 × 每段 3 帧）**

| 录屏 | 1 cm = ? 像素 | 刻度数 | 跨距 | 三帧一致性 |
|---|---|---|---|---|
| ES0001 _4CH_1 | 31.96 | 12 | 12 cm | Δ=0 |
| ES000108_4CH_1 | 27.73 | 14 | 14 cm | Δ=0 |
| ES0002 _4CH_1 | 21.88 | 16 | 18 cm | Δ=0 |
| ES0003 _4CH_1 | 25.96（首帧读不到 → 第 15 帧读到） | 13 | 15 cm | Δ=0 |
| 0X100…（4 段） | 30.00 | 15 | 14 cm | Δ=0 |

**8 / 8 命中，8 / 8 多帧完全一致。** ES000108 的 27.73 与旧文档里手点的 27.88 差 0.5%。ES0003 首帧刻度被遮挡 → 所以自动定标现在会**依次试第 0 / 15 / 30 帧**。

**界面改动**

- 删除「标尺定标…」按钮，视频卡片标题行右边改成**只读**的标尺读数：`标尺 1.24 mm/像素（自动）` / `自动定标中 …` / `未读到深度刻度：只报像素` / `本视频没有深度标尺：只报像素`。
- 删除 `CalibDialog`（手动点两点填厘米的弹框）与 `Ev_`。

## 16 输出文字边框伸缩（2026-11-19）

**现象**：点「▶ 开始分析」，等板子跑完、结果文字一出来，窗口（和各栏卡片的边框）就左右抽动一下；结果越全、抽动越多。

**根因**：主窗口**没有设定尺寸**（只有 `root.geometry("+x+0")` 摆位置），Tk 的窗口大小 = 内容请求尺寸。结果区那几个标签（EF、心率、质量灯、LVEF 分档、RV/LV 面积比、分析片段、自动定标说明……）取值是**变长的文字**：`"—"` → `"62%"` → `"LVEF 分档：中度减低（30–40%）（ESC 2021）"`。每换一次文字，标签的**请求宽度**就变一次 → 整栏请求宽度变 → 窗口请求宽度变 → 边框左右跳。

实测（真 tkinter、把 `HeartApp` 真建起来、逐个 StringVar 设成长文案后量 `winfo_reqwidth`）：

| 变量 | 位置 | 长文案时窗口宽度 |
|---|---|---|
| `var_ef` | 结果区 EF（30 pt 大字） | 1461 → **4546**（+3085） |
| `var_ra` / `var_rv` | 全心卡片 | +1476 / +1440 |
| `var_hr` / `var_light` | 结果区 | +1455 / +1457 |
| `var_win` | 分析片段 | +858 |
| `var_band` | LVEF 分档 | +705 |
| `var_scale` | 视频卡片标题行 | +664 |
| `var_mef` / `var_edv` / `var_esv` | 快照测量卡片 | +2826 / +1403 / +1403 |

**改了什么**：给这 **11 个**取值会变长变短的标签加**固定字符宽度** `width=N` —— Tk 里一旦写了 `width`，标签的请求宽度就只由 `N` 决定，跟文字内容无关。

| `var_ef` | FONT_EF 30b | 5 | 136 px | `100%`（112 px） |
| `var_hr` | FONT_HR 15b | 8 | 110 px | `120 次/分`（91 px） |

| `var_win` | FONT 10 | 20 | 166 px | `放好后 12–40 帧（1.2 s）`（154 px） |
| `var_scale` | FONT_SMALL 9 | 24 | 174 px | `本视频没有深度标尺：只报像素`（168 px） |

做法和这个文件里原来的几处一致：`var_ft`（`width=50`）、`var_xy`（`width=56`）、`var_name`（`width=44`）、状态栏（`width=1`）都是同一个理由。

## 17 容积曲线拖动提速（2026-11-19）

> **这是归档里最新的一笔**，也是唯一一笔只改板端 `app/workstation.py`、完全没碰 PC 侧的改动。

**现象与根因**

| 现象 | 根因 | 结果（板上真数据） |
| --- | --- | --- |
| 拖容积曲线，"跟手，但每换一帧都要顿一下" | 每换一帧都要在 448×448 上**重新放大底图 + 重算轮廓边界 + 用布尔掩膜整幅上色**（22.7 ms），贴图后还要**重画两条光标**（12.3 ms）；整帧照片缓存只有 32 帧，扫一遍全不命中 | 一帧 **40.1 → 4.1 ms**（9.8×）；从没看过的帧 **40.1 → 21.0 ms**；画面**逐字节不变** |

**改前到底慢在哪（板上逐段实测，ms/帧）**

| 段 | 改前 | 说明 |
| --- | --- | --- |
| `contour_rgb` 合成一帧 | **22.7** | |
| ↳ PIL 双线性放大 112→448 | 9.7 | 每帧都重做，帧本身是不变的 |
| ↳ `_edge` 求轮廓边界 | 3.0 | 掩膜不变，每帧都重算 |
| ↳ `rgb[布尔掩膜] = 颜色` | 2.4 / 每条 | 要在 20 万个位置上过一遍 |
| ↳ `Image.fromarray` + `ImageTk.PhotoImage` | 1.2 + 2.7 | |
| 贴图 + 一次 flush | **12.3** | 其中**事件时间线那条光标就占 7~8** |
| 合计 | **≈ 40**（25 帧/秒） | 与 `verify_real.py` 量的 40.1 ms 对得上 |

> 11-18 那轮已经把 `np.repeat`、`_edge` 的放大、`_canvas` 的整张重合成、拖动事件合并且照片缓存都做过了，所以这一次不是"重做一遍"，而是把**剩下的大头**——每帧重复的计算和第二条光标——去掉。

**四处改动**

1. **放大底图 + 轮廓下标按帧缓存**（`_vprep_get` / `_vprep_build`）。底图（112→448 双线性）与每条轮廓的**扁平下标**都只跟帧和掩膜有关。现在按帧存 `(放大后的 448×448 灰度底图, [(该轮廓的扁平下标数组, 颜色), …])`。换一帧时只做三通道填充 + `rgb.reshape(-1,3)[下标] = 颜色`（只碰轮廓上那约 1000 个像素，0.13 ms）。按 `WS_V_PREP`（默认 200 帧）LRU。
2. **后台预取**（`_vprefetch`）。分析一结束就起一个后台线程，从**当前帧往两边扩**把底图与下标先算好（只碰 numpy/PIL，不碰 Tk）。150 帧 ≈ 2 s 的一个核。掩膜 / 点击一变（`_vclear`）就作废，正在跑的线程看到代数 `_vgen` 变了会自己退出。
3. **整帧照片缓存放宽 + 空闲预热**（`_V_CACHE_MAX` 32 → 64，`_vwarm_photos`）。照片缓存命中时换一帧只要 **4 ms**（底图命中但照片没命中要 17 ms），所以分析完再把最近一圈整帧照片在主线程**一小口一小口**补进缓存（1 帧/25 ms，正在出图或正在拖时自动让路）。
4. **拖动中只动一条光标**（`_draw_cursor(only="cv")` + `_vsettle_later`）。拖动时只重画**容积曲线**那条竖线；事件时间线那条等手停下来 **160 ms** 再补。省掉每帧 7~8 ms。

**改后（同一套脚本、同一段真视频、同一台板子）**

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 拖曲线换一帧（已预热） | **40.13 ms**（25 帧/秒） | **4.10 ms**（≈ 240 帧/秒） |
| 拖到没预热过的帧（照片缓存全清） | 39.56 ms | **20.99 ms** |
| 预热耗时（60 帧） | — | 2.13 s（后台 + 空闲分块，不挡操作） |
| 分析结果 | EF 50.14 % | EF 50.14 %（不变） |

合成数据 150 帧：第一次拖动 39.61 → **4.01 ms**；拖到没预热的远端 38.91 → **17.80 ms**；再拖回来 16.80 → **3.97 ms**。

**画面逐字节对拍**：新路径（底图 + 下标）与老路径（`echo_ws.contour_rgb` + `add_contour`）在 5 帧（含右室 / 右房双轮廓的两帧）上 `np.array_equal` **全部一致，差异像素 0**。所以板上看到的轮廓、底图与改前完全相同，快出来的只是"怎么算出来"。
