## 1. 为什么要这么绕：三条硬约束

1. **PL 读不到 DDR**：FZ3B 出厂 PS 配置**没有使能任何 PL→PS 从口**（实测 HPC0/HP0/HP1/ACP
   全悬空）。PLD 原设计里 UNet IP 是 AXI-MM 主设备、挂在 `ps_HP0/HP1` 上读写 DDR ——
   **这套在我们板上跑不了**。
2. **片上 BRAM 装不下整网张量**：ZU3EG 全片 BRAM 216×36Kb ≈ **0.97 MB**，现有 PL 已用 64 块；
   而 512×512 下光一层 8 通道张量就是 512×512×8×2B = **4 MB**。
3. **不能动 Linux/boot.bin**（用户要求）；自制 boot.bin 那条路之前把板子搞砖过。

→ 只剩一条路：**PS 当"搬运工"，PL 当"计算器"**。张量放 **DDR**（PS 能访问），
PL 里只放**层引擎**（行缓存 + 权重缓存），每层由 PS 把输入推进去、把输出拉回来。

## 2. 数据流

```
PC ──TCP──► PS(Linux)
             │  ① 收图（512×512 RGB）
             │  ② 预处理：推给 PL 的 img_proc_axil（现有 6 模式，**不改**）
             │  ③ 预处理结果缓存进 DDR（张量区）
             │  ④ 逐层跑 U-Net：对 30 个节点
             │        ┌──── 从 DDR 取该层输入张量
             │        ├──── 分块推给 PL 的「层引擎」(conv / eltwise)
             │        ├──── 拉回该层输出张量
             │        └──── 写回 DDR
             │  ⑤ 后处理：logit ≥ -3 → 血管掩膜；算血管占比等统计
             └──TCP──► PC（掩膜图 / 掩膜叠加图 / 统计，按上位机选择）
```

**张量生命周期**：PS 端调度器按 `network.txt` 的层顺序分配/复用 DDR 缓冲区
（PLD 的 README 明确说"可以在最后一个消费者用完某个张量后回收它的缓冲区"）。

## 3. 层表（U-Net 真实结构，来自 `unet_network/vectors/network.txt`）

三级 U-Net，512 → 256 → 128 → 256 → 512；通道 **8 / 16 / 32**；
30 个节点 = 20 CONV（17 个 3×3、2 个 2×2 转置、1 个 1×1）+ 5 Add + 2 Concat + 2 MaxPool。

| 层级 | 分辨率 | 通道 | 该层张量大小（int16 容器，通道补到 8） |
| --- | --- | --- | --- |
| L0 | 512×512 | 8 | **4 MB** |
| L1 | 256×256 | 16 | 2 MB |
| L2 | 128×128 | 32 | 1 MB |
| 输入 | 512×512 | 3→8 | 4 MB |
| 输出 | 512×512 | 1→8 | 4 MB（可只留 1 通道 0.25 MB） |

**激活格式**：NHWC，每值 int16 容器（INT8 层也用 int16），通道补齐到 8 的倍数，
一个 **128bit 字 = 一个像素的 8 个通道**，lane i 在 bit 16i~16i+15。
**权重格式**：64bit 字；`params/<name>.bin`。

## 4. 关键决策：**算子代码一行不改**，把 IP 的内存口从 DDR 挪到片上 BRAM

PLD 的 `conv_layer` / `eltwise_layer` 已经过 C 仿真 + RTL 协同仿真 + **整网上板**验证，
**不重写、不改接口**。它们的 `m_axi_gmem*` 是**主设备**，指向哪里由**运行时传的基址**决定：

| | PLD 原版 | 我们这版 |
| --- | --- | --- |
| IP 源码 | — | **完全不变**（重新用 2025.2.1 从同一份源码导出 IP） |
| `m_axi` 指向 | `ps_HP0/HP1` → DDR | **片上 BRAM**（AXI BRAM Controller + 互联） |
| 控制口 | AXI-Lite | 同一套（走我们的 **PS→PL 主口，已验证可用**） |
| 张量存放 | DDR（IP 直接读写） | **DDR 为主**（PS 管）；每层按**条带**搬进 BRAM 给 IP 算，算完搬回 |

### 4.1 为什么要按条带

BRAM 只有 ~0.68 MB 可用，而 L0 一层张量就是 4 MB —— 一次性放不下。
所以一次只喂「**条带 + 上下 halo**」给 IP：IP 在喂进去的块边界会**按图像边界零填充**，
于是**只保留中间有效行、丢掉 halo 行的输出**即可得到正确结果。
IP 的 `in`/`out` 指针与 `in_h`/`in_w` 都是**运行时可传的参数**，
所以按条带调用**不需要改一行代码**。

### 4.2 为什么这条路对

- ✅ 复用**已验证**的算子（不用重新证明算得对）；
- ✅ 不依赖 PL→PS（IP 只访问片上 BRAM，控制口走 PS→PL 主口）；
- ✅ 张量主体在 DDR，**BRAM 只当"一层条带的暂存"**；
- ⚠ 代价：PS 要在 DDR↔BRAM 之间搬数据，**搬运是主要耗时**（见 §6）。

### 5.1 ⛔ 上板实测暴露的真问题：位宽转换器丢写数据

```
conv IP 控制寄存器: CTRL 读出 0x00000004 (ap_idle=1 → IP 在响应, 读是好的)
                    9 个配置寄存器(mode/cin/cout/in_h/in_w/relu/shift/qmin/qmax) 写一个都没落
PS→BRAM(32→128):    64 个 32bit 写，只有 16 字节对齐的 16 个落进去，其余全 0
```

**根因**：128 位的 IP 数据主口和 32 位的 PS 主口挂在**同一个互联**上 → Vivado 把互联内部
通路撑到 128 位 → 每条 32 位路径都被插了 `auto_us` + `auto_ds`。
**这些位宽转换器在这个工具链/器件上：只让 16 字节对齐地址的写数据通过**
（和 §10 修 img_proc 时那个 bug 同一类，只是这次连**加宽方向**也一样有）。

### 5.2 修法（下一步做，保持"不改算子代码"）

**让每条路径的位宽自洽，彻底不出现转换器**：

1. BRAM 用 **True Dual Port、A 口 128 位 / B 口 32 位**（同一块存储、两个独立端口）；
2. **两个 `axi_bram_ctrl`**：128 位那个（`SINGLE_PORT_BRAM=1`）接 A 口跑 IP；
   32 位那个接 B 口给 PS —— 这样 PS(32)↔B(32)、IP(128)↔A(128)，**两边都不转换**；
3. **AI 控制通路单独一个"只有 32 位主从"的互联**（PS 32 → conv/elt 的 AXI4-Lite 32），
   不和 128 位主口混 —— 或者直接挂到现有那条已验证的 32 位 FPD 通路上。

**PS 端驱动的顺序**（照抄 PLD 板端程序的做法，见 `embedded/`）：
1. 把该层的权重/Bias/M/offset 按 `params/<name>.bin` 的顺序搬进 BRAM(B 口)；
2. 搬入输入激活（条带 + halo）；
3. 写 IP 的 AXI-Lite 寄存器（指针、mode、cin/cout、h/w、relu、shift、qmin/qmax）并启动；
4. 轮询完成；
5. 把输出激活搬回 DDR（丢掉 halo 行）。

### 5.3 修法已实现（第二轮 BD），地址有变

**结构**（每条路径位宽自洽，生成日志确认 32 位通路上**只有 `auto_pc`、没有 `auto_ds`**）：

```
PS(32) → sc_axil(1SI:4MI, 32位)
    M00 → pc_axil → img_proc_axil_0     (不动)
    M01 → conv_layer_0/s_axi_control
    M02 → eltwise_layer_0/s_axi_control
    M03 → bram32_ctrl/S_AXI             (PS 读写 BRAM)
6 个 IP 主口 → ai_ip_ic(6SI:1MI, 128位) → bram_ctrl/S_AXI   (128位)
BRAM: bram_gen True Dual Port — A 口 128 位接 bram_ctrl, B 口 32 位接 bram32_ctrl
```

| 从机 | **新地址** |
| --- | --- |
| conv_layer_0 控制 | `0xA001_0000` |
| eltwise_layer_0 控制 | `0xA002_0000` |
| BRAM（32/128 两口） | `0xA010_0000`（128K） |
| img_proc_axil | `0xA000_0000`（未动） |

时序 WNS +0.058 / WHS +0.014；比特流 bin md5 `36af5796…`。

### 5.5 P3 单层测试结果（2026-10-01）—— **控制通路修好了 ✅，数据通路还没通 ❌**

**做成了（本轮最大进展）**：位宽修复让**控制通路通了** ——
往 conv IP 的 13 个配置寄存器写值**全部写入成功并读回正确**
（`mode=0 cin=3 cout=8 in_h=7 in_w=9 relu=1 shift=27`），
`ap_start` 启动、`ap_done` 置位、`ap_return=0`（CONV_OK）—— **IP 真的跑完了**。
图像通路回归也照旧 4/4 PASS（没伤原功能）。

**还没通**：**PS 往 BRAM 的写完全不落地**。证据：

```
写 0xDEADBEEF@0x000 / 0x12345678@0x400 / 0xCAFEBABE@0x800  ->  读回全是 0
全片 128KB 扫描这三个标记 -> 一个都找不到
P3 输出比对 -> mismatch 1006/1008 (IP 拿到的输入/权重都是 0, 所以输出也是垃圾)
```

读是好的（有从机、不挂、返回快），**只有写不落**。

**怀疑点**：BRAM 用了**非对称双口**（A 口 128 位给 IP / B 口 32 位给 PS），两个
`axi_bram_ctrl` 都设成 `SINGLE_PORT_BRAM=1`。`blk_mem_gen` 里 `Write_Depth_B` 没写出来（是计算值），
而且**单口模式的控制器可能只认 Single_Port_RAM，不认 True_Dual_Port_RAM 的端口** → 写被丢。

**下一步**：换成更标准的组合再验，候选——
1. 两个控制器都 `SINGLE_PORT_BRAM=0`（双口）+ 把 BRAM 两口的宽度都设成与控制器一致；
2. 或者干脆**放弃非对称双口**：BRAM 只做 32 位（一个 32 位控制器给 PS），
   IP 侧那 128 位用一个**显式配好的** dwidth converter（PLD 原设计里 64→128 那个 upsizer 是能工作的）；
3. 再不行就走"BRAM 全 128 位 + PS 侧显式转换"那条，但注意 32↔128 的转换器是已知会丢写数据的。

判据不变：先把标记值写进 BRAM 再读回来对上，然后才谈 P3 的逐字节比对。

### 5.6 数据通路的两次尝试都撞在同一个矛盾上（2026-10-01 晚）

**根本矛盾**：PS 是 32 位、IP 的数据主口是 128 位。只要这两者在**同一个互联**里，
互联内部就被撑到 128 位，32 位那条就被插 `auto_us`/`auto_ds` —— **而这类位宽转换器在本工具链/器件上
只让 16 字节对齐地址的写数据通过**（§5.4/§10 已两次实测）。

| 尝试 | 结构 | 结果 |
| --- | --- | --- |
| fix2 | 合并成一个互联(PS+6 IP 主口) + 32 位单口 BRAM | `validate` 过，但生成日志里 **PS 那条又出现 `auto_us`** → 没敢综合 |
| fix3 | 控制(32)走 HPM0_FPD；数据另开 **`M_AXI_HPM1_FPD`(128)** + 6 IP 主口 → 128 位互联 → 128 位 BRAM | `validate` 过、`bram_ctrl` 128 位 ✓；但 **PS 的 `Data` 空间报"没有可用窗口"，BRAM 被自动排除** → PS 仍然够不到 BRAM |

  （非对称双口方案里必然出现一次跨名连接，很可能就是它丢的写）。

### 5.7 ✅ 根因找到并解决：两个 FPD 主口的 PL 地址窗口是分开的

之前"PS 的 Data 空间没有可用窗口"的真正原因是——**`M_AXI_HPM0_FPD` 和 `M_AXI_HPM1_FPD`
在 PL 里各占一半地址空间**，Vivado 报得很明确：

```
Valid apertures are {<0xB000_0000 [256M]>, <0x5_0000_0000 [4G]>, <0x48_0000_0000 [224G]>}
```

即 **HPM0_FPD 管 `0xA000_0000`~`0xAFFF_FFFF`，HPM1_FPD 管 `0xB000_0000`~`0xBFFF_FFFF`**
（跟"裸 PS 没套预设"无关 —— 我一开始猜错了）。

**从零重建后的最终地址表**（`bd/build_ai_sys.tcl`，一条 Tcl 从零出比特流）：

| 主口 | 宽度 | 从机 | 地址 |
| --- | --- | --- | --- |
| `M_AXI_HPM0_FPD` (GP0) | 32 | `img_proc_axil_0` | `0xA000_0000` |
| " | | `conv_layer_0` 控制 | `0xA001_0000` |
| " | | `eltwise_layer_0` 控制 | `0xA002_0000` |
| `M_AXI_HPM1_FPD` (GP1) | **128** | `bram_ctrl`（+ 6 个 IP 主口也映射到它） | **`0xB000_0000`**（128K） |

两条路都同宽 → **全程没有任何位宽转换器** ✓。PS 写 BRAM 用 `0xB000_0000`，
IP 的指针也用 `0xB000_0000`（同一块存储）。`validate_bd_design` 通过，已进入综合实现。

### 5.8 ✅ P4：整网在 32×32 上跑通（逐节点 bit-exact）

**做法**：整网按 **32×32** 跑。因为 `in_h/in_w` 是运行时参数，**整网可以在任意分辨率执行**
（权重不变），而 32×32 时**全部张量峰值只占 5120 字 / 80 KB**，那片 128 KB 张量 BRAM 装得下 ——
于是**一个新比特流都不用出**，直接复用 P3 的 `ai_sys.bin`。

**判据**：用**一字未改的** `conv_layer.cpp` / `eltwise_layer.cpp` 在 Vitis HLS 里跑一遍
`csim_design`（10 秒），逐节点 dump 期望张量 → 板上结果与它**逐字节比对**。

**结果**：**30/30 节点 bit-exact**（两组不同输入：im0002 抽样相位 0 与相位 8，各 0 差异）。
覆盖 3×3 / 1×1 / 2×2 转置 conv、Add、Concat、MaxPool 以及张量缓冲复用。
加速器侧 30 个节点合计 **3.0 ms**。

**板端调度器**（`ai/net/unet_board.py`）要点：
- `/dev/mem` 映射 conv 控制 `0xA001_0000` / eltwise 控制 `0xA002_0000` / 张量 BRAM `0xB000_0000`；
- BRAM 内的 buffer 分配由主机端 `plan.json` 给定（含**缓冲复用**：分析每个张量最后一次被消费的节点，
  用完即回收），并做**两两重叠检查**；
- 每个 CONV 节点：把 `params/<name>.bin` 搬进参数区 → 写 13 个寄存器 → `ap_start` → 轮询 `ap_done`。

**指纹别搞错**：`img_proc_axil` 的 `VERSION` 在偏移 **`0x10`**；偏移 `0x00` 是**只写的 CTRL**，
读回来恒 0 —— 用它判断"PL 是不是我们的设计"会得到假阴性。

**下一步 P4-full**：同一套调度器改成**条带 + halo**跑 512×512。3×3 时产出一行输出需要
`y-1..y+1` 三行输入；喂给 IP 的条带在**条带边界**会被零填充，所以**丢掉首尾 halo 行的输出**、
只留中间有效行即可。IP 一行都不用改。

### 5.9 ✅ P5 + P6：接进上位机链路、C 驱动、换权重

**板端驱动从 Python 换成了 C**（`src/unet_ai.c` + 生成的 `src/unet_net_data.c`），
直接跑在 TCP 服务进程里：同一份工作 **2.87 ms vs Python 8.99 ms（3.1×）**，
且两组向量的逐节点比对都是 `mismatch = 0 / 1024`。

**协议加了 flags**（控制头 v3，8 字节；板子先读 2 字节 magic 再决定读几字节，
所以 v2 老客户端照旧可用）：

| flags | 回传内容 |
| --- | --- |
| b0 | 预处理图（默认，等价于旧行为） |
| b1 | AI 血管掩膜图（0/255 展开成 RGB） |
| b2 | 掩膜叠加图（掩膜以红色叠在预处理图上） |
| b3 | 图像流之前先回 64B 统计块（血管像素数/占比/连通域/logit 范围…） |
| b4 | 只做识别，不回传图像 |

`aiparam`：bit0 = AI 输入源（原始 RGB / 预处理结果），bits[15:8] = 阈值（默认 -3）。
**下行顺序固定**：统计块 → 预处理图 → 叠加图 → 掩膜图。

**换模型的接口**（P6）：换 `network.txt` + `params/*.bin` → 用 `ai/net/gen_unet_c.py`
重新生成 `src/unet_net.h` / `src/unet_net_data.c` → 重新编译部署。**RTL 与驱动都不改。**
真机验证：把 `final` 层的 `mult`/`offset` 取负（等价于 `logit → -logit`），
掩膜从 3.6% 翻到 98.7%，且 1024/1024 逐值精确符合 `logit_B == -logit_A`。

**P6 提速的诚实结论**：32×32 下 AI 只占整帧 ~4%（整帧 74 ms 里 AI 3 ms），
**瓶颈已经不是 AI**，而是 TCP 收图 + PS↔PL 预处理 + 多幅回传。
本章 §6 里"GDMA 搬运 / 选择性片上缓存"是为**全分辨率**准备的，现在还用不上。

**真机实测（真实眼底图 test.ppm，mode 0）**：

| flags | 板端 recv | 预处理 | AI | 回传 | PC 端总耗时 |
| --- | --- | --- | --- | --- | --- |
| v2 老头 | ~21 ms | 20 ms | — | 11 ms | 55.8 ms |
| proc,mask,stats | 21 ms | 20 ms | 3 ms | 25 ms | 74 ms |
| proc,mask,overlay,stats | ~22 ms | 20 ms | 3 ms | ~50 ms | 94.9 ms |
| noimage,stats | 22 ms | 20 ms | 3 ms | ~0 | 42.2 ms |

AI 输出 `vessels=37/1024 (3.6%)`，叠加图红色落在**视盘/血管汇聚区**，是合理结果。

### 5.10 ✅ P4-full：全分辨率 512×512（条带调度）

**整套设计与调试日志另见 [`ai_full_resolution_strip_plan.md`](ai_full_resolution_strip_plan.md)**，这里只放结论：

* 张量从"全放片上 BRAM"改成 **常驻 PS 内存（30 节点共 ~85 MB）**，
  128 KB BRAM 只当"一层条带的暂存"；每个节点按**输出行**切条带（`S` 行一趟）。
* 行依赖：**3×3 要 `y±1`**（喂 S+2 行、丢首尾各 1 行）；**1×1 与转置无 halo**；
  Add/Concat 逐像素；MaxPool 要 `2y,2y+1`。**图像边界由我们自己补零行**，
  不依赖 IP 的边界填充。
* **实测**：与 PLD 自己的 golden `262144/262144 逐值一致`，**2106 ms/帧**。
* **分辨率旋钮**：`--ai-res 512|256|128|64|32`（客户端可在 `aiparam` bits[4:2] 覆盖）。
  512→2185 ms / 256→568 ms / 128→205 ms / 64→116 ms / 32→94 ms（PC 端总耗时）。
* **瓶颈**：2.1 s 对应 ~80 MB 搬运 → 有效 ~38 MB/s，是 PS 对 Device 内存访存的量级。
  **不是 PL 算力问题**；想快就加大 BRAM 或降分辨率。
* ⛔ **必须记住的坑**：**`/dev/mem` 映射区不能用 `memset`**
  （glibc 大块 memset 用 `DC ZVA`，对 Device 内存未定义 → **SIGBUS**）；
  用 `memcpy`，补零自己写 volatile 循环。

## 6. 带宽与速度预算（**如实说：这是这套方案最大的代价**）

CPU 访问 PL 区域是**非缓存单次 32bit 访问**，实测 **~94 ns/次写、~188 ns/次读**
（≈ 20~40 MB/s）：

- L0 一层张量 4 MB：搬进去约 **0.2~0.4 s**，搬出来同量级；
- 整网 30 节点、约 80 MB 张量流量 → **约 3~5 s/帧**（还没算 PL 计算 ~0.44 s）。

**先跑通，再提速。** 提速抓手（按性价比）：
1. **PS 自带 GDMA**：从 DDR 直接搬到 PL 地址段，**能砍掉大部分搬运时间**（首选）；
2. **把 PL 区域映射成可缓存**并配 cache flush/invalidate，让 CPU 按 cache line 突发访问；
3. **选择性片上缓存**：把小的/热层（L2 的 1 MB 张量）常驻 BRAM，省掉往返；
4. **提高时钟**（注意：PS 的 PL 时钟由 FSBL 决定，加载 bit 改不了，见 [[zynqmp-pl-clock-from-fsbl]]）。

## 7. 上位机协议扩展（**保留原 6 个预处理模式不变**）

控制头现在是 `magic(0x4D43) + mode(0..5)`。扩展为：

```
magic(0x4D43) + mode(0..5, 预处理模式，原样不动) + flags(u16) + [ai_param]
```

`flags` 位定义：

| 位 | 含义 |
| --- | --- |
| `b0` | 回传**预处理后**的图（= 现在的行为） |
| `b1` | 回传 **AI 血管掩膜图**（0/255 单通道→展开成 RGB） |
| `b2` | 回传 **掩膜叠加图**（掩膜以红色叠在预处理图上） |
| `b3` | 回传 **数值统计**（血管像素占比、连通域数、平均宽度…），放在行包头或单独的统计包 |
| `b4` | 只做识别、不回传图（省带宽，只要统计） |

**默认 flags = b0（回传预处理图）**，行为与现在**完全一致**，PC 端老代码不用改。

**统计的返回格式**（`b3`）：建议在图像流之前先回一个 64B 统计块
（`magic + flags + 血管像素数/总数 + 占比(定点) + 连通域数 + 版本`），再回图像流。
具体字段在接口冻结时定。

## 9. 风险

| 风险 | 应对 |
| --- | --- |
| 流接口改造破坏已验证的算子行为 | 每个算子改完**先跑 PLD 的测试向量回归**（现成的 cases_all.txt / cases_bad.txt），过了再综合 |
