# P4-full：全分辨率（512×512）条带调度方案

> 目标：让 U-Net 在 **512×512** 上跑，而不是现在的 32×32。
> 本文既是设计说明，也是**调试过程日志**（每步都往下追加实际情况与踩坑）。
>
> 起点：2026-10-02。上游 `ai_inference_design.md` §4.1 已经指出方向（条带 + halo），
> 本文把它落成可执行的规格。

---

## 1. 为什么必须切条带

| 张量 | 大小（int16 容器，通道补到 8） | 说明 |
| --- | --- | --- |
| L0 / 输入 / 输出（512×512，8 通道） | **4 MB** | 一片就是整块 BRAM 的 32 倍 |
| L1（256×256，16 通道） | 2 MB | |
| L2（128×128，32 通道） | 1 MB | |

片上张量 BRAM 只有 **128 KB**（8192 个 128bit 字），当前 `ai_sys` 比特流已用掉
160/216 块 RAMB36，理论上限也就 ~350 KB —— **整层张量永远放不下**。

所以：**张量放 DDR（PS 管），BRAM 只当"一层条带的暂存"**。IP 的 `in/out` 指针与
`in_h/in_w` 都是运行时可传参数，所以按条带调用**不用改一行算子代码**。

---

## 2. 每一项算子的"行依赖"（这是条带正确性的全部依据）

从 PLD 的 `conv_layer.cpp` / `eltwise_layer.cpp` 逐行推出来的（不是猜的）：

| 算子 | 输出行 y 需要哪些输入行 | halo | 条带处理方式 |
| --- | --- | --- | --- |
| **3×3 conv**（mode 0） | `y-1, y, y+1` | **上下各 1 行** | 喂 `S+2` 行，**丢掉首尾各 1 行输出**，保留中间 `S` 行 |
| **1×1 conv**（mode 1） | `y` | 无 | 喂 `S` 行，全部有效 |
| **2×2 转置 conv**（mode 2） | `y>>1`（一行要产两行输出） | **无** | 喂 `n` 行，**产出 `2n` 行且全部有效** |
| **Add**（ELT 0） | `y`（逐像素） | 无 | 喂 `S` 行，全部有效 |
| **Concat**（ELT 1） | `y`（逐像素，按行搬 a、b 再拼） | 无 | 喂 `S` 行，全部有效 |
| **MaxPool**（ELT 2） | `2y, 2y+1` | 无 | 喂 `2S` 行，全部有效 |

推导要点（关键几行）：

* **3×3**：`base_row = y-1`，`need = base_row + kk - 1 = y+1`；滚动窗口 `rows[3]`
  里 `slot0/1/2` 分别落在 `(y+2)%3 / y%3 / (y+1)%3`，正好对应 `y-1 / y / y+1`。
* **转置**：`kk=1`、`base_row = y>>1`、`need = base_row`，只用到一行；`tap = ((y&1)<<1)|(x&1)`
  只决定用 4 个权重里的哪一个（**横向也不跨行**）。
* **MaxPool**：`lane_max(in_a[row+row_words+n], buf_a[n])` 把 `2y / 2y+1` 两行取最大，
  再横向两两取最大。

### 2.1 3×3 的边界怎么处理（**不要依赖 IP 自己的零填充**）

如果指望"IP 在条带边界自动零填充、只丢首尾行"，那么图像**真正的**上下边界
（y=0 与 y=511）会被**多填一次零**（本来该填的地方填了、不该填的也填了）——
第一版设计在这里踩过，后来改成**自己显式提供零行**：

> 设条带要产出输出行 `[y0, y1)`，`S = y1-y0`。
> 组装输入缓冲 **`S+2` 行**，缓冲第 `j` 行 = **真实输入行 `y0-1+j`**；
> 真实行号 `<0` 或 `>= h` 的行**整行写 0**。
> 跑 IP（`in_h = S+2`）得到 `S+2` 行输出，**只保留第 `1..S` 行**（对应真实行 `y0..y1-1`）。

这样：
* 中间条带：缓冲 0..S+1 行全部来自真实数据，IP 不会触发它自己的边界填充；
* `y0=0` 时缓冲第 0 行 = 真实行 -1 → 我们自己写的零行，正是卷积要的 padding；
* `y1=h` 时缓冲第 `S+1` 行 = 真实行 h → 同理。

**结论：图像边界的零填充由我们负责，IP 只当"内部没有边界"用。**

## 3. 每条带能吃多少行（BRAM 预算）

一次调用占用：`in`（若干行）+ `out`（若干行）+ `params`，全部挤在 8192 字里。

记 `rin = w_in × g_in`（输入一行多少字），`rout = w_out × g_out`，`P` = 该层 params 占的字数。

| 情形 | 约束 | 条带高度 |
| --- | --- | --- |
| 3×3 conv | `(S+2)·rin + S·rout + P ≤ 8192` | `S ≤ (8192-P-2·rin)/(rin+rout)` |
| 1×1 conv | `S·(rin+rout) + P ≤ 8192` | `S ≤ (8192-P)/(rin+rout)` |
| 转置 conv | `n·rin + 2n·rout + P ≤ 8192` | `n ≤ (8192-P)/(rin+2·rout)`，**产出 2n 行** |
| Add / Concat | `S·(rin_a+rin_b+rout) + P ≤ 8192` | `S ≤ …` |
| MaxPool | `S·(2·rin+rout) + P ≤ 8192` | `S ≤ …`，且 `2S` 必须是偶数（天然满足） |

按 128 KB（8192 字）算出来的**最坏几层**：

| 层 | w | mode | rin | rout | P | 条带高度 | 512 行要跑几趟 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `up_path_0_conv_layer_block_2` | 256 | 3×3 | 1024 | 512 | 624 | **3** | 86 |
| `up_path_1_conv_layer_block_2` | 512 | 3×3 | 1024 | 512 | 168 | **4** | 128 |
| `down_path_1_block_5` | 128 | 3×3 | 512 | 512 | 1248 | **3** | 43 |
| `cat_1` | 512 | Concat | 512+512 | 1024 | 0 | **2** | 256 |
| 普通 3×3（cig=cog=1，w=512） | 512 | 3×3 | 512 | 512 | ≤336 | **6** | 86 |

> 一眼看出：**Concat 在 512 分辨率下最吃亏**——一行要搬 a(512 字)+b(512 字)、写回
> 1024 字，一次只能吃 2 行。这一项单独就占 256 趟。

## 4. 张量放哪：**PS 内存**（不是 BRAM，也不是 /dev/mem）

* 30 个节点的张量**全部常驻 PS 堆内存**（`malloc`），不复用。
  512 分辨率下总和约 **90 MB**（32×32 时的 21888 字 × 256）。
  板子有 ~1.4 GB 空闲，够用。
* **不做缓冲区复用**：复用能省到 ~21 MB，但要多写一套 C 版分配器 + 重叠校验，
  收益（省 70 MB）不值得在这个阶段冒正确性风险。**先跑通、再优化。**
* 张量在 PS 内存里就是 **128bit 字的裸数组**（每像素每 8 通道 = 16 字节），
  与 BRAM 里的布局完全一致，所以搬运就是 `memcpy`。

---

## 5. 分辨率旋钮（"资源不够就降档"）

条带方案本身**不吃分辨率**（最坏情况 `S=1` 也能跑），所以"资源不够"这条实际上
不会触发。真正需要权衡的是**速度**：512 分辨率下每条带都要 PS↔BRAM 搬一遍，
预计**秒级/帧**。

于是把工作分辨率做成**运行时可调**：网络表里存的是 512 的尺寸，
运行时按 `2^shift` 整除即可得到 512/256/128/64/32。
U-Net 的所有空间尺寸都是 512 的 2 的幂分之一，所以整除永远成立。

* `shift=0` → 512（全分辨率，最慢最准）
* `shift=4` → 32（= 现在 P4 的档位，最快）
* 中间几档给"要快一点又不想太糊"的场合

**默认值待实测后再定**（见第 8 节）。

## 8. 调试与实测记录

### 8.1 ⛔ 第一个大坑：`memset` 到 Device 内存会 SIGBUS

第一次上板，两种档位都是 `Bus error (core dumped)`，而且**一行日志都没有**——
因为 stdout 是块缓冲的，崩了就被吞掉。加了 `setvbuf(..., _IOLBF, 0)` 才看见：

```
[ai] tensors: 30 nodes, 85 MB resident in PS memory
[ai] U-Net ready: ...
[ai] input tensor filled (32x32)
[ai] node 1 kind=1 mode=0 in=32x32 out=32x32 g=1
[ai]   conv S=32 in_off=0 out_off=1088 par_off=2112 par_bytes=768 rin=32 rout=32
[ai]   strip y0=0 Sact=32 nin=34
Bus error (core dumped)
```

崩在"组装输入条带"这一步。而这一步的第一个动作，恰好是 3×3 卷积给条带**补零行**
（`ty = -1`）时的 `memset(dst, 0, 512)`。

**根因**：glibc 的 `memset` 对大块且对齐的目标会用 **`DC ZVA`**（数据缓存清零指令）。
`DC ZVA` 只对 **Normal 内存**合法；对 `/dev/mem` 映射出来的 **Device 内存是未定义行为**，
ARM64 上直接抛 **SIGBUS**。

> 这条值得单独记住：**/dev/mem 映射区绝不能用 `memset`**（也不能用任何可能落到
> `DC ZVA` 的库函数）。`memcpy` 反而没事——它走 `ldp/stp`，地址对齐就行。

**对策**（现在的代码）：

| 用途 | 实现 | 原因 |
| --- | --- | --- |
| 数据搬运 | **`memcpy`** | 不用 `memset`，走 ldp/stp，对齐即可；而且比逐字快得多 |
| **补零行** | 自己写的 **volatile 32bit 循环** | 编译器绝不会把它换成库调用，也不可能用 DC ZVA |

零行只出现在每个节点的首/末条带，走慢路径对总耗时没影响。
（试过全程用 volatile 32bit 循环：功能正确，但 32×32 档位从 9 ms 掉到 25 ms —— 4 倍差距。）

### 8.2 ✅ 档位回归：条带调度器 vs P4 的 golden

**条带逻辑正确** ✓（作为对照：P4 那套"张量全放片上 BRAM"的调度是 2.87 ms；
条带版多出来的开销是逐行 memcpy 与更多次寄存器配置。）

### 8.3 ✅ 全分辨率：512×512 vs PLD 自己的 golden

判据是 PLD `deployment/unet_network/vectors/images/im0002/` 里的
`input.bin`（512×512×8）与 `golden/final.bin` —— 他们用**同一套 HLS 源码**跑 C 仿真得到的。


### 8.5 时间都花在哪（从 2.1 s 反推）

整网一次要把约 **80 MB** 的张量从 PS 内存搬进/搬出 BRAM，
其中还因为 halo 多搬了一部分。2.1 s / 80 MB ≈ **38 MB/s** —— 正好落在
"PS 对 Device 内存单次访存 ~94 ns/写、~188 ns/读"的带宽量级上。
**瓶颈是 PS↔BRAM 的搬运，不是 PL 的计算，也不是带宽之外的东西。**

想再快，方向是（按性价比）：
1. **加大 BRAM**（现在只用 128 KB，板子上还有 ~56 块 RAMB36 空闲）。
   条带高度 S 近似线性于 BRAM 大小 → 搬运次数近似反比 → 有可能砍掉一半以上。
2. **降低工作分辨率**（`shift=1/2/3`）——见第 5 节的旋钮。
3. 让 PS 用 NEON 做搬运（现在 `memcpy` 已经是 libc 的向量实现，提升空间有限）。

### 8.6 ✅ 接进服务 + 分辨率扫描（真机，test.ppm）

板端加了 `--ai-res <32|64|128|256|512>`（默认 512），
客户端可以在 `aiparam` bits[4:2] 里逐帧指定（0 = 用板端默认）。
两者都走同一套条带调度，只是把节点尺寸右移若干位。

真机实测（test.ppm = im0002 眼底图，mode 0，flags=proc,mask,overlay,stats）：

| 分辨率 | AI 整网 | 血管像素 | 连通域 | PC 端总耗时 |
| --- | --- | --- | --- | --- |
| **512** | **2076 ms** | 16458/262144 (6.3%) | 12587 | **2185 ms** |
| 256 | 480 ms | 4317/65536 (6.6%) | 69 | 568 ms |
| 128 | 120 ms | 761/16384 (4.6%) | 67 | 205 ms |
| 64 | 31 ms | 120/4096 (2.9%) | 15 | 116 ms |
| 32 | 8.3 ms | 37/1024 (3.6%) | 4 | 94 ms |

（512 那一档 AI 占整帧 95%；32 那一档 AI 只占 9%，剩下的都是 TCP 收图 + 预处理 + 三幅回传。）

**效果**：512×512 的掩膜（`e2e_out/fullres_mask_512.png`）是一棵**真正的血管树**——
左侧视盘、放射状主血管、上下血管弓都清清楚楚；
叠加图（`fullres_overlay_512.png`）里红色几乎精确地贴在真实血管上。
**这才是"全分辨率"的意义**：32×32 时掩膜是 16 倍放大的方块，什么都看不出来。

### 8.7 结论

* **全分辨率跑通了**，而且结果与 PLD 自己的 golden **逐值一致**（262144/262144）。
* 代价是 **2.1 秒/帧**（≈0.47 fps）。这是"PS 当搬运工"这条路线的**硬上限**：
  瓶颈是 PS 对 Device 内存的访存带宽（~38 MB/s 有效），不是 PL 算力。
* 想快就**降分辨率**（现成的旋钮），或者**加大 BRAM**（还没做，见 8.5）。
* ⚠ 一个必须记住的坑：**`/dev/mem` 映射区不能用 `memset`**（`DC ZVA` → SIGBUS），
  用 `memcpy`；补零要自己写 volatile 循环。

## 9. A1：加大张量 BRAM（128 KB → 256 KB，2026-10-02）

**目标**：把条带暂存从 128 KB 加到片上能放下的最大，减少条带搬运次数。

### 9.1 能加到多大（先算账）

实现后的真实占用（`ai_sys` 128 KB 版）：**160 / 216 块 RAMB36**，其中
img_proc 帧缓冲 **64** ＋ 张量 BRAM **32** ＋ conv_layer **39** ＋ eltwise_layer **25**。
**只剩 56 块**。张量 BRAM 128 KB（1 Mb）＝ 32 块，**翻倍到 256 KB 约需 64 块**
（→ 总计 192/216 ≈ 89%）；**再大到 384 KB 会超**（224 > 216）。所以 A1 = **256 KB**。

### 9.2 改动

| 位置 | 改动 |
| --- | --- |
| `ai/bd/build_ai_sys.tcl` | `bram_gen` `Write_Depth_A 8192→16384`；地址段 `-range 128K→256K`；`validate_bd_design` 改 `-force` |
| 同上（**顺手修的脚本 bug**） | 加 `set_property STEPS.WRITE_BITSTREAM.ARGS.BIN_FILE true [get_runs impl_1]` —— 否则 `write_bitstream` 只出 `.bit`，脚本拷 `.bin` 那步会报错 |
| `ai/net/gen_unet_c.py` | 默认 `bram_words 8192→16384`（条带调度分支与 plan 分支各一处） |
| `src/unet_net.h` | `UNET_BRAM_WORDS 8192u→16384u`（驱动据此 mmap 256 KB 并算条带高度） |

**不需要动**：RTL 一行没改、驱动逻辑一行没改、地址基址仍是 `0xB000_0000`。

### 9.3 结果（真机）

- 综合实现：**0 error / 0 warning / 0 critical warning**；
  **WNS +2.013 / WHS +0.0115**（全部满足）；Block RAM **192/216 (88.9%)**、
  LUT 50.6%、DSP 57.2%。`.bin` md5 `9f141b1b4f175faddeb9e6c3f0d8049e`
  （旧 128 KB 版 `3e9051a4…`，备份在 `bitstream/_pre_a1/ai_sys_128kb.bin`）。
- **验证（`ai/net/run_fullres.py`）**：

| 档位 | A1 前 | A1 后 | 一致性 |
| --- | --- | --- | --- |
| 512×512（shift=0） | 2106.6 ms | **1946.8 ms** | `mismatch = 0 / 262144` **PASS** |
| 32×32（shift=4，回归） | 9.07 ms | 8.62 ms | `mismatch = 0 / 1024` **PASS** |

  logit 范围 `[-107..100]`、非零 `261623/262144` —— 与改前**逐值不变**。
- 端到端（PC 客户端 `imagelink.py`，走服务进程）：`ai_us=1948708`，
  `mask(rows_ok=512)`，总耗时 2026 ms —— 服务确实用上了 256 KB。

### 9.4 ⚠ 为什么只有 7.6%（重要结论，别高估这个方向）

事前用 `ai/net/_a1_estimate.py` 按 `unet_ai.c` 的条带公式把两个 BRAM 尺寸下
**逐节点搬运量**都算了一遍：

```
BRAM 8192 字 (128KB): TOTAL in=7976960 out=5341184 params=116384  sum=13434528 字 = 215.0 MB
BRAM 16384 字 (256KB): TOTAL in=7307776 out=5341184 params=48068  sum=12697028 字 = 203.2 MB
```

**只降 5.6%，实测 7.6%**（多出来的部分来自每条带固定开销减少）。原因：
1. **输出搬运量与条带高度无关** —— 5.34M 字永远要整张从 BRAM 拉回 PS 内存；
2. **halo 只在输入侧**（3×3 的 `+2` 行），且占总输入不到 10%；
3. **params 逐条带重复拷贝**总共才 116k 字（0.9%）—— 之前以为是个大项，算下来不是。

（交叉验证：把模型缩到 32×32 档得 215 MB/256 ≈ 0.84 MB，按 ~100 MB/s 折合 ~8.2 ms，
与实测 9.07 ms 吻合，模型可信。）

**所以 A1 是"便宜、安全、但只值个位数百分比"的一步。** 真正的杠杆在
**降低搬运量本身**（int8 打包 → 减半）或**提高搬运算力**（把 PS↔BRAM 访问
从 Device 强序换成可流水的映射）。见 §7 的 8.5 与交接文档里的方向清单。

## 10. 第 0 步：整网时间分解（2026-10-02，实测）

给 `src/unet_ai.c` 加了插桩（`unet_stats_t` 扩了 `ap_us/put_us/get_us/zero_us/
strips/put_words/get_words/param_words`，并可按节点 dump），板端 `unet_selftest`
打印；跑法 `ai/net/_profile_run.py`（发 `UNET_PROFILE=1`）。

### 10.1 结果（512×512，整帧 1948.8 ms）

| 段 | 时间 | 占比 | 吞吐 |
| --- | --- | --- | --- |
| **get  BRAM → PS** | **1112.0 ms** | **57.1%** | 5 341 184 字 = 85.5 MB → 76.9 MB/s（**208 ns/字**） |
| **ap   PL 计算**（等 ap_done） | **531.4 ms** | **27.3%** | — |
| **put  PS → BRAM** | **287.9 ms** | **14.8%** | 7 322 564 字 = 117.2 MB → 407 MB/s（**39 ns/字**） |
| zero 补零行 | 2.1 ms | 0.1% | — |
| other（PS 循环/索引/寄存器/取 logits） | 15.5 ms | 0.8% | — |

条带数 **826**；搬运字数与 `_a1_estimate.py` 的模型 **逐位吻合**
（out = 5 341 184 完全一致；in+params 差 < 0.5%）—— 模型已验证。

32×32 档（8.86 ms）同比例：ap 2667 / put 1046 / get 4566 / other 329 us。

### 10.2 三个结论

1. **搬运确实是主瓶颈**（put+get = 1400 ms = **71.8%**，计算只有 27.3%）——
   文档早先"瓶颈是 PS↔BRAM 搬运、不是 PL 算力"的判断**成立**。
2. **但结构完全出乎意料：读占 57%、写只占 15%。** 读一个 128 位字要 **208 ns**、
   写只要 **39 ns** —— **读比写慢 5.3×**。这不是数据量问题，是 **PS 读 Device 内存
   的强序代价**（每次读一个完整的 AR→R 往返，无法流水）。
   （早先文档按"80 MB / 38 MB/s"估的带宽是**低估**：实测写 407 MB/s、读 77 MB/s。）
3. **读是最值钱的单一目标**：1112 ms 里绝大部分可省。

### 10.3 由此排出的下一步（按性价比）

| 方向 | 预期 | 难度 | 说明 |
| --- | --- | --- | --- |
| **A-ov 计算/读回重叠（双缓冲）** | **省 ~450–530 ms（23–27%）** | 中 | **纯软件、不用重出比特流**。IP 跑第 k 条带时 CPU 去拉第 k-1 条带的输出 —— 把 ap(531 ms) 藏到 get+put(1400 ms) 后面。**需要两块输出/输入缓冲 → 正是 A1 腾出来的 256 KB 才有空间做。** |
| A3a 让读走可流水映射 | 省 ~800 ms（40%+，?) | **高** | 给 BRAM 做内核模块 `ioremap` 成 Normal-NC/WC，让 CPU 能流水化读。要编 vendor 4.14 模块，风险/未知大。 |
| A3b int8 打包 | 省 ~550 ms（28%） | **高** | 读量减半。要重导两个 HLS IP、全链路重做。 |

**结论：下一步做 A-ov（重叠），是"纯软件 + 收益 ~25%"的最优解**；A1 加大 BRAM
的真正价值也在这里兑现（没有那多出来的 128 KB，双缓冲要把条带砍到一半，
halo 开销反而吃掉收益）。

## 11. A-ov（读回与计算重叠）—— **试做了，被硬件挡住（2026-10-02）**

第 0 步的分解说明 `get`(1112 ms) >> `ap`(531 ms)，所以重叠"读回"与"计算"
理论上能把 ap 整个藏起来。**实现并上板了，但结果是错的** —— 这一节把经过和
判据钉下来，**以后别再重走**。

### 11.1 设计（已实现，代码留在 `ai/net/_unet_ai_aov_overlap_reference.c.txt`）

- **输出缓冲 ×2，输入仍 ×1**：因为 get(1112) >> put(288)，把"组装"也重叠是白搭
  （CPU 总工作量本来就 > 计算），而只翻倍输出让条带高度只从 14 降到约 10
  （不是砍半），halo 代价小。
- 循环重排成软件流水：
  `组装(k) → 编程+start(k)[异步] → 拉回(k-1)[与 IP 重叠] → wait(k)`
  （`start_and_wait` 拆成 `start_ap` + `wait_ap`）。

### 11.2 ⛔ 结果：快了，但**数据是错的**

| 版本 | 512 档耗时 | 与 golden |
| --- | --- | --- |
| A1（单缓冲，不重叠） | 1949 ms | **0 / 262144 PASS** |
| **A-ov（重叠）** | **1626 ms** | **253787 / 262144 FAIL** |
| A-ov 但 `UNET_NOAOV=1`（同布局同条带，只关重叠） | 1992 ms | **0 / 262144 PASS** |

**判据（决定性）**：第三行用的**布局、条带高度、条带数（1207）、搬运字数全部相同**，
只把"读回调到 wait 之后" —— 就 PASS 了。⇒ **布局/条带高度/双缓冲都是对的，
唯一变坏的是"CPU 在 IP 运行期间访问同一片 BRAM"这件事本身。**

（另：重叠有效是真的 —— 1626 vs 1992，**重叠本身值 18%**。但数据坏了，不能用。）

### 11.3 根因（推断）

**这是本工程第一次出现"CPU 与 IP 同时对同一片 BRAM 发起访问"**：
A1 及以前每个条带都是 `组装 → start → wait(IP 跑完) → 拉回`，CPU 与 IP
**从不同时**碰 BRAM。重叠后变成"IP 在写 out[k&1]，CPU 在读 out[(k-1)&1]"，
两个 master 同时向 `ai_data_ic`（axi_interconnect，7 SI → 1 MI）→ `bram_ctrl`
发事务，数据就坏了。

最像的原因是**互联/控制器对并发读的 ID（RID）路由**或**单口 BRAM 的
读写切换**处理不住 —— 症状是输出饱和到 ±127（像输入被读错），
且 96.8% 的像素都错。

### 11.4 结论与可选出路

- **默认状态已回退到单缓冲（A1 语义）**，`src/unet_ai.c` 里所有条带仍走
  `start_and_wait`；板端服务已重编部署，与 golden 逐值一致。
- **A-ov 本身没问题，是被这块板子的 BRAM 访问路径卡住。** 想解锁只有改 BD：
  1. **`blk_mem_gen` 改真双口 + `axi_bram_ctrl` `SINGLE_PORT_BRAM=0`** —— 让控制器
     能在 A 口读的同时 B 口写，绕开单口读写切换。**改动最小、最值得先试。**
  2. 数据通路 `ai_data_ic` 从 `axi_interconnect` 换 **`SmartConnect`（高性能模式）**，
     它自己管 RID 分配。（注意：Low-Area 模式的 SmartConnect 在本板有"返回上一次
     读的数据"的实测 bug，见 9.6。）
  3. 把张量 BRAM 拆成两块、各挂一个 `axi_bram_ctrl`，让 CPU 与 IP 走**不同从机**。
- 以上都要**重出比特流 + 全回归**（约 30–40 min），且**不保证有效**。相比之下
  **A3a（让 BRAM 读走可流水映射）与 A3b（int8 打包）绕开了这个问题**，
  但一个风险高、一个工程量最大。

## 12. A3b（int8 打包）—— **实测证明无效，不做**（2026-10-02）

### 12.1 为什么"减字节"没用：访问次数才是成本

在板上用同一段代码、同样 16 字节步长各搬 16 MB（脚本 `ai/net/_memtest.py`）：

```
A 128bit(ldp): 16384 次 x 16B | 207296 us | 197.7 ns/次 | 80.9 MB/s
B  64bit(ldr): 32768 次 x  8B | 414547 us | 197.7 ns/次 | 40.5 MB/s
```

**每次访问的耗时完全相同（197.7 ns），与一次搬多少字节无关。** ⇒ 读 BRAM 是
**纯延迟 / 访问次数主导**（每次一个完整 AXI 往返，没有流水）。

**所以"int8 打包"（每个字仍是 8 通道、只把 16 位压成 8 位 = 每次搬的字节减半、
访问次数不变）→ 一点都不会快。** 这个方向是死的。

（反推验证：整帧 读 5 341 184 次 × 198 ns = 1057 ms，实测 1112；写 7 322 564 次
× 39 ns = 285 ms，实测 288 —— 成本模型 = **次数 × 每次延迟**，完全对得上。）

### 12.2 198 ns 是谁的：一半是映射、一半是 PL 通路

同一段代码分别读三块（脚本 `ai/net/_memtest2.py`）：

| 目标 | ns/次 | MB/s |
| --- | --- | --- |
| **PL 张量 BRAM** `0xB0000000` | **197.7** | 80.9 |
| **PS 自己的 DDR** `0x40000000`（同样走 `/dev/mem`） | **102.9** | 155.5 |
| **普通内存**（malloc，可缓存） | **4.2** | 3810 |

⇒ **~103 ns 是 `/dev/mem` 的 Device 映射语义**（强序、不可缓存，连读 PS 自己的
DDR 都要这么久）；**另外 ~95 ns 是 PL 通路**（NoC → `ai_data_ic` → `bram_ctrl` 往返）。
**可缓存访问只要 4.2 ns —— 快 47 倍。**

### 12.3 结论：真正有效的只剩三条路

| 方案 | 效果 | 代价 |
| --- | --- | --- |
| ~~int8 打包（8 位宽仍是 8 通道/字）~~ | **0%（已证）** | — |
| **每字塞 16 个 int8 通道**（访问次数减半） | 只对 ≥16 通道的层有效 → **整体 ~19%** | 改两个 HLS 算子（lane 8×16b→16×8b）+ 重出比特流 + 全部软件/金标准重做。**工程量最大** |
| **改映射：内核模块 `ioremap` 成 Normal-NC/可缓存** | 搬运可从 1400 ms → ~700 ms（**整体 ~36%**）；若可缓存 + cache 维护甚至更高 | **要编内核模块**；板上**没有 kernel build 目录**（`/lib/modules/4.14.0-xilinx-v2018.3/build` 不存在），得先搞到内核源码+config 交叉编译。有风险 |
| **PS 自带 GDMA 做搬运**（板上有：`/sys/class/dma/` 22 个通道，`zynqmp-dma` 已加载） | 支持 burst，可能 4–10× 于搬运 | 没有内核 build 目录 → 只能用户态直接编程寄存器（有挂总线风险），或也走内核模块 |

**一句话：A3b（int8 打包）实测无效；要继续提速应该打"每次访问 198 ns"本身
（改映射 / 上 DMA），而不是打"搬多少字节"。**

## 13. 改映射：`plbram.ko`（2026-10-02，代码就位、等内核源码）

按 §12 的结论，选"把 BRAM 换成 Normal-NC 映射"这条路。模块与脚本已全部写好并
放到板上（`tcp_image_rx/kmod/`，板上 `/root/tcp_image_rx/kmod/`），**只缺内核源码树**。
完整说明见 **`kmod/README.md`**。

要点回顾：
- `/dev/mem` = Device 映射 → 每次访问 103 ns（连 PS 自己的 DDR 都一样慢）；
  换 **Normal-NC（写合并）** 让 CPU 能有多笔未完成访问 → 读应显著变快。
- **不选"可缓存"**：ARM64 用户态**不能**执行 `DC IVAC`（失效），没法安全地做 cache 维护。
  Normal-NC **不缓存 ⇒ 零 cache 维护，也不存在和 PL 的一致性问题**。
- **在板上原生编译**（板载 gcc 7.5.0 正好配 4.14 内核），避开工具链不匹配；
  板上 MODVERSIONS/MODULE_SIG 都没开 → 不需要 `Module.symvers`、不需要签名。
- 阻塞项：需要 Xilinx linux-xlnx 2018.3 的源码树（`make kernelrelease` 必须是
  `4.14.0-xilinx-v2018.3`）。

---

## 14. `plbram.ko` 上板实测（2026-10-02）—— **写快 2.7×，读不变；整体 −9.4%**

### 14.1 过程（三个坑）

1. **板上没有 `bc`**，而 Kbuild 靠它生成 `include/generated/timeconst.h`
   （`echo 250 | bc -q kernel/time/timeconst.bc`）→ `make modules_prepare` 直接
   `bc: not found` 挂掉。板子没外网装不了 → **写了个 Python 的 `bc` 替身**
   （`kmod/bc`，把 timeconst.bc 的 gcd/fmul/fadj/fmuls 算法原样实现，带数值自检），
   装到 `/usr/local/bin/bc`，内核树一行没改。
2. **4.14 里没有 `misc_unregister`** → 是 `misc_deregister`。改了就好。
3. 其余一切顺利：板上 gcc 7.5.0 原生编译，`vermagic=4.14.0-xilinx-v2018.3 SMP
   mod_unload aarch64` 与运行内核完全一致（MODVERSIONS/MODULE_SIG 都没开，
   所以不需要 `Module.symvers`、不需要签名）。

### 14.2 结果：**只有"写"变快了**

同一段代码、同样 16 B 步长（`ai/net/_plbram_bench.c`）：

| 目标 | 操作 | `/dev/mem` (Device) | `/dev/plbram` (Normal-NC) |
| --- | --- | --- | --- |
| **PL BRAM** `0xB0` | 读 | 197.8 ns/字 | **197.7 ns/字（没变）** |
| **PL BRAM** `0xB0` | 写 | 39.5 ns/字 | **14.8 ns/字（2.67×）** |
| PS DDR `0x40`（不过 PL） | 读 | 102.7 ns/字 | **102.9 ns/字（没变）** |
| PS DDR `0x40` | 写 | 9.4 ns/字 | **3.2 ns/字（2.9×）** |

**读一点没变——连 PS 自己的 DDR 也一样。** ⇒ **这颗 CPU 的"非缓存读"就是一次完整
往返、不流水，跟映射属性（Device vs Normal-NC）无关；Normal-NC 只对"写"有效
（写合并/写缓冲）。** 所以读那 57% 的成本（1112 ms）靠改映射**救不了**，
只能靠"少访问几次"（更宽的打包）或换 burst 主设备（DMA）。

### 14.3 整帧效果（驱动已接入，`/dev/plbram` 优先、没有就退回 `/dev/mem`）

| | A1（`/dev/mem`） | A1 + `plbram.ko` |
| --- | --- | --- |
| 512 整帧 | 1950.9 ms | **1767.9 ms（−9.4%）** |
| put（写） | 287.9 ms | **107.9 ms（2.67×）** |
| get（读） | 1112 ms | 1112.7 ms（不变） |
| ap（PL 计算） | 531.4 ms | 531.4 ms（不变） |
| golden | 0/262144 PASS | **0/262144 PASS** |

服务里端到端：`ai_us` 1948708 → **1765383**，`vessels=35257/262144` 与改前
**完全一致**。32 档 8.88 → 7.98 ms。

⚠ **写合并的正确性保护（必须保留）**：Normal-NC 下组装的写可能还在 CPU 写缓冲里，
而 `AP_START` 是走**另一个口**（HPM0 控制口）发出去的，两条路无顺序保证 →
加 `bram_commit()`：**读回程序顺序里最后一个写入字**，靠"同 master 对同从机的写保序"
确保它之前的写都已到 BRAM。代价 ~200 ns/条带，可忽略。

### 14.4 顺带把 A-ov 也重试了 —— **仍然坏，且与映射无关**

用新映射重跑 A-ov（`ai/net/_make_aov_plbram.py` 把存档的 A-ov 版接上 plbram）：

| 版本（都走 Normal-NC） | 耗时 | 与 golden |
| --- | --- | --- |
| A-ov 重叠 ON | 1437 ms | **253787/262144 FAIL** |
| 同布局、只关重叠 | 1805 ms | **0/262144 PASS** |

**失配数 253787 与当初用 `/dev/mem` 时一模一样** ⇒ **并发访问的破坏在 PL 互联/
控制器那一层，跟 CPU 侧映射属性无关。`plbram.ko` 救不了 A-ov。**
（A-ov 要活只能改 BD：真双口 BRAM / SmartConnect / 拆两个控制器。）

### 14.5 交付状态

- `plbram.ko` 已放进 `/lib/modules/<ver>/extra/`，并做成开机自加载
  （`/etc/systemd/system/plbram.service`，`systemctl is-enabled` = enabled）。
- 驱动 `src/unet_ai.c`：优先 `/dev/plbram`，没有就自动退回 `/dev/mem`
  （`UNET_BRAM_MEM=1` 可强制走 `/dev/mem` 做对照）。**模块不在也不影响功能**，
  只是没有那 9.4%。
- 脚本：`_plbram_setup.py`（check/install-bc/install-boot/build/bench/bench-ddr/status）、
  `_make_aov_plbram.py`、`_plbram_bench.c`。
