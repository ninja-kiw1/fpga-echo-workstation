# PL 后处理流水线：可行性摸底（2026-10-12）

> **同日补充：原型结果**（`ai/pp_hls/`，详见那里的 README）。功能：阈值、整数双线性放大、4/8 连通计数、最大块 + 填洞、分块和、位掩膜。
> 174 个用例（真实眼底、CT、心超 logit + 人工难例）在原生 g++、Vitis C 仿真里全部逐位一致；3 个代表用例的 C/RTL 协同仿真通过。
> **资源（Vivado OOC 综合）**：LUT 8 561、DSP 23、BRAM 15 块，100 MHz 下时序 5.85 ns。并进现有设计后约为 BRAM 203/216、LUT 81%，**放得下**；
> 第四节估的 4–8 块 BRAM 偏低，实际 15 块，余量仍够。
> **速度**：v1 每像素约 9 拍（眼底计数 24 ms）。**v2 改成每行一个 II=1 循环后：眼底 512 计数 3.67 ms（板上 PS 4.5 ms），心超清理 0.57 ms，CT ×4 放大 3.40 ms**；
> 资源反而更少（LUT 7 652、DSP 19、BRAM 11 块，6.32 ns），182 个用例逐位一致，协同仿真通过。下一步是接进 BD。

> 问题：想在 PL 上加一条后处理流水线（阈值 → 放大 → 形态学 → 连通域 → 统计），BRAM 只剩 28 块，
> 要不要先把 `img_proc_axil` 的全帧缓冲（64 块）改成行缓冲，把 BRAM 腾出来？
> 依据：当前部署的固件 xu2dp_e2b 的布线后网表（`report_utilization -hierarchical`）、RTL 源码、`unet_ai.c`、
> e2b 验收时的逐层计时。**没有改任何设计。**估算部分标"估"，要等 HLS 综合确认。

## 结论

1. **不需要动帧缓冲。**按流式设计，后处理流水线估计只要 **4–8 块 RAMB36**，现在空着的 28 块够用。
   真正要算清的是 **LUT**（已用 67%，剩约 2.3 万）和**怎么接进现有数据通路**（建议见第五节）。
2. 帧缓冲**可以**换成行缓冲：只有模式 0（归一化）和模式 4（归一化 + 伪彩）需要整帧 min/max，其余模式只看 3×3 邻域。
   但腾出来的 64 块 BRAM，更值得留给"把张量 BRAM 加大一倍"去评估 AI 提速，而不是给后处理用（第四节）。
3. 下一步建议：先用 HLS 写后处理流水线的 C 仿真原型，再综合拿到真实的资源数，然后才决定动不动 BD。

## 二、`img_proc` 为什么要全帧缓冲

数据通路（`rtl/gray_frame_store.v` + `rtl/mode_map.v`）：PS 通过 AXI-Lite 寄存器逐像素写入 → 转灰度 → **写进 512×512×8 位的帧 RAM，同时统计 min/max** →
整帧写完后，按 3×3 窗口读出 → 按模式映射 → PS 逐像素读回。

帧缓冲的唯一硬性理由是**归一化要先知道整帧的 min/max**，单趟流式拿不到。各模式依赖什么：

| 模式 | 计算 | 需要整帧 min/max | 需要的窗口 |
| --- | --- | --- | --- |
| 0 归一化 | `(g−min)·recip[max−min] >> 8` | **是** | 1×1 |
| 1 阈值 | `g ≥ thr` | 否 | 1×1 |
| 2 Sobel 边缘 | \|gx\|+\|gy\| | 否 | 3×3（两行行缓冲） |
| 3 伪彩（原始灰度） | `jet[g]` | 否 | 1×1 |
| 4 归一化 + 伪彩 | `jet[norm]` | **是** | 1×1 |
| 6 边缘叠加 | PL 跑模式 2，PS 叠加 | 否 | 3×3 |

## 三、腾出帧缓冲的三种办法

| 办法 | 做法 | 代价 | 评价 |
| --- | --- | --- | --- |
| A 两趟推送 | 模式 0/4：第一趟只统计 min/max，第二趟再推一遍，经行缓冲输出；其余模式只推一趟 | 模式 0/4 每帧多一次 AXI-Lite 推送（现在灰度模式整帧推 + 拉约 20 ms，估计多 10–20 ms，需实测） | 计算全在 PL，但模式 0/4 变慢 |
| B PS 顺手算 min/max | PS 本来就逐像素在推，顺手统计 min/max 写进一个寄存器；PL 用两行行缓冲（约 1 块 BRAM 或 LUTRAM） | 几乎为零 | 最省事，但"统计"这一步在 PS 上，报告里要如实写 |
| C 借用张量 BRAM | 预处理和 AI 分时复用那 256 KB（正好放下一帧 8 位灰度） | 要给 `img_proc` 加一个访问张量 BRAM 的主口，还要分时仲裁 | 改动大，不划算 |

三种办法都能腾出约 63 块 BRAM，但**后处理流水线用不到**（见第四节）。这 63 块真正有价值的用途是：

- **张量 BRAM 从 256 KB 加到 512 KB**：条带变高，条带数（512 档现在 853 条）减少，halo 的重复搬运变少，
  有可能削减 `put`/`get`（现在约 76 + 79 ms）。具体能省多少要单独评估。这属于 PL 性能这条线，和后处理无关。
- 第二个卷积引擎**仍然放不下**：要约 39 块 BRAM 加 185 个 DSP，但 DSP 只剩 98 个。

## 四、后处理流水线需要多少资源（估）

假设做成一个 HLS IP，按行流式处理，一拍一个像素：

| 级 | 做什么 | 存储需求 | 估计 BRAM |
| --- | --- | --- | --- |
| 阈值 | `logit ≥ thr` | 无 | 0 |
| ×k 双线性放大（128 → 512，CT 用） | 系数 1/8、3/8、5/8、7/8，整数运算可以和 `ct_volume.upsample_bilinear` 逐位对齐（待验证） | 两行源数据（128×8 位） | 0（用 LUTRAM 或寄存器） |
| 3×3 形态学（开、闭） | 二值腐蚀和膨胀 | 每次运算两行 512×1 位 | 0（LUTRAM） |
| 单遍连通域标记 + 特征表 | 带标号回收的单遍算法：同一时刻存活的标号不超过宽度的一半（256 个），每个连通块累加面积、外接框、Σx、Σy，连通块结束时直接输出 | 标号行缓冲 512×9 位；合并表 256×9 位；特征表 256×约 110 位 | **2–4** |
| 填洞 | 对背景再做一次连通域，不碰边界的背景块就是洞 | 第二套标号和合并表，或者对已存的位掩膜再扫一遍（位掩膜存回张量 BRAM，不额外占用） | 1–2 |
| 4×4 分块求和（F5 配准） | 16 个累加器 | 无 | 0 |
| 输出缓冲 | 位掩膜和连通块表写回张量 BRAM | 复用张量 BRAM | 0–2 |
| **合计** | | | **约 4–8 块（估）** |

LUT 估计在 5 000–10 000（连通域的合并逻辑和特征累加是大头），DSP 只需个位数。**能放进现有余量**，但 LUT 用量会到 75–80%，布线时序要实际跑过才知道（现在 101 MHz 的余量还不错）。

三维连通域（CT 用）不放在 PL：PL 每层给出二维连通块表，PS 只需要在"块表"上做层间合并，数据量很小。
Zhang-Suen 骨架化（血管形态指标）要多次迭代，不是流式运算，**留在 PS**。

## 五、接进数据通路的方式

| 方式 | 说明 | 评价 |
| --- | --- | --- |
| 接在 `img_proc_axil` 上（AXI-Lite 逐像素） | PS 每帧要推、拉 26 万次寄存器访问 | ✗ 512 档每帧多 10–20 ms 的推拉，而且 logit 本来就在张量 BRAM 里，绕一圈不划算 |
| **做成第三个 HLS 算子，和 conv/eltwise 一样走张量 BRAM**（推荐） | 最后一层卷积的每个条带算完、还在 BRAM 里时，PS 启动后处理 IP，就地读 logit，把位掩膜和连通块表写回 BRAM。IP 内部保留跨条带的行缓冲和标号状态 | ✓ 完全沿用现在"PS 调度、PL 计算、BRAM 交换"的架构；`ai_data_ic` 加一到两个主口（约 1–2 千 LUT） |

顺带的收益：
- 最后一层的输出现在按每像素 16 字节读回（8 个 int16 通道里只用了第 0 个），512 档是 4 MB，约占全部读回量的 4.9%（约 4 ms）。改成只读位掩膜（32 KB）和连通块表后，这部分基本消失。
- 这是小头，主要价值仍然是把阈值、形态学、连通域**从 PS 搬到 PL**。

会用到这条流水线的地方：`ai_view` 的掩膜、叠加和连通块计数；CT 的放大、阈值和最大连通块（二维部分）；心超 EchoNet 的清理（最大连通块 + 填洞）；F5 的分块求和。

## 六、风险

- **LUT**：估计用量到 75–80%，比 BRAM 更可能成为瓶颈。要以 HLS 综合报告为准。
- **逐位一致**：现在的 PS/PC 实现（`ai_view_count`、`ct_volume.upsample_bilinear`、`echo_ws.clean`）就是 golden。
  双线性放大要证明整数实现和 float32 结果逐位相同（k=4 时系数是 1/8 的倍数，理论上可以）。
- **连通域算法本身**：单遍算法的合并和标号回收逻辑容易出错，C 仿真要覆盖螺旋、U 形、梳状等难例，再拿真实掩膜跑。
- 时序：101 MHz 下应该没问题；如果以后提到 148 MHz，要重新收敛。

## 七、建议的下一步

1. **HLS C 仿真原型**（约 1–2 天）：阈值 + 放大 + 形态学 + 连通域特征表 + 分块求和；
   拿现有 PS/PC 实现做 golden，用 CT、EchoNet、眼底的真实 logit 逐位比对。
2. **C 综合**：拿到真实的 LUT、BRAM、DSP 和时序估计，确认放得进去，再决定要不要接进 BD。
3. 接进 BD、改调度、上板，按现有验收流程做 17 个程序回归。
4. 帧缓冲先不动。将来评估"张量 BRAM 加倍"时，再按第三节的办法 B（PS 顺手统计 min/max）腾出 BRAM。
