# ① 实时化：紧凑帧 + 板端跟踪状态 + 流水线（v5.4，2026-10-09）

**一句话**：心超的序列跟踪从约 9 帧/秒（板端往返）、界面 5 帧/秒，提到板端 **25.8 帧/秒**、界面 **25.5 帧/秒**。比特流和 PL 一点没动，结果与原通路逐位相同。

## 为什么慢

| 项 | 原通路（每帧） |
|---|---|
| 上行 | 512×512 RGB，分 512 行，每行带 CRC：789,504 字节 |
| 下行 | 统计块 + 掩膜图 + logit 图，各 786,432 字节：约 1.57 MB |
| 板端推理（128 档） | 37.7 ms |
| 往返 | 约 110–116 ms |

心超、皮肤等 128 档模型实际只用 128×128 的像素（板端 `[::4, ::4]` 取样），**每帧多传了约 2.3 MB**。时间主要花在网络和 PS 的拷贝上，不在 PL 上。

## 做了什么

1. **紧凑帧**（控制头 v6c，`"GM"`，16 字节）：头后面只跟模型要的 w×w 灰度或 RGB（128 档灰度是 16 KB），附 CRC。
   板端直接按 w 选分辨率档位跑整网，不经 PL 预处理和 DMA。回传也只有：
   - 统计块；
   - 可选的分块和块（b7）；
   - int8 logit（b8，16 KB）和 / 或位掩膜（b9，2 KB），各附 CRC。
2. **板端跟踪状态**（每个连接一份，`accept` 时清空）：
   - `track = 1`：板子把上一帧结果拼进 G 通道（B = 128，即 echo_seq 的编码），PC 只发灰度帧；没有状态时自动用 F1；
   - `track = 2`：先清状态；
   - `track = 3`：本帧按 PC 给的 RGB 跑，结果写回状态。点击纠错走这条：纠正后的结果写回状态，接着从这里往后传播。
3. **流水线**：PC 一次发多帧、不等回复，板端按顺序处理，TCP 缓冲让收下一帧和算这一帧重叠。服务端不需要多线程。
4. **界面**（`tcp_image_ui/sequence.py`）：
   - 自动探测：老板端不认 `"GM"` 头会断开连接，界面据此退回整幅帧通路；
   - 后台线程最多 2 帧在途；
   - 每次开始或继续时，第一帧把上一步结果显式拼好发出去（`track = 3`），重连后状态丢了也不会算错；
   - 轮廓用 Pillow 在 128 网格上计算，面积直接在 128 网格上算（0.4 ms，原来 6.2 ms），屏幕刷新和曲线重画都限频。

代码：板端 `src/tcp_image_server.c`（`receive_v6c`、`handle_v6c`）、`src/image_proto.h`（v6c 头、b8 / b9）；统计块升到 version 7。
上位机：`proto.pack_v6c`、`imagelink.send_v6c / recv_v6c / v6c_round_trip`、`sequence.py`。**`unet_ai.c` 没有改**（这个文件归负责 PL 优化的队友）。

## 速度（同一批帧，板端 v5.4，比特流 V9b 不变）

| 场景 | 原通路 | 新通路 | 提升 |
|---|---:|---:|---:|
| 心超 128 档，一帧一等 | 8.6 帧/秒 | 25.4 帧/秒 | 2.9× |
| 心超 128 档，2–4 帧在途 | — | 25.7–25.8 帧/秒 | — |
| 板端跟踪模式（3 帧在途） | — | 25.8 帧/秒 | — |
| **序列窗口（界面实测，300 步）** | 约 5 帧/秒 | **25.5 帧/秒**（屏幕刷新 21 次/秒） | 约 5× |
| 眼底 512 全分辨率 | 1.54 帧/秒 | 1.71 帧/秒（2 帧在途） | 1.11× |

- 128 档的上限由板端推理决定：37.7 ms，对应 26.5 帧/秒。新通路达到上限的 97%，再往上要靠 PL 提速（见 `pl_optimization_guide_2026-10-09.md`）。
- 512 档本身就是 PL 计算受限（564 ms），新通路只省掉了网络和拷贝的那部分。
- 流水线的提升很小（25.4 → 25.8）：**3 倍的提升几乎全部来自“只传需要的像素”**，每帧数据量从约 2.4 MB 降到 32 KB。

注意口径：“帧/秒”是板端真实完成计算并回到 PC 的结果数，不是播放帧率。CAMUS 原始帧率约 50–64 帧/秒，现在约是它的一半。
