# AI 识别耗时分解与优化方案

> 实测日期：2026-10-06　工程：`tcp_image_rx`　配置：512×512 全分辨率、`ai_sys` 比特流（256 KB 张量 BRAM）、`plbram.ko` 已加载
> 基线正确性：整网输出与 PLD golden **逐字节 0 / 262144 一致**（`ai/net/_prof_golden.log`），即下面所有耗时都是在"结果正确"的前提下测的。

## 0. 一句话结论

**最长的一步是"把每层输出从 PL 的 BRAM 读回 PS"——占 AI 阶段的 63%、整帧的 59%**，
而 CPU 读它的成本被硬件钉死在 **每次 16 B 访问 ≈ 198 ns（≈81 MB/s）、完全不流水**。

本轮做了两件事：
1. **把这个"墙"证死了**：加宽指令、NEON、多流交错、改映射属性，全都没用（NEON 反而慢一倍）。
   所以只有两条路：**减少访问次数**，或**换一个能发 burst 的主设备**。
2. **把第二条路走通了**：PS 自带的那 16 个 `xilinx-zynqmp-dma` 通道**能到达 PL 的 `0xB0000000`**，
   BRAM→DDR 读实测 **1290 MB/s（比 CPU 快 15.9×）**，整网 193 MB 搬运从 **1162 ms → 166 ms**，
   且逐字节校验 0 差异。**不需要改 BD、不需要改 HLS、不需要重出比特流。**
   做完这一项，整帧预期 **1768 → ~713 ms（−60%）**，此后瓶颈变成 `ap`（PL 计算，占 75%）。

按收益排序（模型量化 + 真机实测，详见第 5 节）：

| # | 方案 | 预期省 | 占 AI 段 | 工程量 | 风险 | 状态 |
|---|---|---|---|---|---|---|
| **1** | ⭐ **让 PS 自带的 GDMA 搬数据** | 实测省 **941 ms** | 53% | 中 | 低 | ✅ **已落地**（见第 8 节） |
| 2 | 去掉 bounce 那次 memcpy（DMA 直写张量） | ~90 ms | 5% | 中 | 中 | 待做（第 8.4 节） |
| 3 | PL 提频 101→148 MHz（**ap 现在是最大项，占 64%**） | ~167 ms | 9% | 小 | **高**（写 CRL_APB 可能挂死） | 待评估 |
| 4 | 计算/搬运重叠（把 289 ms 搬运藏到 532 ms 计算后面） | ~290 ms | 16% | 中 | 中高（并发访问 BRAM） | 待评估 |

**GDMA 探测的分阶段纪律**（因为这个探测"最坏情况会把板子挂死、要断电重启"）：
`gdmatest.ko` 用 `mode=` 参数分四档，一档一档 insmod：
`mode=0` 只做 DDR→DDR 自检（零风险）→ `mode=1` 读 BRAM 4 KB→64 KB→256 KB →
`mode=2` 写 BRAM + 回读校验 → `mode=3` 模拟 826 条带的真实工作量。
模块**故意在 init 末尾返回 `-ENODEV` 不常驻**，所以每档都能反复跑、不用 `rmmod`、也不会占着 DMA 通道。
实测**全程板子在线，没有需要重启**。

### 3.1 现在的关键比例

- **`ap` 一个人占 68%**，读回从 63% 掉到 16% —— **瓶颈已经从"搬运"转到"PL 算得慢"**。
- `get` 内部：**DMA 传输 88 ms + bounce memcpy 37 ms**。
  纯 DMA 是 1.29 GB/s（85.5 MB 只要 66 ms），多出的 ~22 ms 是每笔 ~25 µs 的固定开销
  （ioctl + `dma_map/unmap` + 完成唤醒）× 826 笔。
- `put` 108 ms **不要动**：同样走 DMA 会变成 162 ms（慢 54 ms），因为要先 memcpy 进 bounce，
  而 CPU 的 Normal-NC 写合并本来就是 1.08 GB/s。

## 4. ⭐ 本轮最关键的发现：读的成本被硬件钉死

### 4.1 微基准结果（`_prof_recon*.log`）

`_prof_recon3.py`，同一个循环里换"一条指令搬多少字节 / 发几条独立 load"：

| 读法（PL BRAM，Device 映射） | ns / 16B | MB/s |
|---|---|---|
| `ldp` 单条 16 B（= glibc memcpy 用的） | **198.2** | **80.7** |
| `ldp` ×4（64 B/轮，四条独立） | 199.4 | 80.3 |
| `ld1 {v0.16b}` 单条 16 B | 396.5 | 40.4 |
| `ld1` ×2 **独立** 32 B/轮 | 394.9 | 40.5 |
| `ld1` ×4 **独立** 64 B/轮 | 395.4 | 40.5 |
| `ld1` ×8 **独立** 128 B/轮 | 396.9 | 40.3 |
| `ld1 {v0-v3}` 单条 64 B | 394.5 | 40.6 |
| glibc memcpy（现用） | **197.8** | **80.9** |
| *（对照）普通可缓存堆内存 ld1 ×1 / ×4* | 7.7 / 5.1 | 2080 / 3154 |

`_prof_recon.py` 里还测了 2/4/8 路**地址交错**的读：`394.5 ~ 396 ns` 一模一样。
写侧：`Device 64 bit store = 79 ns/16B`、`st1 x4(64B) = 39.6 ns/16B`、**`Normal-NC 写 = 14.8 ns/16B = 1.08 GB/s`**。
映射属性对读**完全无效**：`/dev/mem`(Device) 与 `/dev/plbram`(Normal-NC) 读数逐位相同。

### 4.2 三条硬结论

1. **读 = 每次 16 B 访问 ≈ 198 ns 的纯延迟，不流水、不能重叠。**
   把 8 条**互不相关**的 16 B load 背靠背排在一起，耗时与 1 条完全相同 —— 这条通路从头到尾**只有一笔读在飞**（无 MLP）。
   所以"用更宽的指令搬更多字节"在**读**侧是白费：每次访问搬 16 B 还是 64 B，都收 198 ns 的账。
2. **NEON/AdvSIMD 的 load 在这条通路上比整数 `ldp` 还慢一倍**（395 vs 198 ns / 16 B）。
   —— 想用"一条 `ld1 {v0-v3}` 搬 64 B"绕过延迟的方案，**实测被证伪**。
3. **写侧是唯一"能 burst"的方向**：Normal-NC 写合并跑满 **1.08 GB/s**，说明 PL 互联通路本身带宽远高于 81 MB/s。
   ⇒ 读卡住不是带宽，是**单笔往返延迟且不允许并发**。这给第 5 节的方案 3/4（换 master / 用缓存行填充发 burst）留了口子。

### 4.3 因此：现有驱动已经到顶

`bram_get()` 用的正是 `memcpy`（= `ldp`），就是上表里最快的一档。
**软件层面再怎么改循环（NEON、展开、预取、多流）都不会更快** —— 这一点本轮已经用实验排除了，
以后再看到"用 NEON 加速搬运"的想法可以直接跳过。

### 5.1 各方案量化对比（512 全分辨率，**2026-10-06 GDMA 之后的新单价**）

```
S0 现状(GDMA + bounce)     | 读 5.3M字 124ms | 写 7.3M字 108ms | ap 531ms | 合计 763ms (1.3 fps)

S3 搬运与计算重叠(理想)      | 读 5.3M字 124ms | 写 7.3M字 108ms | ap 531ms | 合计 544ms | 省 220ms
S4 S1+S3 一起上            | 读 5.3M字  87ms | 写 7.3M字 108ms | ap 531ms | 合计 544ms | 省 220ms
S5 BRAM 加大到 ~344KB      | 读 5.3M字 118ms | 写 7.2M字 106ms | ap 531ms | 合计 756ms | 省   7ms
S6 HLS 改 16×int8/字       | 读 4.1M字  96ms | 写 5.4M字  81ms | ap 531ms | 合计 708ms | 省  55ms
S7 连 put 也走 DMA         | 读 5.3M字 124ms | 写 7.3M字 162ms | ap 531ms | 合计 817ms | 省 -54ms(更慢!)
```
> 模型与实测对得上：get 模型 123.7 / 实测 125.4 ms，put 108.2 / 108.3，合计 763 / 777（差 2%）。
> 读字数 5.3412M、条带数 826 与实测**逐位一致**。

**这张表最值得记的两件事**：
1. **`put` 走 DMA 是负收益（−54 ms）** —— 写侧 CPU 的 Normal-NC 写合并已经 1.08 GB/s，
   DMA 反而要先 memcpy 进 bounce。**不要动它**。
2. **`ap` 成了天花板**：S1~S7 里凡是只动搬运的，最多省 55 ms；
   只有"重叠"（省 220 ms）和"提频"（省 167 ms）能动到 `ap` 那条线。

> 下面 5.2 / 5.5 / 5.6 里"分组链式""可缓存映射"这些是 GDMA **之前**的分析，
> 结论仍然成立（都已标注"不做"），保留下来是为了说明当初的取舍依据；
> 但**它们的收益数字是旧单价下的**，GDMA 之后要按 1290 MB/s 重算，都会大幅缩水。

### 5.2 方案 4：分组层间链式（**原本首推，现已被方案 1 取代**）

> ⚠ **结论更新（2026-10-06 当日晚，GDMA 实测之后）**：这个方案的收益是"省下 3.60 M 字的**读**"，
> 按 CPU 的 198 ns/字算是 713 ms；但 **GDMA 把这些字读下来只要 ~48 ms**（58 MB @ 1.2 GB/s）。
> 所以做完方案 1 之后，链式的价值从 660 ms 掉到 **~60 ms**，而工程量（重写调度器 + halo 逐级传递）
> 一点没少。**→ 不建议再做**，除非哪天 DMA 路线被别的因素堵死。
> 下面保留原分析，作为"如果只能改软件、又不能用 DMA"时的备选。

**问题**：现在每个节点都是"补 halo → 写进 BRAM → 起 IP → 读回 PS"。同一份中间结果被搬了两趟。
**做法**：把**同一分辨率的整条支路**当成一组，组内节点串起来跑，中间张量**一直留在 BRAM 里**，
CPU 只在组头喂一次输入、组尾收一次输出。**PL 一行不改**——两个算子的 `in/out` 指针本来就是运行时参数，
让它们都指向 BRAM 内的不同偏移即可；`in_h/in_w` 也照样传（所以 halo 逻辑照旧）。

实测可成组的 7 组（`_prof_model.py` 自动算过 BRAM 是否装得下）：

| 组 | 节点 | 省下的读（字） |
|---|---|---|
| `first_block_2 → first_block_5 → first_shortcut_1 → add` | 4 | 786 432 |
| `down_path_0_block_2 → _block_5 → _shortcut_1 → add_1` | 4 | 393 216 |
| `down_path_1_block_2 → _block_5 → _shortcut_1 → add_2` | 4 | 196 608 |
| `up_path_0_conv_layer_block_2 → _block_5 → _shortcut_1 → add_3` | 4 | 393 216 |
| `up_path_1_conv_layer_block_2 → _block_5 → _shortcut_1 → add_4 → final` | 5 | 1 048 576 |
| `up_path_0_up_layer_block_0 → conv_bridge_block_2 → cat` | 3 | 262 144 |
| `up_path_1_up_layer_block_0 → conv_bridge_block_2 → cat_1` | 3 | 524 288 |
| **合计** | | **3 604 480（= 5.34 M 的 68%）** |

- 收益：3.60 M 字 × 198 ns = **713 ms 省读**，写侧净变化 +49 ms（模型偏悲观）→ **净省 ≈ 660 ms（39%）**。
- 成本：halo 逐级传递（3×3 链 K 个节点，组头要多喂 2K 行），条带高度受 BRAM 挤压。
- 工程量：**大**。要重写 `unet_ai.c` 的调度为"组 + 组内逐条带"，halo 行数按消费者需求倒推。
- 风险：**中**。halo 记账错一行就会整体错位（本工程 2026-10-01 就踩过"下移一行"）。
  必须用 `run_fullres.py` 的 golden 逐字节回归（0/262144）当验收线，并且逐节点都用现成的
  `vectors` 比对（30 节点 bit-exact 的那套）。
- 配套：BRAM 现在 192/216 块，若把张量窗口从 256 KB 加到 ~344 KB（还剩 24 块 RAMB36），
  链式组里的 buffer 会更宽裕、条带高度更大 —— **这是"加大 BRAM"唯一真正值得做的场合**。

### 5.3 方案 3：计算 / 搬运重叠（**做完方案 1 之后变小**）

- 现状：`get+put` 1400 ms 与 `ap` 531 ms **串行**。若能重叠，省 531 ms（30%）。
- **GDMA 之后**：搬运只剩 166 ms，重叠的对象变成"把 166 ms 藏到 531 ms 计算后面"，
  最多省 **~180 ms**（而且那时 ap 已经是主导项，重叠本身也变成顺手的事——
  DMA 本来就是异步的，`dma_async_issue_pending` 之后 CPU 可以直接去启动 IP）。
- ⚠ 但注意：**DMA 与 IP 并发访问同一片 BRAM** 很可能踩到与 A-ov 同一类的问题
  （见 [[zynqmp-concurrent-bram-access]]：CPU+IP 并发实测把数据搞坏）。
  安全做法是**用两块不重叠的 BRAM 区域做乒乓**，让"正在被 DMA 读的区域"和"IP 正在写的区域"物理分开。
- 旧结论（保留）：2026-10-02 实测"重叠版 1626 ms 但 253 787/262 144 像素错"，
  同布局只关重叠就 PASS → 根因在 PL 互联/BRAM 控制器对**并发访问**的处理。

### 5.4 ⭐ 方案 1：让 PS 自带的 GDMA 搬数据（**已实测跑通，首选**）

板上已有 **16 个 `xilinx-zynqmp-dma` 通道**（8 个 FPD GDMA @`0xFD500000`（128 bit）
+ 8 个 LPD ADMA @`0xFFA80000`（64 bit）），内核 `zynqmp_dma.c` L1141 注册了
`device_prep_dma_memcpy`。实测脚本/模块：`kmod/gdmatest.c`（板上原生编译，`ai/net/_gdma_test.py` 分阶段跑）。

**关键问题的答案：FPD GDMA 的主口能到达 PL 的 `0xB0000000`** ✓（这是之前唯一的未知，
一碰就挂死板子的那一步——这次没挂，板子全程在线）。

实测数据（`ai/net/_gdma_stage*.log`）：

| 测试 | 结果 | 校验 |
|---|---|---|
| DDR→DDR 256 KB（自检） | 73 µs → **3590 MB/s** | mismatch 0/262144 ✓ |
| BRAM→DDR 读 4 KB | 15 µs → 265 MB/s | |
| BRAM→DDR 读 8 KB | 17 µs → 475 MB/s | |
| BRAM→DDR 读 16 KB | 22 µs → 720 MB/s | |
| BRAM→DDR 读 32 KB | 34 µs → 951 MB/s | |
| BRAM→DDR 读 64 KB | 58 µs → 1120 MB/s | |
| BRAM→DDR 读 128 KB | 106 µs → 1228 MB/s | |
| **BRAM→DDR 读 256 KB** | 203 µs → **1290 MB/s** | **与 CPU 逐字对账 mismatch 0/65536** ✓ |
| **DDR→BRAM 写 256 KB** | 194 µs → **1346 MB/s** | 回读 0/262144（DMA）+ 0/65536（CPU）✓ |
| **真实条带模拟**：826 条带 ×（写 142 KB + 读 103 KB）= 193 MB | **166 286 µs = 166 ms** → 有效 **1218 MB/s** | |

**⇒ 同样这 193 MB，现在 CPU 要 1162 ms，GDMA 只要 166 ms —— 光这一项就省 ~996 ms**
（这是模块自己按 0.95 ns/B 写 + 12.3 ns/B 读算的对比；拿实测的 1221 ms 当基准还要多省一点）。
（读从 81 MB/s 提到 1290 MB/s = **15.9×**；写本来就是 1085 MB/s，只快到 1346 MB/s，1.2×。）

**为什么会快**：CPU 的读是"每次 16 B 一笔往返、不许并发"（第 4 节），而 DMA 是**另一个 AXI 主设备、能发 burst**，
把 198 ns 的往返延迟摊到了一整串 beat 上。写侧本来就靠写合并 buffer 攒出了 burst，所以反而没什么空间。

**新账（做完 1 之后）**：`ap 531 + 搬运 166 + zero/other 16 ≈ 713 ms`（从 1768 → **−60%**）。
再往后 **`ap`（PL 计算）变成最大项，占 75%**，所以第 2 顺位自然变成提频、而不是继续抠搬运。

**⚠ 实现上必须注意的三件事（不做就等于白做）**：

1. **必须把"逐行 memcpy"合并成"整条带一笔"**。现在 `unet_ai.c` 的 `bram_put`/`bram_get`
   是在**行的循环里逐行调用**的（`for (j…) bram_get(out_off + j*rout, …)`），一帧约 **2.5 万笔**。
   DMA 每笔有 **~12 µs 固定开销**（从尺寸扫描外推：4 KB→15 µs、256 KB→203 µs），
   2.5 万笔 × 12 µs = **300 ms**，会把收益吃掉一大半。
   好在条带内的行在源和目的两端都是**连续的**（`out_off + j*rout` 连续递增），
   合并成一笔是很直接的事；合并后 ~1650 笔 × 12 µs = 20 ms（上面 166 ms 的数就是这么算的）。
2. **张量内存要能被 DMA 安全访问**。现在张量是**用户态 `malloc` 的缓存内存**（85 MB）；
   DMA 往 DDR 写完之后，CPU 的 cache 里可能是旧数据。
   两条路：① 内核模块提供 `ioctl` 形式的 "DMA memcpy"，模块里 `get_user_pages` 把张量页**一次性钉住**
   （不要每笔都 pin），每笔前后按需 `dma_sync_single_for_cpu/for_device`；
   ② 把张量搬进模块持有的 coherent 区域再 mmap 给进程（更干净，但要 85 MB coherent 内存）。
   推荐 ①——改动小，且 CPU 从此**根本不碰张量字节**，所以张量内存的访问速度不再重要。
3. **`bram_zero`（补零行）也要走 DMA**：可以用一个预先清零的 DDR 缓冲做源，把若干尾行合并成一笔。

**不需要**：改 BD、改 HLS 算子、重出比特流、动 boot.bin。这是本次所有方案里唯一"**收益巨大 + 已验证 + 不碰 PL**"的。

**下一步落地路径**：把 `gdmatest.c` 里的 `gd_memcpy` 抽成 `plbram.ko`（或新模块 `plbdma.ko`）的一个 ioctl，
驱动侧把 `bram_put/bram_get/bram_zero` 三个函数换成 ioctl 调用 + 条带级批量化，
然后用 `run_fullres.py` 的 **0/262144** 当验收线（本工程 10-06 已两次跑过这条线，基线是可靠的）。

### 5.5 方案 6：把张量窗口映射成**可缓存**（**已被方案 1 覆盖，不必再做**）

> **结论更新**：这条路想解决的正是"读 81 MB/s"的问题，而 GDMA 已经把它解决到 1290 MB/s，
> 且**不需要碰 cache 维护**（DMA 目标用 coherent/钉住的页，风险低得多）。
> 可缓存方案要自己管 flush/invalidate、还要担心投机取巧越界挂死 → **不做**。

- 事实：可缓存内存的读写是 **4~8 ns/16 B（快 40×）**；而 `Normal-NC` 只帮写、不帮读（本轮再次确认）。
- 理论上：把 BRAM 映射成 Normal-WB 后，CPU 读会走**缓存行填充（64 B 一笔 burst）**，
  若 burst 有效（写侧已证明有效），读有望从 198 ns/16 B 降到 ~50-100 ns/16 B（2~4×）。
- 代价与风险：
  - 必须显式做 cache 维护（IP 写 BRAM 前 flush 输出区、IP 跑完 invalidate），且顺序错会**静默出错**；
    本工程已经有 `bram_commit()` 这个"写序保护"的先例，说明这类坑是真实存在的。
  - **投机取巧的边界风险**：缓存行填充/预取可能越过映射窗口读到没有从机的 PL 地址 → 挂死。
    窗口是 256 KB 且 4 KB 对齐，跨行风险低，但仍需谨慎设计（映射整块、不与窗口边界对齐）。
- 落点：`kmod/plbram.c` 增加一个 `cacheable=1` 模式 + `PLBRAM_SYNC` ioctl。

### 5.6 方案 5：HLS 算子改 16×int8/字（**做完方案 1 后收益大幅缩水**）

> **结论更新**：这个方案省的是"读的**访问次数**"，按 CPU 的 198 ns/次算是 265 ms；
> 但 GDMA 读一次 16 B 只要 ~12.6 ns，同样的字数只省 **~17 ms**。工程量却是最大的一档
> （改两个 HLS 算子的内存布局 + 重导 IP + 重出比特流 + 全链路 golden 重做）→ **不划算，不做**。

- 原理：现在一个字 16 B 装 8 个 16 bit lane（8 通道）。若改成 16 个 int8 lane，
  则 16/32 通道的层"每像素字数"减半（8 通道的层不变）。
- 模型：读 5.34 M → 4.15 M 字（省 265 ms，16%）；写量也降（写侧已带宽受限，收益小）。
- 代价：**最大的一档**。要改 `conv_layer.cpp` / `eltwise_layer.cpp` 的内存布局、
  重导两个 HLS IP、重出比特流、重做全部 golden 向量与整链路（本项目曾花两周才把 30 节点做到 bit-exact）。
- 另外 2 个节点本来是 INT16 精度，压成 int8 会掉精度。

### 5.7 方案 2/7/8：做完方案 1 之后才值得看的小杠杆

- **提频 101→148 MHz**：ap 531→364 ms（省 167 ms）。GDMA 之后整帧 ~713 ms，
  **ap 占 75%，所以这 167 ms 等于新帧的 23%** —— 相对价值反而变高了。
  但 PL 时钟由 FSBL/boot.bin 设定，加载 `.bit` 改不了；运行时写 `CRL_APB` 有挂死风险
  （本板掉线要断电重启），且 2026-10-01 试过"改 BD 约束提频"上板无效。**先不急**。
- **BRAM 再加大**：只影响输入侧 halo 写量，模型算 ~2%；而且写完要用 DMA 搬回来，
  意义更小了。**不做**。
- **降分辨率**：客户端 `aiparam` bits[4:2] 就是现成旋钮，512→256 整帧 2185→568 ms（**3.8×**）。
  精度换速度，看使用场景。这是**唯一零工程量**的办法。

## 6. 建议的执行顺序

1. **（可选，零工程量）先确认精度需求**：256 档够用的话今天就能拿 3.8×。

     （不合并的话 2.5 万笔 × 12 µs = 300 ms 会把收益吃掉一半）。
   - 验收线：`run_fullres.py` 的 **0/262144**（10-06 已跑过两次，基线可靠）+ 30 节点 bit-exact。

4. **方案 3（重叠）** 可作为第 3 步的备选：DMA 本身异步，把 166 ms 藏到 531 ms 计算后面最多再省 ~180 ms；
   但要小心 **DMA 与 IP 并发访问同一片 BRAM**（很可能和 A-ov 是同一类问题）→ 用乒乓的两块不重叠区域。
5. **不做**：分组层间链式、HLS int8 打包、可缓存映射、BRAM 加大（见 5.2 / 5.5 / 5.6 的结论更新）。

- **顺带修/踩的四个坑**（都写进代码注释了）：
  1. `pgrep -x tcp_image_server` 永远匹配不上——Linux 的 `comm` 只留 **15 字符**，实际名字是 `tcp_image_serve`，

     （`'-mgeneral-regs-only' is incompatible with floating-point argument`）。

     （代价是 shell 里 `insmod` 会返回非 0，日志里 `INSMOD_RC=1` 属正常）。
  5. **⚠ 运维坑（值得记住）**：部署脚本是 `make clean; make CC=gcc` 重编服务——
     **如果这次编译失败，`make clean` 已经把 `tcp_image_server` 删掉了，
     systemd 服务会进入 `activating` 重启循环**（板子上的业务就断了）。
     这次因为漏了一个 `now_us()` 的前向声明踩到了。**教训：改完先本地交叉编译 `-fsyntax-only`
     过一遍（`_prof_all.py check`），再去板上 `make clean`。**
  6. **GBK 控制台会打断脚本**：板上输出里的 `∘`/`µ` 之类字符会让 Python 的
     `print` 抛 `UnicodeEncodeError`，**整个脚本当场中断**。→ 脚本开头
     `sys.stdout.reconfigure(errors="replace")`，subprocess 也带 `errors="replace"`；
     板上 printf 一律用 ASCII。
  7. **崩溃+块缓冲 = 什么都看不到**：selftest 的 stdout 是管道（全缓冲），
     一崩就什么都不剩，看起来像"卡住了"。→ 用 `stdbuf -oL -eL` 跑，并且 `echo RC=$?`
     看返回码（139=SIGSEGV）。这次就是靠它才判断出"不是挂死而是崩了/算错了"。
- **基准测试要丢掉第一帧**：GDMA 之后第一帧比稳态慢 ~8%（842 vs 777 ms），
  差在 `bounce_memcpy`（冷页/冷 cache 时 94.8 ms，稳态 36.9 ms）。

## 9. 重叠优化（220 ms 那项）：做了、测了、**否决**

### 9.1 目标与做法

模型说"把 233 ms 搬运藏到 531 ms 计算后面"能省 220 ms。实现方式是把 BRAM 布局改成
**输入 2 块 + 输出 2 块**（`[in0][in1][out0][out1][params]`），条带循环改成软件流水：

```
每一轮:  收上一条带的输出(DMA) → 组装本条的输入 → 起本条的 IP
         其中"收上一条的输出"与"本条的 IP 计算"在时间上重叠
```
不改 PL、不改 HLS、不用出比特流；只需要同步版 ioctl（不需要异步 API）。
实验开关 `UNET_DBUF=1`，对照开关 `UNET_NOOVL=1`，代码都在 `src/unet_ai.c` 里。

### 9.2 三档对照（512 全分辨率，同一份代码只切开关）

| 配置 | 总时间 | golden |
|---|---|---|
| **A** 双缓冲布局 + **不重叠**（对照） | **891.2 ms** | ✅ `0/262144` **PASS** |
| **B** 双缓冲布局 + **重叠** | **781.7 ms** | ❌ `233879/262144` FAIL（logits 饱和 ±127） |
| C 32×32 + 重叠（回归） | 4.34 ms | ✅ `0/1024` PASS |
| （基线）单缓冲 + GDMA | 776.5 ms | ✅ `0/262144` PASS |

**A 全对 ⇒ 布局与流水记账没问题；坏就坏在并发本身。**

### 9.3 两个硬结论

**结论 1：PS 侧读 ∥ IP 写 = 坏数据（硬件级）**
这正是 2026-10-02 A-ov 翻车那类缺陷，只是当年是 **CPU∘IP**，这次是 **DMA∘IP**。

> ⚠ 中途我做过一个"并发探针"（`UNET_OVL_PROBE=1`）：在 `ap` 期间并发一笔 DMA 读并逐字节校验，
> 结果 **ok=114 / bad=0，整网 golden 还 PASS** —— 我当时据此判断"并发是安全的"，**这个判断是错的**。
> 因为探针读的是**输入区**（IP 只读它），测的是"**读∥读**"；
> 而真实场景里 DMA 读的是**上一段的输出区**、IP 同时在**写**自己的输出区，是"**读∥写**"。
> **教训：判并发要造出"读∥写"的场景，读∥读的通过说明不了问题。**

**结论 2：就算并发没问题，这个优化也是白做（≈ −5 ms）**

拆开看（A 与 B 相减）：重叠确实省了 **781.7 − 891.2 = −109.5 ms**；
但双缓冲布局把条带数从 826 抬到 **1809**，而 **IP 每次启动有约 100 µs 的固定开销** ——
多出来的 983 次启动要付 **+114.7 ms**。两笔相抵，净收益 **−5 ms**。

**"IP 每次启动 ~100 µs"是这轮最有价值的新数字**，用两组数据反推出来的：

```
826  条带 -> ap = 531.4 ms
1809 条带 -> ap = 675.4 ms
=> ap ≈ 61 ms x 输入百万字 + 0.102 ms x 条带数      (两点拟合, 与 32x32 档吻合)
```
所以模型里"ap 与条带高度无关"这个假设**只对了一半**：计算量确实与条带高度无关，
但**每次调用 IP 的固定开销**（参数加载 / 流水线填充 / 握手）是实打实按次数收的。
826 次调用 ≈ **84 ms** 纯开销，占 ap 的 16%。

**⇒ 反过来说，"条带数变少"是有价值的**：如果 BRAM 能装下更大条带（条带数 826 → 650），
ap 能省 ~26 ms；要到"每层一次调用"（30 次）才能省下全部 ~80 ms，但那要整层张量进 BRAM，做不到。

### 9.4 现状与后续

**已回退**：生产代码默认走单缓冲（`UNET_DBUF` 不设），实测 **776.5 ms、golden `0/262144` PASS**，
条带 826、搬运字数与之前逐位一致。实验路径保留在同一个文件里（`UNET_DBUF=1` 可复现）。

**这条路的解锁条件**是修 BD 层的并发（真双口让 CPU 口与 IP 口物理独立 / SmartConnect 高性能模式 /
BRAM 拆两块各挂一个控制器），而 A-ov 那次已经证明改 BD 也不保证有效。**性价比很低，建议放弃。**

**剩下的杠杆**（512 档 776 ms 里）：
| 杠杆 | 省 | 说明 |
|---|---|---|
| PL 提频 101→148 MHz | ~167 ms | ap 占 68%，这是最大的一项；但写 CRL_APB 有挂死风险 |
| DMA 直写张量（去掉 bounce memcpy） | ~37 ms | 干净、独立、可单独做 |
| 减少条带数（加大 BRAM 到 ~344 KB） | ~26 ms | 由"每次调用 ~100 µs"推出来 |
| ~~搬运与计算重叠~~ | ~~220 ms~~ | ❌ **实测否决**，见上 |

**⇒ 到这一步，AI 的时间已经基本被"PL 算得慢 + 每次调用的固定开销"锁死了。**
想再上一个台阶，就得动那个 HLS 算子本身（改并行度/流水），而不是继续在 PS 侧搬数据的方式上做文章。

## 10. 下一步：HLS 算子并行化（2026-10-06 开工，已量化 + 已试一版）

`ap` 就是那两个 HLS 算子跑的时间，所以这是剩下的唯一大杠杆。分析与实验都在
**`ai/opt_hls/`**（README 有完整过程），这里只摘结论。

### 10.1 瓶颈量化（`ai/net/_hls_analyze.py`）

把 30 个节点的计算量算出来，和每节点实测 `ap_us` 对账：

```
合计 2256 MMAC / 532.7 ms = 平均 41.8 MAC/周期
```

而综合报告显示 COMPUTE 主循环已经是 **II=1、每周期 64 MAC**（8 输出通道 lane × 8 输入 lane）
—— **流水线已经榨干，没有气泡可挖，只能"每周期多做活"**。逐档看谁值钱：

| 档 | MAC | 时间 | MAC/周期 | 占时 |
| --- | --- | --- | --- | --- |
| **3×3 conv** | 1868.6 M | **417.7 ms** | 44.1（峰值的 69%） | **78.4%** |
| 1×1 conv | 92.3 M | 48.3 ms | 18.9 | 9.1% |
| Add/Concat | 26.2 M | 43.4 ms | 6.0 | 8.2% |
| 转置 2×2 | 67.1 M | 17.8 ms | ~37 | 3.3% |
| MaxPool | 0.8 M | 5.5 ms | 1.4 | 1.0% |

资源现状（conv IP 综合报告）：**BRAM18 148/432、DSP 134/360、FF 18871/141120、LUT 29195/70560**。
整板（ai_sys）用掉 LUT 53% / DSP 57% → **LUT 与 DSP 都还有余量，FF 更是只用了 13%**。

**该选哪个方向加宽**（表格见 `ai/opt_hls/README.md`）：最贵的是 `wbuf` 那个 144 路权重 mux，
所以优先选**多个输出列（x）并行**——XU 个像素共享同一组权重，mux 不用加；
而最贵的几个节点恰好是 `cog=1, cig=1`（8→8 的 3×3），其他方向根本没得并行。

### 10.2 做出来的东西与验证

* `ai/opt_hls/src/conv_layer.cpp`：XU 参数化的并行版（接口/寄存器/内存布局/整数语义全不变）。
* **逐位等价性验证**：把 **PLD 原版一字不改**当参考实现（`tb/conv_layer_orig.inc`），
  同一份随机输入喂两个实现逐 int16 lane 比对 ——
  **25 个用例 / 737,695 个字 / 0 差异**（含 20 个真实层配置、3 个全尺寸、奇数宽度边界、relu/shift=0）。
  为什么能保证：累加是 mod 2^32 的整数加法（有结合律），并行只是把**互相独立的像素**放到同一拍算，
  没有改变任何单个像素的加法集合；requantize 逐字沿用。
* **XU=1 综合结果与 PLD 原版逐周期、逐资源一致**（40,943,870 周期 / DSP 135 / LUT 29646 / BRAM 148）
  → 这次重构本身零代价，是安全的基线。

### 10.3 两版 XU 并行化的实测结果

**第一版（给 BRAM 分 bank）⛔ 撞上工具级规模爆炸**：C 仿真逐位通过，但 csynth 出不来 ——
设计规模在 `Array/Struct` 阶段从 2,527 条指令**炸到 125,915 条**（50×），卡在调度阶段无报告。
两种写法都炸（`ARRAY_PARTITION factor`、把 bank 写进数组形状）。

**第二版（寄存器滑窗 line buffer）✅ 结构性障碍解决、但撞上资源墙**：
把 3 行滑窗搬进寄存器，数据仍由原 BRAM 每拍喂 1 列 ⇒ **不需要给 BRAM 分 bank**，
绕开了第一版的坑。"计算 / 补窗 / 存回上一步结果"放进同一个流水循环（DSP / BRAM 读口 / orow 写口互不冲突）。

| | 原版 | **XU=2（滑窗）** |
| --- | --- | --- |
| 设计规模（Array/Struct） | 2,527 条 | **6,996 条**（第一版是 125,915） |
| BRAM18 | 148 (34%) | 148 (34%)（**不用分 bank** ✓） |
| DSP | 134 (37%) | 227 (63%) |
| FF | 18871 (13%) | 43114 (30%) |
| LUT | 29195 (41%) | **57765 (81%)** |
| STEP 循环 | — | **II=2，Resource Limitation** |

**C 仿真逐位等价，一次通过**（25 用例 / 737,695 字 / 0 差异）。
**但 II=2 正好抵消"迭代数减半" ⇒ 吞吐没有净提升。**
原因：XU=2 让数据通路翻倍（2× MAC + **2× requantize**）+ 滑窗的运行时索引 mux，
整个循环体塞不进一个 10 ns 周期（流水级时序估计 6.62 + 2.70 ns ≈ 9.3 ns）。
LUT 81% 说明是 LUT 卡住的，最大消耗是 requantize（65/67 位 round-even + clamp ×8 lane ×XU 份）。

### 10.4 requantize 分拍（已做）：资源大幅改善，II 仍未下来

把 16 份 requantize 减到 8 份（`last` 只存累加器，requantize 挪到本步尾巴、每拍一个 `(u,cg)`）：

| | 原版 | XU=2(滑窗) | **XU=2(滑窗+requantize分拍)** |
| --- | --- | --- | --- |
| DSP | 134 (37%) | 227 (63%) | **128 (35%)** |
| FF | 18871 (13%) | 43114 (30%) | **32764 (23%)** |
| LUT | 29195 (41%) | 57765 (81%) | **46159 (65%)** |
| BRAM18 | 148 (34%) | 148 (34%) | 148 (34%) |
| STEP | II=1 | II=2 | **仍 II=2** |

✅ C 仿真逐位等价（25 用例 / 737,695 字 / 0 差异）；✅ DSP −44%、LUT −20%；
❌ **但 II 仍是 2 → 吞吐还是没有提升**。

**价值在于排除法**：STEP 流水级**自身**只用了 8409 LUT (11%) / 128 DSP (35%) / 0 BRAM 却仍报资源受限
⇒ **II 的瓶颈不是 requantize，也不是这一级的绝对资源量**，而在别处（最可能是"一拍内同时读 `rows`

## 8. 方案 1 已落地：实现与实测（2026-10-06）

### 8.1 结构

```
kmod/plbdma.c        -> plbdma.ko   /dev/plbdma   内核侧: bounce 缓冲 + DMA ioctl
kmod/plbdma.service               开机 modprobe(已 enable, 与 plbram 同一套路)
src/unet_ai.c        -> bram_get() 用户侧: 读回改走 GDMA
ai/net/_gdma_deploy.py             check / mod / golden / deploy / boot / quick 分步部署
```

**为什么中间隔一层 bounce，而不是让 DMA 直接写进张量**：
张量是进程 `malloc` 的，**物理不连续**，直接 DMA 要么拆成几十笔（每笔 ~25 µs 固定开销，亏死），
要么上 `get_user_pages` + sg 映射（复杂，且 cache 维护容易出错）。
隔一层之后：DMA 永远是一笔连续传输，cache 维护由 `dma_map_single/unmap_single` 包办，
代价只是多一次内存 memcpy。**这个取舍后面还有优化空间（见 8.4）。**

**`plbdma.ko` 干了什么**：
- 申请一块**物理连续**的 bounce 缓冲（`alloc_pages`，自动 order 9→6，本板拿到 **2 MB**）；
- 把它 **mmap 给用户进程（默认 vma_page_prot = 可缓存）** —— 用户态在它上面做 memcpy 很快；
- 两个 ioctl：`PLBDMA_IOC_INFO`（问大小/状态）与 `PLBDMA_IOC_XFER`（`{bram_off, len, dir}`，
  只做 "BRAM ↔ bounce" 这一段 DMA）；
- BRAM 一侧用 `dma_map_resource(dev, 0xB0000000+off, len, dir, 0)`，
  bounce 一侧用 `dma_map_single/unmap_single` —— **cache 维护就在这对函数里**：
  `DMA_FROM_DEVICE` 会 invalidate（用户态看得到 DMA 写进来的新数据），
  `DMA_TO_DEVICE` 会 clean（用户态刚写的脏行落回内存，DMA 才读得到）。
- `dir` 只支持 64 字节对齐的传输，且 `bram_off + len` 不能越过 256 KB 窗口。

**`unet_ai.c` 改了哪里**（只动"读回"这一条路）：
1. `unet_init` 里 `gdma_open()`：开 `/dev/plbdma`、`mmap` bounce；失败就打印一行原因并**自动退回 CPU**（`UNET_NOGDMA=1` 可强制对照）。
2. `bram_get()`：有 GDMA 就 `ioctl(XFER, dir=0)` + `memcpy(bounce→dst)`；任何一笔出错就**永久退回 CPU**（并打印一次原因）。
   `dst` 是可缓存张量，**DMA 从不直接写它** → 不存在任何 DMA/CPU 缓存一致性风险。
3. **把"逐行搬运"合并成"整条带一笔"**（CONV 与 ELT 两处循环）：条带内的行在 BRAM 侧和 PS 侧都是连续的。
   **这一步是必须的**：第一版忘了合并，`get` 只从 1113 ms 降到 325 ms；
   合并后降到 **181 ms**（每笔固定开销 ~25 µs × 约 1 万笔 = 260 ms 被省掉了）。
4. `put` / `zero` **故意不动**：8 KB 一行用 DMA 要 12 µs 固定开销 + 6 µs 传输 = 18 µs，
   而 CPU 靠 Normal-NC 写合并只要 7.6 µs —— **换过去反而更慢**。

### 8.2 实测

| 上位机 只算不传（noimage+stats） | 1771 ms | **827 ms**（824–832，3 帧） | 2.1× |
| 板端 AI 整网 | 1768 ms | **835 ms** | 2.1× |

| ├ `put`（写回，仍走 CPU） | 108 ms | 108 ms | — |

正确性：`run_fullres.py` → 32×32 档 `mismatch 0/1024 PASS`、512 档 **`mismatch 0/262144 PASS`**；

### 8.3 开机固化

`plbdma.ko` 已装到 `/lib/modules/<ver>/extra/` + `depmod`，并做了 `plbdma.service`
（`modprobe plbdma bram=0xB0000000 window=0x40000`，`enable` 且 `Before=tcp-image-server`）。
**没装模块也不影响功能**，只是读回退回 CPU（慢 6 倍）。

### 8.4 接下来还差什么（2026-10-06 复测后的排序）

现在的账（512 稳态）：**`ap 531（68%）+ get 125（16%，其中 DMA 88 + memcpy 37）+ put 108（14%）+ other 12`**。

| 方案 | 省 | 工程量/风险 | 判断 |
|---|---|---|---|
| **搬运与计算重叠** | **220 ms** | 要解决 DMA 与 IP 并发访问同一片 BRAM | 收益最大；先做可行性验证 |
| **PL 提频 101→148 MHz** | **167 ms** | 小，但写 `CRL_APB` 有挂死风险 | ap 是最大项，所以这 167 ms = 新帧的 21% |
| DMA 直写张量（去掉 bounce memcpy） | 37 ms | 中（张量要换成模块持有的连续可缓存区） | 干净的小改进 |
| HLS 改 int8×16/字 | 55 ms | 很大 | 从 265 ms 缩水到 55 ms → 不做 |
| BRAM 加大 / put 走 DMA | 7 ms / **−54 ms** | — | 都不做 |

- **重叠（首选，省 220 ms）**：现在搬运只占 233 ms、计算 531 ms，所以"藏"的收益上限就是那 233 ms。
  做法要么给张量 BRAM 拆出**乒乓的两块不重叠区域**（避免 DMA 与 IP 并发碰同一片 BRAM ——
  这正是 2026-10-02 A-ov 翻车的原因），要么先花半天验证"DMA + IP 并发"在这片 BRAM 上到底行不行。
  DMA 本来就是异步的（`dma_async_issue_pending` 之后 CPU 可以立刻去启动 IP），所以代码改动不大。
- **提频（次选，省 167 ms）**：**GDMA 之后 `ap` 已经是 68%**，所以提频的相对价值反而变高了。
  但 PL 时钟由 FSBL/boot.bin 设定，运行时写 `CRL_APB` 有挂死风险，建议单独找时间做、且先想好回滚。
- **DMA 直写张量（省 37 ms）**：把张量从 `malloc` 换成**模块持有的、物理连续的、可缓存**的区域
  再 mmap 给进程（不是 coherent，仍是可缓存，只是每笔前后做 cache 维护）→ DMA 直接落进张量，
  那次 36.9 ms 的 bounce memcpy 归零。注意稳态下它只值 37 ms（第一帧是 95 ms），所以优先级不高。
- **低分辨率场景的另一条线**：32×32 档整帧 45 ms 里 AI 只占 4 ms，
  剩下 41 ms 全是"TCP 收帧 23 + 展开 2.7 + 预处理 PL 往返 20"这些固定项。
  如果实际业务跑低分辨率，**该优化的是那趟 20 ms 的预处理 PL 往返**，不是 AI。
