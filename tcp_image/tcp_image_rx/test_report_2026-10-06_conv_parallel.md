# 测试报告 2026-10-06 —— conv 算子并行化（XU=2）

> 目标：把 HLS 里的 3×3 卷积改成并行结构，尽可能榨干资源、优化耗时；
> 需要随机读取的内容用 FF 而不是 BRAM。
> 范围：HLS 算子 → IP → 比特流 → **上板复测 ap**（全程真实执行，不是推演）。
> 完整推导与历代版本对比见 `ai/opt_hls/README.md` 第 4~8 节。

---

## 1. 一句话结论

**ap（PL 计算）531.99 ms → 354.17 ms，1.502×；整网板端 776.3 → 599.0 ms；
512 分辨率端到端 898.5 → 698.2 ms。golden 逐字节 0/262144 PASS。整板 BRAM 一块没多。**

---

## 2. 做了什么

原版 conv 的 COMPUTE 主循环**已经是 II=1、每周期 64 MAC**，流水线本身没有气泡可挖，
所以唯一出路是"每周期多做活"：**一拍并行算 2 个输出列（XU=2）**，两列共享同一组权重。

过程中挖出并解决了四个真问题（每一个都有 csynth 报告/实测支撑）：

1. **II=2 的真因不是 BRAM 分 bank，也不是 requantize，而是滑窗的读口。**
   `#pragma HLS ARRAY_PARTITION variable=win complete`（不带 `dim`）在
   Vitis HLS 2025.2.1 上**只切开了首尾两维**，中间两维被实现成 24 个 LUTRAM
   （storage report：`ram_2p`, bitwidth 16, depth 16）→ 每拍只有 1 读 1 写，
   一拍读 2 列就报 `Lower bound of II is 2`。

2. **"真 FF 滑窗"能修好 II，但代价不可接受。**
   逐维显式 complete 后 II 确实回到 1，但 384 个寄存器按运行时索引 `(ky,u+kx,ig)` 读
   要铺成 48 选 1 的 mux：STEP 自身 LUT 8409→22239，**整体 LUT 46159→72497（102%），装不下**。

3. **真正的吞吐瓶颈是"流水线每个 x 步都要重启"。**
   STEP 循环 iteration latency = 39~40 拍，而 3×3/cog=cig=1 时每步只有 9 次迭代
   → 每步排空重灌一次：`40+9·II` 拍算 2 个像素。原版是整行一条循环 41+4607 = 4648 拍/512 像素。
   ⇒ **XU=2 按老结构不但没提速，是比原版慢 2.7 倍**（这条推翻了上一轮"吞吐持平"的结论）。

4. **HLS 不跨循环共享硬件。** 试过"3×3 走新结构、1×1/转置沿用原版循环"，
   结果乘法器 128+96、requantize 出现 3 份副本 → **DSP 329（91%）/ LUT 72800（103%）**。
   必须所有模式共用一条循环。

**最终结构**（`ai/opt_hls/src/conv_layer.cpp`）：

* **整行一条流水线**：x 步展开成 slot，`[0,work)` 算、`[0,nfill)` 补窗、`[0,nq)` requantize+存回，
  `ncyc = max(work, nfill, nq)`（**重叠不相加**，后两者等于白搭在计算 slot 上跑），
  整行 `total = (nsteps+2)·ncyc`，prologue 只付一次。
* **滑窗 = 循环槽位 + A/B 双份 LUTRAM**：列索引走 RAM **地址**（不产生大 mux），
  存两份让 `u=0` 读 A、`u=1` 读 B（两块 RAM 各出一个读口，绕开 1R1W）；
  窗口宽 6 格、每步转 2 格，**用取模寻址代替移位** → 移位免费、滑窗零读改写，
  计算读的槽位与补窗写的槽位**天然不相交**，所以补窗能和计算同拍跑。
* 三种模式共用同一条循环；1×1/转置的窗口参数按模式取。

## 7. 第二轮（V10 / V11）：想把那 31% 的搬运折进流水线 —— **两版都上板实测，都更慢，废弃**

### 7.1 想法

第一轮之后每行还有 `LOAD(548)+init(48)+STEP(2365)+STORE(515)=3476` 拍，
其中 **1063 拍（31%）是纯搬运**。于是试了两个版本，都是把这部分做成 slot
（`ncyc = max(...)` 对 3×3/cog=cig=1 仍是 9，模型上"白搭"、一拍不多）：

* **V10**：预取（读 `in`）+ 回写（写 `out`）**都折进**计算流水线；
* **V11**：**只折回写**（纯写），预取仍是独立一趟（纯读），两个方向不混。

两版都通过了 csim 逐位等价与 csynth（STEP_ALL `II=1`），资源也都在预算内。

### 7.2 上板实测（同一块板、同一会话 A/B，每次烧录都回读 md5 确认换成功）

| | ap | golden | 整网 |
| --- | --- | --- | --- |
| **V9b**（三趟分开，交付版） | **353.7 ms** | 0/262144 PASS | 620.1 ms/帧 |
| V11（只折回写） | **539.2 ms（慢 1.52×）** | 0/262144 PASS | 802.8 ms/帧 |
| V10（读写都折） | **576.1 ms（慢 1.63×）** | 0/262144 PASS | 838.9 ms/帧 |

**三组数放一起就能定位**：V10 只比 V11 多慢 37 ms（那是"多折一个读"的代价），
而 V11 比 V9b 慢 185 ms ⇒ **代价来自"把 m_axi 访问折进计算流水线"本身**，
跟"读写混合"无关（那个假设被这组数据否掉了）。golden 全过，所以不是数据坏，是纯性能回归。

**⇒ 结论：本设计里 LOAD / COMPUTE / STORE 必须各自成环，不能折进同一条流水线。**

### 7.3 而且搬运这条路本来就到头了

**张量 BRAM 是单口**（`blk_mem_gen Single_Port_RAM` + `axi_bram_ctrl SINGLE_PORT_BRAM=1`），
每行至少 `512 读 + 512 写 = 1024 次访问 → 硬件下限 ≈1024 拍`。
V9b 实测 `LOAD(548)+STORE(515) = 1063` 拍，**已经贴着下限**（多出的只是流水线 prologue）。
合并成一条循环也不会更快 —— 访问次数没变，单口 RAM 一拍只能做一次访问。

**计算那侧也到顶**：`ncyc = work = 9·cog·cig`，一拍 2 像素 × 64 MAC = 128 MAC/拍；
再快只能上 XU=3（192 DSP），整板 DSP 会到 335/360 = 93%，超出当初留的余量。

### 7.4 这轮的事故（如实记录）

第二轮测试中板子被挂死过一次：脚本在 conv 核还有任务在跑（`ap_idle=0`）时就重编了 PL，
把 PS 的 AXI 互联挂死，整板 ping/SSH 全断；本机 JTAG 又看不到目标，**只能断电重启**。

已修并沉淀成规矩：`ai/net/_board_load_bin.py` 现在
① 编程前先 `systemctl stop tcp-image-server`；
② **读 CTRL 确认两个 HLS 核 idle，等不到就中止、不烧**；
③ 烧完回读板上文件 md5 与本地比对，打 `>>> LOAD_OK / LOAD_FAILED`
（这招还顺带抓到过一次"脚本在板上 Python 3.6 上崩了、其实根本没烧进去"的假数据）。

## 8. 最终结论与下一步

**交付版本 = V9b**（`bitstream/ai_sys_xu2_v9b.bin`，板上现在跑的就是它）：

| | PLD 原版 | **V9b（交付）** |
| --- | --- | --- |
| ap | 531.99 ms | **353.7 ms → 1.502×** |
| 整网（板端） | 776.3 ms | **599.0 ms → 1.296×** |
| 512 全回传（上位机） | 898.5 ms | **698.2 ms** |
| golden | — | **0/262144 PASS** |
| 整板 BRAM / DSP / LUT / WNS | 192 / 206 / 35.7K / +2.013 | **192（不变） / 271 / 46.5K / +1.819** |

**下一步真正有收益的两件事（都要另外开一轮、且都要重出比特流）：**

1. **把张量 BRAM 改成真双口**（`blk_mem_gen` → `True_Dual_Port`、`axi_bram_ctrl`
   `SINGLE_PORT_BRAM=0`）：RAMB36 本来就有双口能力、**块数不变**，双口后每拍 2 次访问，
   搬运可从 1063 砍到 ~550 拍/行 → **ap 354 → ~309 ms**。
   代价：动 BD（整个系统重出比特流）+ 重验 PS 侧通路。
2. **eltwise IP**（Add/Concat/MaxPool）占 ap 里剩下的 ~49 ms（13.8%）；
   它同样是搬运受限的，所以大概率也要等第 1 条的双口 BRAM 才能动。

**不建议做**：XU=3（DSP 超预算）、给 `rows` 加第 4 个行槽（BRAM 已 88.9%，是唯一紧的资源）、
以及任何"把 m_axi 折进计算流水线"的变形（本轮已实测否掉两版）。
