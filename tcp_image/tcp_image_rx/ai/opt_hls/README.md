# conv 算子并行化（XU = 每周期并行几个输出列）

## 0. 为什么要动这里

2026-10-06 把"读回"换成 GDMA 之后，板端 AI 整网 **1768 → 776 ms**，新的分解是：

```
ap（PL 计算）  531.4 ms  68.4%      <- 现在最大的项
get（读回）    125.4 ms  16.1%
put（写回）    108.3 ms  13.9%
```

`ap` 就是这两个 HLS 算子跑的时间。把 30 个节点的计算量算出来对账
（`ai/net/_hls_analyze.py`，数据来自 network.txt + 每节点实测 ap_us）：

```
合计 2256 MMAC / 532.7 ms = 平均 41.8 MAC/周期
```

而综合报告说 COMPUTE 主循环已经是 **II=1、每周期 64 MAC**
（8 个输出通道 lane × 8 个输入 lane）——**流水线已经榨干，没有气泡可挖**。
所以唯一出路是"**每周期多做活**"。逐档看谁最值钱：

| 档 | MAC | 时间 | MAC/周期 | 占时 |
| --- | --- | --- | --- | --- |
| **3×3 conv** | 1868.6 M | **417.7 ms** | 44.1 | **78.4%** |
| 1×1 conv | 92.3 M | 48.3 ms | 18.9 | 9.1% |
| Add/Concat | 26.2 M | 43.4 ms | 6.0 | 8.2% |
| 转置 2×2 | 67.1 M | 17.8 ms | ~37（本脚本对 tconv 的 MAC 估算偏高 4×） | 3.3% |
| MaxPool | 0.8 M | 5.5 ms | 1.4 | 1.0% |

**3×3 卷积一个人占 78%**，所以先动它。

## 1. 为什么选"并行多个输出列"这一维

conv IP 的综合报告（`ai/build/conv_ip/solution1/syn/report/csynth.rpt`）：

```
BRAM18 148 (34%)   DSP 134 (37%)   FF 18871 (13%)   LUT 29195 (41%)
COMPUTE   II=1, trip 73728, slack 0.12ns      <- 时序几乎顶死, 不能再往一条路径里塞逻辑
```

xazu3eg 全片：**70560 LUT / 141120 FF / 360 DSP / 216 RAMB36**。
整板（ai_sys 比特流）当时用掉 LUT 53%、DSP 57%，所以 **LUT 与 DSP 都还有余量**。

可选的"加宽"方向与代价：

| 方向 | 输入读口 | 权重 mux | 适用面 |
| --- | --- | --- | --- |
| 多输出列（x） | 要 XU 个读口（`rows` 按 x 分 bank） | **不增加**（XU 个像素共享同一组权重） | 全部卷积 |
| 多输出通道组（cg） | 不用加（输入共享） | **要 XU 倍**（wbuf 那个 144 路 mux 是大头） | 只有 cog≥2 的层 |
| 多输入通道组（ig） | 要 XU 个读口 | 要 XU 倍 | 只有 cig≥2 的层 |

**最贵的是权重 mux，所以选"多输出列"**：XU 个像素共享同一组权重，
`wbuf[tap][cg][ig][o][i]` 那个 mux 一份就够。而最贵的几个节点恰好是
`cog=1, cig=1`（8→8 的 3×3），cg/ig 方向根本没得并行——只有 x 能用。

实现代价也小：
* `rows[3][MAX_W][MAX_G][LANES]` 在 dim 2 上 **factor=XU 分割** → 相邻列落到不同 bank，一拍拿到 XU 个读口
* `orow[MAX_W][MAX_G][LANES]` 在 dim 1 上同样分割 → 一拍写 XU 列
* 累加器 `acc[XU][LANES]`，XU 组独立（**这才是真正的并行**，不是把依赖链展开）
* requantize 复制 XU 份（只在最后一个 tap 拍用到）

## 2. 正确性：为什么可以保证逐位一致

* 累加是 **mod 2^32 的整数加法**（`acc_t` = ap_int<32>），加法有结合律/交换律；
  并行只是把**互相独立的像素**放到同一拍算，**没有改变任何单个像素的加法集合**。
* 每个像素的 tap 遍历顺序、requantize（乘 M、加 offset、round-to-nearest-even、clamp）
  **逐字沿用原实现**，一行没改。
* 转置模式（mode 2）的 `tap = (y&1)*2 + (x&1)` 依赖输出列的奇偶：
  因为 x0 恒为偶数（out_w 恒为偶、步长 XU=2），所以 u=0/1 对应 tap 的 +0/+1，
  而且两列落在**同一个输入列**（`x>>1` 相同）→ 只发一次读，不占额外读口。
* 右边界多了个 `(x0+u) < out_w` 保护（宽度为奇数时最后一个 u 不写）。

## 3. 验证方法（不依赖 PLD 的向量生成）

`tb/` 里把 **PLD 原版算子一字不改**地当参考实现编译进来（只把函数名改成 `conv_layer_ref`，
原文件原样拷成 `tb/conv_layer_orig.inc`），然后**同一份随机输入同时喂给两个实现，逐 int16 lane 比对**：

```
tb/ref_conv_layer.cpp     #define conv_layer conv_layer_ref  ->  #include "conv_layer_orig.inc"
tb/test_conv_par.cpp      自己造输入/参数, 调两个实现, 逐字比对
```

跑法（主机）：`_run_hls.bat <XU> csim`

**用例覆盖**：20 个真实卷积层 (mode, cin, cout) 组合（尺寸缩小）+ 3 个**全尺寸**
（512×512 m0 8→8、512×512 m1 8→1、128→128→256 m2）+ 128×128 32→32
+ **奇数宽度**（31×33、16×17，专打 XU 的右边界）+ relu=0/shift=0。

### 4.3 第一版（给 BRAM 分 bank）⛔ 撞上 Vitis HLS 的规模爆炸

**C 仿真逐位通过，但 csynth 出不来。** 设计规模报告：

```
                        XU=1        XU=2
Compile/Link            3,043       3,045
Unroll/Inline           2,362       2,362
Array/Struct **        2,527     125,915   <-- 50 倍
```

`Array/Struct` 阶段（应用数组 partition 之后）把设计从 2,527 条指令撑到 12.6 万条，
`csynth` 随后卡在调度阶段十几分钟出不来报告。两种写法都试过都炸：
① `ARRAY_PARTITION variable=rows dim=2 factor=XU`；
② 把 bank 写进数组形状 `rows[3][XU][RW/XU][MAX_G][LANES]`（后者已保证读地址里没有 mux）。
**结论：只要给那片行缓冲要 2 个读口，这个版本的 HLS 就走 reshape 病态展开。**

### 4.4 ⭐ 第二版：**寄存器滑窗（line buffer）** —— 结构性障碍解决了

思路：**把 3 行滑窗搬进寄存器**（`win[3][XU+2][MAX_G][LANES]`，complete 展开）。
寄存器没有读口限制，一拍想读几列读几列；数据仍由原来那片 BRAM 每拍喂 **1 列**进来
——**完全不需要给 BRAM 分 bank**，所以绕开了 §4.3 那个坑。

每步三件事放在**同一个流水循环**里（资源互不冲突：BRAM 读口 / DSP / orow 写口）：
计算（`work = cog*kk²*cig` 次迭代，每次 XU 个像素）、补窗（`sft*krows*cig` 次列读）、
存回上一步的结果（`XU*cog` 个字，用 resA/resB 双缓冲避免和本步计算抢同一拍）。

**成果**：
* **C 仿真逐位等价，一次通过**：`SUMMARY cases=25 words=737695 failures=0`
* **设计规模回归正常**：Array/Struct 阶段 13,813 → 6,996 条指令（第一版是 125,915）
* **BRAM 148 (34%) 完全不变** —— 确实不需要分 bank

**但 XU=2 仍然拿不到加速**（`build/conv_par_xu2_w1/.../csynth.rpt`）：

| | 原版 | XU=1 | **XU=2（滑窗）** |
| --- | --- | --- | --- |
| BRAM18 | 148 (34%) | 148 (34%) | 148 (34%) |
| DSP | 134 (37%) | 135 (37%) | **227 (63%)** |
| FF | 18871 (13%) | 18875 (13%) | 43114 (30%) |
| LUT | 29195 (41%) | 29646 (42%) | **57765 (81%)** |
| STEP 循环 | — | — | **II=2，Resource Limitation** |

**II=2 把"迭代数减半"正好抵消掉了 → 吞吐没有净提升。**
原因：XU=2 让数据通路翻倍（2× MAC + **2× requantize**），再加上滑窗的运行时索引 mux，
整个循环体**塞不进一个 10 ns 周期**（该流水级的时序估计 6.62 ns + 2.70 ns uncertainty ≈ 9.3 ns，已经很紧）。
LUT 81% 说明它就是被 LUT 卡住的，而最大的 LUT 消耗是 requantize
（65/67 位 round-to-nearest-even + clamp，×8 lane ×XU 份）。

### 4.5 requantize 分拍（已做）：资源大幅改善，但 II 仍是 2

原来 `last` 那一拍要同时做 **XU*LANES = 16 份 requantize**（65/67 位 round-even + clamp），
是 LUT 最大的一坨，也在临界路径上。

**改法**：`last` 那一拍只把**累加器**存进 `raw[cg][u][o]`（切断"MAC→requantize"的长组合路径），
然后**在本步计算结束后的尾巴上**，每拍只对一个 `(u,cg)` 做 requantize
（`conv_layer.cpp` 里 STEP 循环后的 `(1b)` 段）。于是物理上只要 **LANES = 8 份** requantize。

> 中途先试过"延迟一拍、每拍一个 u"的写法：对 3×3（cg 间隔 9 拍）没问题，
> 但对 `cig=1` 的 1×1 卷积（cg 间隔只有 1 拍）会**互相覆盖 `raw`** → 2 个用例挂。
> 挪到"本步尾巴"之后就没有这个间隔约束了。**两个真 bug 记在这**：
> ① `pend_cg = cg` 写在计数器自增之后 → 记成下一个 cg（`cog=1` 时还越界写 `resA[.][1][.]`），
> 表现为**输出全 0**；② 上面的 `raw` 覆盖 → 表现为**一半通道错**。

**结果**（`build/conv_par_xu2_w5/.../csynth.rpt`）：

| | 原版 | XU=2(滑窗) | **XU=2(滑窗+requantize分拍)** |
| --- | --- | --- | --- |
| BRAM18 | 148 (34%) | 148 (34%) | 148 (34%) |
| DSP | 134 (37%) | 227 (63%) | **128 (35%)** |
| FF | 18871 (13%) | 43114 (30%) | **32764 (23%)** |
| LUT | 29195 (41%) | 57765 (81%) | **46159 (65%)** |
| STEP | — | II=2 | **仍 II=2** |

* ✅ **C 仿真逐位等价**：`SUMMARY cases=25 words=737695 failures=0`
* ✅ **requantize 瘦身确实有效**：DSP −44%、LUT −20%（57765→46159）、FF −24%
* ❌ **但 STEP 循环仍然是 II=2（Resource Limitation）→ 吞吐没有提升**

**⇒ 这一步把"requantize 是 II 瓶颈"这个假设排除了。** 关键证据：STEP 流水级**自身**只用了
**8409 LUT (11%) / 128 DSP (35%) / 7896 FF (5%) / 0 BRAM**，却仍报资源受限 ——
说明限制不在这一级的绝对资源量上，而在**别的约束**（最可能是访问/端口：
这一步里同时有"`rows` 读 + `orow` 写 + 窗口寄存器访问"，而原版是把 LOAD/COMPUTE/STORE
分成三个独立循环的，从来不需要一拍里同时读写行缓冲）。

**下一步排查方向**（按可能性）：
1. 把**补窗读 `rows`** 和**存回写 `orow`** 分到不同的拍（各自单独成循环，或错开奇偶拍）——
   如果 II 立刻回到 1，就证实是"一拍内同时读写行缓冲"的端口约束。
2. 把 `rows`/`orow` 用 `bind_storage` 明确绑到不同 BRAM，避免 HLS 合并资源池。
3. 看 `conv_layer_Pipeline_STEP_csynth.rpt` 里的 per-instance 表，找出具体哪个 operator 被复制/拆分。



### 4.6 V6a：把 `win` 换成真 FF —— II 修好了，但 LUT 爆了

按 §4.5 的排查方向①动手前，先回 storage report 把根因钉死：

```
p_ZZ...E3win_0_0_U | ram_2p | | | | | auto | 1 | 16, 16, 1
```

**`ARRAY_PARTITION variable=win complete`（不带 dim）在 Vitis HLS 2025.2.1 上只切开了第 1、4 维**
（3 行 × 8 lane = 24 个数组），中间两维 `(XU+2) × MAX_G = 4 × 4 = 16` 被实现成 **LUTRAM**
（`ram_2p`，每拍只有 1 读 1 写口）。XU=2 的 COMPUTE 一拍要读 2 列 → 只能 II=2。
**所以 II 的瓶颈就是滑窗的读口，跟 BRAM 分 bank、跟 requantize 都没关系。**

逐维显式 `complete dim=1..4` 之后（`src/conv_layer_v6a.cpp.txt`）：

| | V6 (w5) | **V6a（逐维 complete）** |
| --- | --- | --- |
| STEP II | 2 | **1** ✅ `Target II = 1, Final II = 1` |
| STEP 自身 LUT | 8409 | **22239** ❌ |
| 整体 DSP | 195 (54%) | 195 (54%) |
| 整体 FF | 32764 (23%) | 60368 (42%) |
| 整体 LUT | 46159 (65%) | **72497 (102%)** ❌ **装不下** |

**II 是修好了，但代价不可接受**：384 个真寄存器按运行时索引 `(ky, u+kx, ig)` 读，
要铺成 48 选 1 的 mux，STEP 自身 LUT 从 8409 涨到 22239。

### 4.7 真正的吞吐瓶颈：**流水线每个 x 步都要重启**

V6a 的报告里还有一条更容易被忽略、但更致命的信息：

```
| STEP | ... | Iteration Latency 39 | II 1 | ... |
```

**STEP 循环的 iteration latency = 39~40 拍**，而 3x3 + cog=cig=1 时它每个 x 步只有 **work = 9** 次迭代。
每进一个新的 x 步，这条 40 级流水线都要**排空再重灌**一次：

```
每步 40 + 9×II 拍算 2 个像素
      V6  (II=2) → 56 拍/2 像素 = 28 拍/像素
      V6a (II=1) → 49 拍/2 像素 = 24.5 拍/像素
原版：整行一条 COMPUTE 循环 41 + 4607 = 4648 拍 / 512 像素 = 9.1 拍/像素
```

⇒ **XU=2 这一路不但没有"没有净提升"，而是比原版慢 2.7 倍。**
（之前 §4.4/4.5 的结论"II=2 正好抵消迭代数减半 ⇒ 吞吐无提升"是**错的** —— 它只算了 II，
没算每步的流水线 prologue。这也解释了为什么它一直不敢上板。）

**结论：要提速就必须让流水线跨过整个 x 步区间，而不是每个 x 步一条循环。**

### 4.8 V8：两条路径分开 —— HLS **不跨循环共享硬件**

V8 的结构是"3x3 走新的 slot 流水线 + 1x1/转置沿用原版循环"。想法是 1x1 的 `work = cog*cig`
太小，塞进 slot 结构摊不开固定开销。结果：

| V8（两条路径） | DSP | LUT |
| --- | --- | --- |
| `Pipeline_STEP_ALL`（3x3，含 128 MAC + 1 份 requantize） | 160 | 19753 |
| `Pipeline_DIRECT`（1x1/转置，64 MAC + **另一份** requantize） | 96 | 14055 |
| 收尾用的第二份 requantize | 32 | 11754 |
| **整体** | **329 (91%)** ❌ | **72800 (103%)** ❌ |

**HLS 不会把两个循环里的乘法器/requantize 合并**，于是硬件直接翻倍。
这条路走不通，必须**所有模式共用一条循环**。

### 4.9 ⭐ V9（当前版）：全模式统一 + **循环槽位 LUTRAM 滑窗**

`src/conv_layer_v9.cpp.txt`（= `src/conv_layer.cpp`）。两个结构性改动：

**① 整行一条流水线。** 把 x 步展开成 slot（`k = 0..ncyc-1`），一个 slot 一拍：

| slot | 做的事 |
| --- | --- |
| `[0, work)` | 计算：第 k 个 `(cg,ky,kx,ig)`，一拍 XU 个像素 × 8 lane × 8 lane 个 MAC |
| `[0, nfill)` | 补窗：一拍读 `rows` 的**一行**，写进滑窗"下一格" |
| `[0, nq)` | requantize：读**上一步**的 raw；顺手用"读旧值"把**上上步**的 resA 写进 orow |
| 步末 | 只推进计数（相位/列号），**不占 slot** |

`ncyc = max(work, nfill, nq)` —— 三者**重叠**而不是相加，补窗和 requantize 等于"白搭"在计算 slot 上跑。
整行 `total = (nsteps+2) × ncyc`，prologue 只付一次（末尾多 2 步空转把最后两步的结果补写出去，
这样**只有一处 requantize**）。

**② 滑窗 = 循环槽位 + A/B 双份 LUTRAM。** 同时解决 §4.6 的读口和 LUT 爆炸：

* 列索引是 LUTRAM 的**地址**（不是寄存器选择）→ 不产生大 mux，LUT 便宜；
* 存 **A/B 两份**（内容恒相同），u=0 只读 A、u=1 只读 B → 两块 RAM 各出一个读口，
  不再撞 `ram_2p` 的 1R1W；
* 窗口宽 `WSN = 2·XU+2 = 6` 格，每步推进 `sft` 列，**用取模寻址代替移位**：

  ```
  逻辑列 c 在步 s 的物理槽位 = (c + sft·phase) mod WSN,   phase = s mod PER
  ```

  "移位"因此是**免费的**（只改 phase），滑窗**没有任何读改写**；
  计算读槽位 `{(0..KC-1) + sft·phase}`，补窗写槽位 `{(KC..KC+sft-1) + sft·phase}`
  —— 两组**天然不相交**，所以补窗与计算同拍跑，不需要 tail/双缓冲。

三种模式共用这一条循环（`PER` 与 `KC` 按模式取）：

| 模式 | krows | sft | KC | PER | 逻辑列 0 对应的输入列 |
| --- | --- | --- | --- | --- | --- |
| 0 (3×3) | 3 | 2 | 4 | 3 | `2s-1` |
| 1 (1×1) | 1 | 2 | 2 | 3 | `2s` |
| 2 (转置) | 1 | 1 | 1 | 6 | `s`（两个输出列对应同一输入列 → 都读逻辑列 0） |

**结果**（`build/conv_par_xu2_v9b/solution1/syn/report/csynth.rpt`）：

| | PLD 原版 | V6 | V6a | V8 | **V9b** |
| --- | --- | --- | --- | --- | --- |
| STEP II | 1 | 2 | 1 | 2 | **1** ✅ |
| BRAM18 | 148 (34%) | 148 | 148 | 148 | **148 (34%)**（**一点没涨**）|
| DSP | 134 (37%) | 195 | 195 | 329 | **198 (55%)** |
| FF | 18871 (13%) | 32764 | 60368 | 48253 | **46168 (32%)** |
| LUT | 29195 (41%) | 46159 | 72497 | 72800 | **49410 (70%)** ✅ |

* ✅ **C 仿真逐位等价**：`SUMMARY cases=25 words=737695 failures=0`（三种模式、奇数宽度、全尺寸都在内）
* ✅ **整行一条 II=1 的流水线**：iteration latency 44，3×3/cog=cig=1 时每行
  `ncyc = max(9, 6, 2) = 9`、`total = 258 × 9 = 2322` 次迭代 → `44 + 2321 = 2365` 拍/行，
  原版同一条行是 `4648` 拍
* ✅ **BRAM 一块没多**（这是整板最紧的资源，只剩 24 块 RAMB36）

**中途踩到的两个真坑（都写进代码注释了）**：

1. **补窗一拍读 3 行 → II=2。** 我想省拍数，让补窗一拍同时读 `rows` 的 3 行（3 块独立 BRAM，理论上各有一个读口），
   但 row 槽位 `sl=(iy+6)%3` 是**运行时索引**，HLS 证明不了 3 条 load 落在不同分片 → 报 3 条 load 撞同一个
   `rows_0_0`。摊成"一拍读 1 行"（token 数 3·XU·cig = 6）后 II 回 1，而且因为 `6·cig ≤ 9·cog·cig` 恒成立，
   **`ncyc` 一点没变，等于免费**。
2. **`nq ≥ work` 时 requantize 读到被覆盖的 raw。** requantize 读的是**上一步**的 raw，
   而计算在**本步**的 slot `work-1` 写 raw；`nq ≥ work` 时 requantize 的 slot 段会盖过那次写入。
   3×3 因为 `work = 9·cog·cig > nq = 2·cog` 恒成立没暴露，**1×1 的 cog=cig=1（work=1, nq=2）直接挂**——
   csim 一次报 7 个 FAIL，而且失败集合精确等于 `nq ≥ work` 的配置。
   修法：raw 做成**两份按 `s&1` 轮转**（写 `raw[s&1]`、读 `raw[(s+1)&1]`），物理上就是不同的寄存器组，
   无论谁大都不冲突。

## 8. V10（当前版）：把 LOAD / STORE 也折进流水线

### 8.1 动机：V9 每行还有 31% 的拍数花在纯搬运上

V9 上板实测 ap = 354.17 ms，但每个输出行的拍数是

```
LOAD(548) + 滑窗init(48) + STEP_ALL(2365) + STORE(515) = 3476
```

其中 **1063 拍（30.6%）** 既不算 MAC 也不 requantize —— 纯粹是把数据在
"m_axi ↔ rows BRAM" 和 "orow BRAM ↔ m_axi" 之间搬。

### 8.2 做法：折成 slot，靠 `max` 重叠，**一拍都不多**

V9 已经有一套 slot 机制（`ncyc = max(work, nfill, nq)`）。V10 只是往里再加两段：

| slot | 做的事 |
| --- | --- |
| `[0, work)` | 计算 |
| `[0, nfill)` | 补窗（一拍读 rows 一行） |
| `[0, nq)` | requantize（上一步的 raw）+ 存回 orow（上上步的 resA） |
| `[0, nload)` | **预取**：m_axi 读 1 个输入字 → 写 rows |
| `[0, nst)` | **回写**：orow 读 1 个字打包 128bit → m_axi |

`ncyc = max(work, nfill, nq, nload, nst)`。对 3×3/cog=cig=1 是
`max(9, 6, 2, 2, 2) = 9` —— **和 V9 完全一样**，也就是说这两段是"白搭"在计算 slot 上跑的。

每行拍数 `3476 → 48 + (52 + 2330) = 2430`，**再省 30%**。

### 8.3 唯一真正的难点：预取要"落后填充 2 列"

`rows` 只有 3 个行槽，而当前输出行要用满 3 行，**没有空闲槽给预取**。
但窗口是**逐列前进**的：预取目标行 `y+2` 的槽位 `(y+2)%3` 正好等于**正在退役的行 `y-1`**
的槽位，而第 s 步的填充只读该行的第 `s·sft+3`、`s·sft+4` 列。
所以只要预取**只写第 `s·sft`、`s·sft+1` 列**（落后 2 列），就永远不会碰到还没读的列：

```
读第 c 列发生在第 (c-3)/sft 步；写第 c 列发生在第 c/sft 步 —— 读一定早于写。
```

而且这样刚好铺满：`nsteps × sft = 512` 列，一步不浪费。转置模式下 `base_row` 连续两行相同，
用 `pf_row` 去重避免重复搬运。

### 8.4 另一处：回写落后 3 步

`orow` 是由 requantize 写进去的（而 requantize 本身又落后计算 1 步），所以回写必须再落后
3 步才能读到最终值；行尾因此多跑 `ST_LAG = 3` 步空转（compute/fill/prefetch 用 `s < nsteps`
挡住），把最后 3 步的结果补写出去。

### 8.6 ⛔ 上板实测结果：V10 **不能用** —— 慢 1.63 倍

V10 把预取（m_axi **读** `in`）和回写（m_axi **写** `out`）折进了同一条流水线，
**conv 会同时读写同一片张量 BRAM**。上板实测（同会话 A/B，golden 都加载成功并逐字节比对）：

| | ap | golden | 整网 |
| --- | --- | --- | --- |
| **V9b**（读写分处两趟） | **353.8 ms** | 0/262144 PASS | 619.5 ms/帧 |
| **V10**（读写折进同一趟） | **576.1 ms（慢 1.63×）** | 0/262144 **PASS** | 838.9 ms/帧 |

**注意 golden 是过的** —— 所以这次不是"坏数据"，是**纯性能回归**。
逐节点看：所有卷积节点慢 1.3~2.05×，eltwise 节点 1.00× 不变（走另一个 IP）。

**对账**：每行张量 BRAM 至少 1024 次访问（512 读 + 512 写）；V10 实测每行 ≈8497 拍
⇒ **方向混在一起时每次访问 ≈ 8 拍**；而 V9 里"纯读一趟""纯写一趟"都是 **1 拍/字**。

**⇒ 硬约束：这块板上对张量 BRAM 的读和写必须按长阶段分开，不能交错。**
这条和本板既有实测（`docs/ai_latency_breakdown_and_optimization.md` 第 9 节：读∥写会坏数据）是同一件事的
两种表现 —— 轻则慢 8 倍，重则数据坏。

### 8.7 V11：**只折回写** —— 上板实测**也慢 1.52 倍**，同样废弃

V11 把回写折进计算 slot（纯写），预取仍是独立的一趟（纯读），方向是分开的。
上板实测（同会话 A/B）：

| | ap | golden |
| --- | --- | --- |
| **V9b**（LOAD / COMPUTE / STORE 三趟分开） | **353.7 ms** | PASS |
| V11（只折回写） | **539.2 ms（慢 1.52×）** | PASS |
| V10（读写都折） | **576.1 ms（慢 1.63×）** | PASS |

**把三个数放在一起就能定位**：V10 比 V11 只多慢 37 ms（那是"多折一个读"的代价），
而 V11 比 V9b 慢 185 ms ⇒ **真正的代价是"把 m_axi 访问折进计算流水线"这件事本身**
（哪怕只有写、哪怕方向不混）。这与"混合读写"无关 —— 那个假设被这组数据否掉了。

**⇒ 结论：本设计里 LOAD / COMPUTE / STORE 必须各自成环，不能折进同一条流水线。**

### 8.8 那还有没有别的路？—— 搬运已经贴着硬件下限了

算一下就知道为什么折进没用、合并不可能更快：**张量 BRAM 是单口**（`blk_mem_gen`
`Single_Port_RAM` + `axi_bram_ctrl SINGLE_PORT_BRAM=1`），每行至少

```
512 读（输入 8KB）+ 512 写（输出 8KB）= 1024 次访问  →  硬件下限 ≈ 1024 拍
```

而 V9b 实测 `LOAD(548) + STORE(515) = 1063` 拍 —— **已经贴着下限**（多出来的只是流水线 prologue）。
把两趟合并成一条循环也不会更快：总访问次数没变，单口 RAM 一拍只能做一次访问。

**唯一能真正解锁的是把张量 BRAM 改成真双口**（`blk_mem_gen` → `True_Dual_Port`、
`axi_bram_ctrl` `SINGLE_PORT_BRAM=0`）：RAMB36 本来就有双口能力，**块数不变**
（见 `docs/fpga_resource_utilization.md`），双口后每拍 2 次访问 → 搬运可以砍到 ~550 拍/行，
`ap 354 → ~309 ms`。代价是要动 BD（整个系统重出比特流）并重验 PS 侧通路。

**计算那一侧也已经到顶**：`ncyc = work = 9·cog·cig`，一拍 2 个像素 × 64 MAC = 128 MAC/拍。
再快只能上 XU=3（192 DSP）—— 整板 DSP 会到 335/360 = 93%，超出当初留的余量，所以没做。
