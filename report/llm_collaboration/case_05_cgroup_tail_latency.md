# 案例 05：提高优先级后尾延迟仍高——cgroup 调度组

## 背景

要证明 FPGA 方案"延迟确定"，必须在 CPU 满载时测尾延迟（P99）。10-16 的性能工作中已经给板端服务加了 `Nice=-20`（最高普通优先级）。

## 模型回答与纠错轨迹

**1. 最初的判断：优先级不够**。10-16 测得 4 核满载时 512 整网从约 470 ms 涨到 899 ms，`nice -20` 能恢复到 469.5 ms，
于是在服务的 systemd 配置里加了 `Nice=-20` 并随 v5.17 部署。

**2. 部署后复测发现不对**：由 ssh 启动的压力程序仍能把已部署的服务拖慢（P50 / P99 = 604 / 1105 ms）。
模型没有继续调优先级，而是查调度结构，结论（记入项目记忆，原文英文）：

> Loaded-latency catch: deployed server under ssh-started hog still slow ... because cgroup v1 cpu: server in /system.slice, ssh in /user.slice, equal shares → nice only works inside a slice.

也就是说：Nice 只在同一个调度组内部起作用，服务和压力程序分在两个调度组里，份额相等，所以 Nice 管不到。

**3. 把这个问题和"能不能讲确定性"联系起来，交给用户决定**（10-20，原文）：

> **要先修一个问题：** 现在部署的服务在满载时 P99 会到 **183.8 ms**。原因是服务和 ssh 起的负载被系统分在两个调度组里，Nice 优先级管不到。修法是给服务单独一个高份额的调度组，需要你同意后再部署一次。不修的话，"确定性"这一条在部署的服务上讲不出来。

**4. 用户同意后，先测基线、再修复、再按同样条件复测**（原文）：

> 基线测完了：128 档空载 P99 是 22.11 ms，CPU 满载时 P99 升到 95.3 ms，内存满载时升到 173.5 ms。现在应用 slice 修复，然后用同样的条件再测一次。

> slice 修复见效了：CPU 满载下 128 档 P99 从 95.3 ms 降到 27.8 ms，内存满载下从 173.5 ms 降到 47.3 ms。

## 结果与证据

- 服务运行在独立的 `tcpimage.slice` 中，此后所有版本沿用；
- 证据：`perf_j/`、交接文档 §9.78。

## 沉淀

`skill/pitfalls.md` 第 3 条。教训：一项优化"在测试程序里有效"不等于"在部署形态下有效"，必须按部署形态复测。
