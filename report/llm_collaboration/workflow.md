# 智能体工作流设计

整个作品是在与 Claude Code 的长期协作中完成的。项目周期六周、对话数十次，每次对话的上下文都有限，
所以工作流设计要解决的核心问题是：**让每一次新对话都能接上前面的进度，而且不重复犯错**。

## 1. 三层"记忆"

| 层 | 载体 | 内容 | 谁来更新 |
| --- | --- | --- | --- |
| 持久记忆 | Claude Code 的记忆目录（每条一个文件 + 一个索引） | 板子当前固件和服务端版本、回滚目标、已用过的测试集、踩过的坑、用户的偏好（例如"全部用中文回复"） | 模型在每个阶段结束时更新；发现旧记录错了就直接改正 |
| 交接文档 | `tcp_image/tcp_image_rx/progress_and_handoff.md`（按 §9.x 编号，至 §9.85） | 每次上板的哈希、回滚方法、改了哪些文件、验收结果、已知差异、还欠的事 | 每次部署后新开一节 |
| 新对话提示词 | 写给下一次对话的开场提示 | 目标、必须先读的文件、已经确认的事实、禁止事项 | 开新对话前由模型起草，人审阅 |

新对话提示词的一个实例（10-07，开新对话做皮肤镜分割之前，由模型起草，节选，已脱敏）：

> 这个对话想评估并（如果可行）实现：**用同一套 FPGA 硬件、只换权重，做 ISIC 2016 Task 1 皮肤镜病灶分割** ……
>
> ## 先读这些（不要从头摸索）
> - `progress_and_handoff.md`：板端系统的总交接（§3.8 现状、§9.10.4 换权重 ……）
> - `deployment_decision.md`、`integer_spec.md`、`mixed_precision_spec.md`：现在的模型、量化规则、混合位宽
>
> ## 已经确认的事实
> - **换任务不用动比特流**：网络结构写在层表 `network.txt`，权重和重缩放参数由 `gen_unet_c.py` 编进板端程序 ……
> - **前提是网络结构与现在完全相同** …… HLS 核的硬限制：每层输入 / 输出通道 ≤ 32 ……

"已经确认的事实"一节的作用是**防止新对话推翻已经验证过的结论**，例如"int8 打包已被证伪，不要再提"。

## 2. 并行子任务

耗时长、互不依赖的工作拆给并行的子对话。例如 10-17：一个对话做 PL 提频（F），另一个对话在板上做性能测量（J3）。
J3 在测量中发现板上 PL 实际时钟与 F 的设计假设不符，F 对话随即按实测时钟重做了时序检查（见案例 01）。
子对话之间不共享上下文，只通过交接文档和记忆传递结论，这也迫使每个结论都要写成可独立阅读的文字。

## 3. 上板操作的固定流程

所有改动板子状态的操作都按同一个模板执行，并且由人逐次批准：

1. 模型给出方案、影响范围和**回滚路径**；
2. 人批准（例如下面的提示词）；
3. 模型执行：先备份 → 部署 → 自动验收 → 任何一项失败就自动回滚；
4. 写交接文档一节、更新记忆。

用户批准上板时的一条原话（10-24）：

> 同意上板：prepare 编译 → 先跑心超模式 0/1 的老回归 → verify_board_echo_kf.py → 都通过再 activate 为 v5.21（回滚 v5.20），交接文档新开一节。

## 4. 测试集只评一次

开发期间所有阈值只在 VAL 上定；最终评测前写预注册文件（33 个文件的 sha256），每个测试集评一次后写锁文件，
评测脚本发现锁文件就拒绝再跑。这条规则写进了持久记忆："No test set may be re-evaluated or used for tuning."

## 5. 反复使用的提示方式

| 提示方式 | 用途 | 例子 |
| --- | --- | --- |
| **先给证据再改代码** | 防止模型凭猜测修改 | "先读日志 / 寄存器 / 报告，说明判断依据，再动手" |
| **每一步先写回滚路径** | 上板与发布前的必要条件 | 见上面的上板提示词 |
| **只接受逐位一致** | 量化、HLS、板上 C 的验收 | "主机参考和板上逐位一致才算通过" |
| **用另一组数据交叉检查** | 发现隐藏的错误假设 | 案例 01：加速比与时钟倍数是否一致 |
| **把结论写成能独立阅读的交接** | 跨对话传递 | 每次部署后"交接文档新开一节" |
| **有疑问就停下来问** | 不可逆操作、医学口径、对外发布 | 公开仓库前确认数据集和权重的范围（案例 07） |
