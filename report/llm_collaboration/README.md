## 每个案例的写法

- **背景**：当时在做什么。
- **提示词**：用户发给模型的原话（引用块）。
- **模型回答**：模型当时的关键判断，摘录原文；原文为英文的保留英文。
- **纠错轨迹**：哪里不对、怎么发现的、怎么改的。
- **结果与证据**：最终数字和仓库中的证据文件。
- **沉淀**：提炼成了 `skill/` 中的哪一项。

所有引文只做了脱敏处理（人名、学校、主机名、口令、本机用户路径替换为说明文字），没有改动内容。

## 共同的教训

1. **先看现场再动手**：案例 04 中，在没看到板子状态时给出的"整卡重写"方案会丢掉两周的部署；看清现场后只需要换一个文件。
2. **用独立的数据交叉检查结论**：案例 01 靠"加速比与时钟倍数是否一致"发现时钟错误；案例 03 靠"主机参考与板上逐位比对"发现两处问题。
3. **不可逆的操作一律先确认**：部署、换比特流、公开发布都在人确认之后才执行；每次都先写好回滚路径。
4. **把一次性的发现固化成脚本或规则**：每个案例结束时都把原因写进交接文档和持久记忆，能自动化的做成检查脚本，避免同一个坑踩第二次。
