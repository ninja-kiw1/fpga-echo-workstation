# 案例 07：整理本公开仓库

## 背景

11-03 用户要求把项目公开到 GitHub，随后又要求按 AMD 选题指南（3.3 自主选题赛道）的提交要求重新整理。
项目目录约 21 GB，其中有多个使用条款不同的医学数据集（EchoNet-Dynamic 禁止再分发；CAMUS、HMC-QU 等仅限非商业使用）。

## 提示词

> 整理相关文件，然后上传至github公开

> 为什么放了这么多版本，不太美观吧

> 按照这里面的要求重新上传github（附选题指南 PDF）

## 模型回答与纠错轨迹

**1. 发布前先审计，并把决定交给用户**。模型发现沿用队友打包规则会发布 11 GB，其中包括根目录下 7 GB 的 EchoNet-Dynamic 压缩包——
这是原打包规则的漏洞，队友包下次重建时也会带上它。模型修正了打包规则，并在发布前就四件事征求用户意见：
发布范围、是否立即公开、竞赛文档是否放、仓库名。

**2. 逐类排查数据泄漏风险**：

- 扫描所有文本文件，查找 EchoNet 视频编号与标签字段同时出现的文件，找到一份含 1,101 段验证视频逐段 EF 误差的表（误差 = 预测 − 专家标注，可反推标注），排除；
- 逐张查看结果图，排除了两张由 HMC-QU、CardiacUDA 原始帧拼成的图；保留的 CAMUS / MSD / ISIC / 眼底图在 README 中注明出处；
- 用 EchoNet 训练的权重（16、21、22 号）最初排除；用户随后明确要求"把权重也加上"，于是加入，并在 README 和 LICENSE 说明中写明仍受数据集条款约束。

**3. 自己写的规则自己又踩了坑，逐个修正**：

| 问题 | 如何发现 | 修正 |
| --- | --- | --- |
| Vitis 导出文件带只读属性，第二次重建时删除失败 | 重建脚本报 `PermissionError` | 删除前清除只读属性 |
| 图片白名单让 HLS IP 的 `logo.png` 绕过了"只保留当前版本"规则，11 个旧 IP 目录只剩图标却出现在仓库里 | 重建后列目录，与预期对比 | 白名单只决定图片是否保留，不再越过其他规则 |
| 从原工程复制来的 `.gitignore` 让 29 个本该公开的文件被忽略 | `git ls-files --others --ignored` 检查 | 公开版不带原工程的 `.gitignore`；第三方目录自带的忽略规则用强制添加处理 |
| 只改大小写的重命名在 Windows 上 git 识别不到 | 文件名检查脚本仍报 520 个旧名 | 重建索引（`git read-tree --empty`）后再添加 |
| 在 MIT 正文后追加了说明，GitHub 识别为 `NOASSERTION` | 查询仓库的协议字段 | LICENSE 只放标准 MIT 正文，说明移到 README |

**4. 按指南改名时保护可复现性**：指南要求文件名只用小写英文。HLS 导出的 IP 内部文件名由工具生成、带大写，直接改名会使 IP 无法使用。
模型的处理是只保留官方导出的 IP 压缩包，并提供解压脚本；改名后，引用这些文件的脚本与文档同步替换，并用 `skill/check_repo_names.py` 检查结果为 0 个违规。

## 结果与证据

- 本仓库：3600 余个文件，约 180 MB，全部名字合规，协议识别为 MIT；
- 生成脚本 `make_github_release.py` 记录了全部排除规则及其原因，可重复执行。

## 沉淀

`skill/check_repo_names.py`；`workflow.md` 中"有疑问就停下来问"。教训：发布前的审计要按"数据—派生数据—派生图像—权重"逐层查，
任何沿用的旧规则都要重新审视，而不是默认它是对的。
