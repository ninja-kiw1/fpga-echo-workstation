# 案例 03：关键帧引擎移植到板上 C

## 背景

创新点 ①"相位自适应关键帧"：PL 只在关键帧做分割，中间帧由 PS 用块匹配跟踪传过去。主机上的 Python 原型验证通过后，
10-24 把它写成板端 C（`echo_num.c`、`kf.c`、`echo_quality.c`），同一份 C 在主机上编译成动态库作为参考，要求板上与主机参考逐位一致。

## 提示词

用户批准上板（10-24，原话）：

> 同意上板：prepare 编译 → 先跑心超模式 0/1 的老回归 → verify_board_echo_kf.py → 都通过再 activate 为 v5.21（回滚 v5.20），交接文档新开一节。

## 模型回答与纠错轨迹

上板验收中出现两处问题，都被验收脚本拦下，模型在启用前修好（10-24，原文）：

> **上板时查出并修好的两个问题**
> - 块匹配调用时漏传了 NEON 标志，板上每个跟踪帧要 5.5–7.5 ms；补上后降到 0.81 ms，和原先的推算一致。
> - PC 上 MinGW 的 `fma()` 不是正确舍入（2 万帧里约 20% 的容积和板上不同）。板上的结果是对的；PC 端 DLL 改用硬件 FMA 后，主机参考和板上已经逐位一致。主机上的各项数字重算后没有变化。

两处的发现方式不同：

- **NEON 标志**：靠"实测与事先推算不符"发现——推算每帧约 0.8 ms，实测 5.5–7.5 ms。
- **`fma` 舍入**：靠"主机参考与板上逐位比对"发现。模型没有直接认定板上错了，而是先判断哪一边符合 IEEE 标准，结论是主机一侧的数学库不精确，修的是参考，不是板端。

修复后，还确认了主机上已经发布的数字没有变化（"主机上的各项数字重算后没有变化"）。

## 结果与证据

- 20 段视频 × 2 套配置 = 40 次，关键帧序列、掩膜、容积、EF、质量灯、区间全部逐位一致；
- 板上跟踪 0.81 ms/帧，关键帧 PL 22.9 ms，关键帧占 17.8 %；
