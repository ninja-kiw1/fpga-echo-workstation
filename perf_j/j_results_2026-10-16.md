## 一句话

- **J1 原来设想的三种改法（链式传输、小条带改 CPU 拷贝、按节点读回）都几乎没收益**：`get` 的 79 ms 里固定开销只有 ~14 ms，其余是 PL 端口带宽。
- **找到一条真正有效的路：读回 DMA 与下一条带的输入写入并行**（IP 空闲时，AXI 读通道 ∥ 写通道）。
  测试程序里 512 整网 **471.7 → 416.9 ms（−54.8 ms，−11.6%）**，不用改内核模块、不空转 CPU；逐位一致（4 个网络 × 2 轮全 `STRICT_NET_PASS`）。
- **搬运受 PL 时钟限制**：CPU 写 BRAM 1616 MB/s = 端口上限（16 B × 101.376 MHz = 1622 MB/s）的 99.6%；
  GDMA 读 1310 MB/s = 81%。F 提频时若把 HPM1 口、`ai_data_ic`、`bram_ctrl` 一起放到新时钟上，`put` 和 `get` 也会跟着按比例缩短。
- **J3 基线**：PL 计算时间（`ap`）在任何负载下都不变；4 核满载时，推理进程用 `nice -n -20` 后 512 整网 469.5 ms（P99 471.9）= 空载，
  同样负载下 CPU 4 线程推理慢 2.07 倍（1 171 ms）。但**现在的服务跑在 nice 0**，满载时会被拖到 899 ms（睡眠等 DMA 的唤醒被抢）。
  卷积引擎利用率：卷积期间 57%、PL 计算期间 51%、整网 33%（14.8 / 13.3 / 8.6 GOPS，峰值 25.95 GOPS）。

| ---: | ---: | ---: | ---: | ---: |
| 64 B | 12.1 µs | 0.9 µs | 0.15 µs | 0.3 µs |
| 1 KB | 12.8 µs | 12.3 µs | 0.5 µs | 0.8 µs |
| 4 KB | 15.1 µs | 48.3 µs | 2.4 µs | 1.8 µs |
| 16 KB | 26.2 µs | 192 µs | 10.5 µs | 6.2 µs |
| 64 KB | 64.0 µs | 768 µs | 42.6 µs | 23.1 µs |
| 101 KB（平均条带） | 92.9 µs | 1 212 µs | 65.6 µs | 36.5 µs |

- 数据核对：256 KB 由 CPU 写入、GDMA 读回，逐字节相同。

### 3. 各改法的评估

| 改法 | 结论 | 依据 |
| --- | --- | --- |
| 多个条带合成一次链式传输 | **做不了** | 单缓冲布局下每条带的输出区被下一条带覆盖，下一条带必须等读回完才能起；条带内已经是一笔。`plbdma.ko` 一次 ioctl = 一个 `prep_dma_memcpy` 描述符，没有链式接口。双缓冲布局（才能跨条带攒）10-06 实测条带数翻倍、+115 ms |
| 小条带改 CPU 拷贝 | **0 收益** | 交叉点 ~1 KB，而 512 档最小条带 16 KB、128 档 4 KB，没有一笔小于 1 KB |
| 按节点读回 | **做不了** | 一个节点的输出 0.5–4 MB，BRAM 只有 256 KB |
| 降低每笔固定开销（改内核模块：轮询完成、不每次 map） | 上限 ~14 ms，叠加下一条后只剩暴露部分 | 下一条做完后主线程还要等 DMA 16–19 ms/帧，固定开销能砍的就在这里面 |
| **读回 DMA ∥ 下一条带的输入写入（新）** | **有效：−54.8 ms（512）** | 见下 |

### 4. 新改法：读回与写入并行

条带循环原来是：等 IP 完成 → **DMA 读回上一条带**（IP 空闲）→ **CPU 写本条带输入和参数**（IP 空闲）→ 起 IP。
读回走 AXI 读通道，写入走写通道，`bram_ctrl` 是双口模式，两者地址不重叠，而且**这时 IP 是空闲的**——
这不是已知做不了的“搬运与计算重叠”（那是 PS 与 IP 同时访问 BRAM）。

微基准（`gdma_bench overlap`，读 X 区 ∥ 写 Y 区，每次都逐字节核对 X 和 Y）：

| 读 / 写 | 串行 | 并行 | 省 | 核对 |
| --- | ---: | ---: | ---: | --- |
| 101 KB / 139 KB（平均条带） | 185.3 µs | 143.3 µs | 42.0 µs | 400 次 0 错 |
| 64 KB / 32 KB | 88.1 µs | 82.6 µs | 5.5 µs | 400 次 0 错 |
| 16 KB / 16 KB | 38.8 µs | 35.3 µs | 3.6 µs | 400 次 0 错 |

整网原型（`make_j1_proto.py` 生成 `unet_ai_j1.c`：在部署版 `unet_ai.c` `0ced96c8…` 上加一个工作线程，
上一条带的读回交给它，主线程同时写输入，起 IP 之前等它完成；环境变量开关，默认行为不变）。
`strict_net_test` 每次都与金标准逐位比对，两轮交替跑，去掉每组第一帧：

| 网络 | 部署版（中位数） | 原型：工作线程空转等待 | 原型：工作线程睡眠等待（条件变量） | 逐位 |
| --- | ---: | ---: | ---: | --- |
| 眼底 512 | 471.7 ms | 412.0 ms（−59.7） | **416.9 ms（−54.8，−11.6%）** | 全部 PASS |
| 皮肤 128 | 31.94 ms | 30.07 ms（−1.87） | 30.36 ms（−1.58） | 全部 PASS |
| 心超 128 | 31.96 ms | 30.16 ms（−1.80） | 30.34 ms（−1.61） | 全部 PASS |
| 眼底 32 | 3.39 ms | 3.40 ms | — | PASS |

（原始数据 `results/j1_ab.log/json`、`results/j1_ab2.log/json`。）

**落地建议（下一步，要用户点头）**：服务端 v5.17 = 把条件变量版原型并进 `src/unet_ai.c`（**不改内核模块、不换比特流**），
验收照 J1 的写法：17 个程序逐位一致、`get` / 整网前后对照、1000 帧稳定性。
可选的第二步：给 `plbdma.ko` 加“提交 / 等待”两个异步 ioctl，省掉线程，大约再拿回 5 ms（空转版与睡眠版之差），要重编、重载模块，收益小，排在后面。

## J3（b）：延迟分布，PL 与 CPU（r2，100 MHz，提频前基线；`results/j3b.json`）

负载：板上没有 `stress-ng`，经用户同意用自写的 `hog`（`/root/perf_j/hog.c`，90 行）：
**cpu4** = 4 线程整数循环（≈ `stress-ng --cpu 4`），**mem4** = 4 线程各 2×32 MB memcpy（≈ `--stream 4`），每线程绑一个核。
PL = `strict_net_test`（与服务端同一份 `unet_ai.c`），CPU = `cpu_unet` NEON 分块版（4 线程 / 1 线程 OpenMP）；**每一次运行输出都逐位比对，全部一致**。
去掉每组第一帧。`chrt -f` 在板上被拒（ssh / 服务所在 cgroup 的 `cpu.rt_runtime_us = 0`），所以“提高优先级”用的是 `nice -n -20`。

| --- | --- | --- | --- |
| **PL，nice −20** | 471.1 / 472.2 / 472.9（nice 0） | **469.5 / 471.9 / 471.9** | **534.1 / 542.8 / 543.3** |

| CPU 4 线程 | 565.3 / 575.9 / 579.5 | 1 171.3 / 1 184.0 / 1 184.6 | 1 183.1 / 1 195.4 / 1 195.9 |

怎么读：

- **PL 计算本身完全不受负载影响**：`ap` 中位数 空载 304.5 / cpu4 304.5 / mem4 305.9–306.2 ms（512）。
- **会被拖慢的是 PS 那一侧**：nice 0 时 cpu4 下 `get` 79 → 500 ms——每条带一次的 GDMA ioctl 在内核里睡眠等完成，
  醒来要和负载线程抢核；`put` 不变。mem4 下 `put` 77 → 114–117 ms（DDR 被抢带宽）。
- **把推理进程提到 nice −20 就恢复**：cpu4 下 512 整网 469.5 ms（P99 471.9）与空载一样；同样负载下 CPU 4 线程推理 1 171 ms（慢 2.07 倍），
  128 档 CPU 4 线程最大值 154 ms（空载 4.4 倍）而 PL 41 ms。mem4 下 PL 只慢 13%（534 ms，DDR 争用落在 `put` / `get` 上），CPU 慢 2.09 倍。
- **当前服务就是 nice 0**（`tcp-image-server.service` 没设 `Nice=`）→ 板上一旦有别的满载任务，延迟会翻倍。
  建议（要用户点头，属于板上配置改动）：服务单元加 `Nice=-20`（或给 GDMA 等待改成轮询）。J1 落地时一起做、一起验收。
- J1 原型（条件变量版）在 nice 0 满载时也会被拖慢（862 / 947 ms），所以 J1 和 `Nice=-20` 要一起上。

## J3（c）：计算效率（`j3c.py` → `results/j3c.json`）

口径：运算量按真实通道数算（与 CPU 基线 `cpu_unet.c` 的 2.028 GMAC 一致），1 MAC = 2 OP；
卷积引擎峰值 = 8 输入通道 × 8 输出通道 × XU 2 列 = **128 MAC/周期**，× 101.376 MHz = **12.98 GMAC/s = 25.95 GOPS**（卷积核占 185 个 DSP）；
全片 360 个 DSP 各 1 MAC/周期 = 73.0 GOPS（只作参照）。逐节点 `ap` 取 r2 验收的 `UNET_PROFILE`（热态那一组），整网分解取本次 A/B 的部署版中位数。

逐层（512）：3×3 卷积 60–76%（通道越多越高：16→32 通道 76%）；**1×1 卷积只有 7–45%**（每像素只有 1 个抽头，
